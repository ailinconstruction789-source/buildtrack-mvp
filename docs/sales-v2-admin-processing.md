# Admin — ตรวจใบรับและยืนยันประมวลผลติดต่อครั้งแรก

สถานะ 17 กันยายน 2569: เตรียมหน้าจอและช่องทางอ่านใบรับในเครื่อง **ยังไม่เปิดฟีเจอร์ ไม่เปลี่ยน env ไม่ติดตั้ง/รัน SQL บน Supabase ไม่อ่านข้อมูลลูกค้าจริง และไม่มี scheduler** ร่าง SQL10 ไม่ใช่ไฟล์สำหรับผู้ใช้นำไปติดตั้ง

## วิธีใช้งานที่เตรียมไว้

ทางเข้า: Lead ส่วนกลาง → **ประมวลผลและตรวจใบรับ (Admin)** หรือ `/sales-crm/sla-processing` เมื่อสวิตช์อ่านพร้อมและบัญชีมีสิทธิ์ Admin จากแหล่งเชื่อถือได้ Sales/Owner ใช้ไม่ได้

1. เปิดหน้าเพื่อตรวจสิทธิ์และอ่านรายการจำลองของงานติดต่อครั้งแรก หน้านี้ยังไม่ส่งคำสั่ง ไม่สร้าง UUID และไม่ลองคำขอค้างให้อัตโนมัติ
2. เลือกทบทวนหนึ่งงาน ตรวจลูกค้า ผู้ดูแล รหัสงาน และกำหนดบริการเดิม ผลจำลองไม่ใช่คำสั่งบันทึกและไม่รับรองผลที่จะเกิดขึ้น
3. อ่านผลกระทบและติ๊กยืนยัน จากนั้นกด **ยืนยันประมวลผลหนึ่งงาน** ระบบตรวจสิทธิ์/สวิตช์อีกครั้งและเก็บรหัสคำขอลงคิวของแท็บก่อนส่ง POST
4. หลังได้ใบรับ แสดงผลและเวลาที่ประมวลผลอย่างชัดเจน ต้องกดโหลดงานล่าสุดเองหากจะทำรายการต่อ ไม่มีการต่อคำสั่งถัดไปเป็นชุด

คำสั่งอาจบันทึกกำหนด Sales, ปิดงานจากหลักฐานติดต่อสำเร็จ, ถอนแจ้งเตือนที่ไม่ตรงหลักฐาน หรือสร้างรายการแจ้งเตือนในแอปแบบกันซ้ำ ไม่ใช่แค่การคำนวณตัวอย่าง ไม่เปลี่ยนกำหนดบริการ/วันที่เป็น Lead และไม่คิด KPI

แม้ผลจำลองเป็น `CONTACT_REVIEW` ก็เลือกให้ Server ตรวจหลักฐานจริงได้ เพราะคำสั่งประมวลผลมีการพิสูจน์หลักฐานสำเร็จละเอียดกว่าตัวจำลอง การเลือกไม่ถือว่าอนุมัติข้ามหลักฐานหรือรับรองว่าจะแจ้งเตือน

## คำขอค้างและการกู้ใบรับ

- คิวเก็บเฉพาะ Admin ID, request ID, task ID และตัวบอกความไม่แน่ชัดใน sessionStorage ของแท็บ ไม่เก็บชื่อลูกค้า เบอร์ รายได้ token หรือใบรับเต็ม
- มีคำขอค้างแล้วห้ามเริ่มรหัสใหม่หรืองานอื่น ให้กด **ตรวจใบรับคำขอค้าง** ซึ่งเป็น GET อ่านอย่างเดียว
- ถ้าพบใบรับที่ตรง Admin/request/task เดิมและตรวจรูปแบบผ่าน จึงล้างเฉพาะคิวนั้นพร้อมอ่านยืนยันว่าล้างสำเร็จ ไม่ล้างคำขออื่นที่ถูกแทนเข้ามาระหว่างรอ
- ถ้าไม่พบใบรับ ยังสรุปไม่ได้ว่าไม่เคย commit หรือคำขอไม่อยู่ระหว่างทำงาน คิวเดิมจึงคงอยู่ ห้ามสร้างรหัสใหม่อัตโนมัติ
- หากต้องลองประมวลผลซ้ำ ใช้ **ทบทวนการลองคำขอเดิม → ติ๊กยืนยัน → ยืนยันลองคำขอเดิม** เท่านั้น รหัสและงานต้องตรงคิวเดิม ไม่มีการส่งซ้ำหลังเปิดหน้า/กลับมาออนไลน์
- ทุกข้อผิดพลาดยังรักษาคิว รวมถึงครั้งถัดไปที่ถูกปฏิเสธแน่นอน เพราะไม่พิสูจน์ว่าครั้งก่อนล้มเหลว
- ได้ใบรับแล้วแต่ล้าง storage ไม่สำเร็จ จะแสดงว่าได้รับใบรับแล้วแยกจากปัญหาคิว ไม่รายงานกลับว่า “บันทึกล้มเหลว” และยังบล็อกรหัสใหม่
- หาก storage เสีย/ถูกบล็อก ยังค้นใบรับด้วยคู่รหัสที่ทราบได้ แต่ไม่อนุญาตให้ส่งใหม่และไม่มีปุ่มล้างข้อมูลเพื่อข้ามปัญหา

ช่อง **ค้นหาใบรับของ Admin บัญชีนี้** รับคู่รหัสเดิม ไม่ใช่การค้นใบรับของทุกคน การค้นใบรับเก่าคนละคำขอกับที่ค้างไม่ปลดล็อกคิวเดิม ไม่สร้างคิวหรือคำสั่งใหม่

ข้อจำกัด: คิวเป็นรายแท็บ ไม่ใช่ offline queue/ล็อกทุกแท็บ และไม่รับประกันการกู้รหัสหลังปิดแท็บหรือล้าง browser storage หน้านี้ยังไม่มีรายการประวัติใบรับทั้งหมดหรือช่องข้ามไปอ่านใบรับของ Admin คนอื่น

## แยกสวิตช์อ่านกับประมวลผล

| การทำงาน | สิ่งที่ต้องพร้อม |
|---|---|
| เปิดหน้า/อ่าน context/ค้นใบรับ | สวิตช์อ่านเดิม 6 ตัวทั้ง Server และฐาน + Admin + contract SQL10 |
| ยืนยันประมวลผล/ลองคำขอเดิม | เพิ่ม `SALES_CRM_SLA_PROCESSING_ENABLED=true` และ `sla_processing_enabled=true`; POST/SQL09 ตรวจเองอีกครั้ง |

ปิดสวิตช์ประมวลผลตัวที่ 7 แล้วยังค้นใบรับเดิมได้เมื่อส่วนอ่านยังพร้อม ไม่ต้องเปิดการเขียนเพื่อกู้ผล แต่หากปิดหนึ่งในสวิตช์อ่าน 6 ตัวหรือถอนสิทธิ์ Admin จะอ่านไม่ได้ด้วย นี่ไม่ใช่สิทธิ์กู้ข้ามบัญชี/ข้ามการปิดระบบ

เมื่อเปลี่ยนบัญชี/ออกจากระบบระหว่างอ่านหรือส่ง หน้าจะซ่อนรายการ ลูกค้า รหัสและใบรับของบัญชีเดิมทันทีตาม listener และไม่รับผลตอบกลับที่มาช้า Client ตรวจบัญชีก่อนคำขอ/หลังตอบกลับ/หลังอ่าน body อีกครั้ง การซ่อนหน้าหรือยกเลิกฟอร์มไม่ยกเลิกธุรกรรมที่ Server อาจทำสำเร็จแล้ว

## ใบรับเป็นประวัติ ไม่ใช่สถานะล่าสุด

แสดงแยก `held`, `scheduled`, `notified`, `already_notified`, `suppressed`, `completed`, `closed` พร้อมเหตุผล จำนวนแจ้งเตือนที่ถอน และเวลา `processedAt`

- พบใบรับเดิมผ่าน GET ไม่ใช่การ replay POST จึงไม่แก้ค่า `replayed` ที่เคยบันทึก
- `staffDueAt=null` ในใบรับไม่ได้แปลว่ากำหนดในตารางงานถูกล้าง โดยเฉพาะงาน completed/closed ที่เก็บค่าเดิมไว้
- ปิดงานจากหลักฐานติดต่อไม่ใช่การรับรองเครดิต KPI ว่า Sales เป็นผู้ทำ และไม่ปิดแผนติดตามครั้งถัดไป

## ขอบเขตเทคนิคและการตรวจรับ

- GET `/api/sales-crm/sla-receipts` ไม่มี query คืนสิทธิ์/ความพร้อม; มี query ต้องเป็น `requestId` และ `taskId` อย่างละหนึ่งค่าเท่านั้น รับ UUID แล้ว canonicalize ไม่รับ actor/clock/owner/ผล preview
- ใช้ public key + session token ที่ `getUser` ยืนยัน ตรวจ trusted role และ capability รุ่น `first_contact_receipt_review_v1` ไม่มี service-role/direct table access
- SQL10 เพิ่มเพียง 2 ฟังก์ชันอ่านแบบ STABLE/SECURITY DEFINER พร้อม search_path ตายตัวและ grants เฉพาะ ไม่เพิ่มตาราง/สวิตช์ ไม่เขียนใบรับ/audit/งาน/แจ้งเตือน และไม่เรียก processor
- ใบรับอ่านจาก ledger เดิมของ SQL09 โดยจำกัด actor+request+task และคัดเฉพาะฟิลด์สาธารณะ ทั้ง Server และ Client ตรวจรูปแบบ/บัญชี/คู่รหัสซ้ำ ส่ง `no-store` และ `Vary: Authorization`
- ไม่มีการเพิ่มปุ่มส่งลงหน้าจำลองหรือ inbox ทั้งสองหน้าคงพฤติกรรมเดิม ไม่มี bulk action, timer, cron, auto retry หรือผลกระทบกับส่วนลด/การจอง

ตรวจด้วย unit/component tests และ integration test ที่ต่อ UI → client → HTTP handler ผ่าน transport/RPC สมมติแยกจากการทดสอบ SQL บน PostgreSQL แยก ขอบเขตนี้ยังไม่ใช่ E2E ของ Supabase JWT/PostgREST หรือ schema/grants/trigger จริง

ผลตรวจรอบนี้: Vitest **3,558 ข้อ / 71 ไฟล์ผ่าน**, TypeScript และ ESLint ของส่วนที่แก้ผ่าน, production build ผ่านด้วย Webpack; default Turbopack ติดข้อจำกัดทรัพยากรเครื่อง ไม่เปลี่ยน config เพื่อหลบปัญหา ชุดอ่านใบรับ SQL10 ผ่าน 53 assertions ในฐานสมมติและฐานถูกหยุดแล้ว

ผลฐานแยกและข้อจำกัดอยู่ใน [รายงาน PostgreSQL แยก](D:/buildtrack/buildtrack-mvp-main/docs/sales-v2-isolated-database-tests.md) รอบถัดมาเตรียม [คำสั่งจำกัด 10 งานต่อรอบ](D:/buildtrack/buildtrack-mvp-main/docs/sales-v2-bounded-cycles.md) แยกจากหน้านี้แล้ว แต่ยังไม่มีตัวตั้งเวลา/worker หรือการเปิดจริง ต้องตรวจ concurrency/HTTP fault/capacity และ staging ก่อน migration/cutover/เปิดใช้จริง
