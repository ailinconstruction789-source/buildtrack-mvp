# เปลี่ยนผู้ดูแล / ปิด Lost และฐานการนับเวลา — ยังไม่เปิดใช้งาน

สถานะล่าสุด 16 กันยายน 2569: เตรียมหน้าเปลี่ยนผู้ดูแล/ปิด Lost พร้อมอ่านผลกระทบและยืนยันคำสั่งแล้ว เพิ่มตัวเตรียมเวรและตัววางแผนแจ้งเตือนแบบคำนวณในเครื่อง **ทั้งหมดยังปิดใช้งาน ไม่ใช่ workflow ที่เปิดใช้ครบ และไม่มี SQL ให้ผู้ใช้นำไปรันในรอบนี้** ไม่เปลี่ยน Supabase, env, บัญชี หรือข้อมูลจริง ไม่แตะระบบเขียน Lead/การขายรุ่นเก่า

รอบต่อเนื่องล่าสุด: ผู้ใช้ยืนยันให้ Admin จัดเวรในแอป จึงเพิ่มหน้า/API จัดเวรแบบเก็บรุ่นและร่าง 06 แหล่งข้อมูลเวรเตรียมแล้ว แต่ยังไม่ติดตั้งหรือใช้ส่งแจ้งเตือน ดู [คู่มือ Admin จัดเวรและสถานะล่าสุด](D:/buildtrack/buildtrack-mvp-main/docs/sales-v2-admin-work-schedule.md)

อัปเดตต่อเนื่อง 17 กันยายน: เตรียมหน้า/API กล่องแจ้งเตือนของตัวเองและปุ่มอ่านแล้ว พร้อมร่าง 07 ที่ตรวจเจ้าของ/เวร/สถานะปัจจุบัน ผู้ใช้ยืนยันเตือนล่วงหน้า 30 นาที ปรับภายหลังได้ ยังไม่คำนวณบันทึก SLA หรือส่งจริง ดู [ขอบเขตและขั้นต่อไป](D:/buildtrack/buildtrack-mvp-main/docs/sales-v2-notifications.md)

## 1. สิ่งที่เตรียมแล้ว

| กรณี | ผู้ทำได้ | ผลที่ออกแบบ | สิ่งที่ไม่เปลี่ยน |
|---|---|---|---|
| เปลี่ยนผู้ดูแลส่วนกลาง | Admin | ย้ายงานเปิดส่วนกลางไป Sales ที่ active | เจ้าของ/งานของทุกโครงการ, วันที่ Lead และกำหนดบริการ |
| เปลี่ยนผู้ดูแลรายโครงการ | Admin | ย้ายเฉพาะความสนใจและงานเปิดของโครงการนั้น | งานส่วนกลางและโครงการอื่น |
| ปิด Lost รายโครงการ | Sales เจ้าของขอบเขตหรือ Admin | ปิดเฉพาะงานก่อนจองของโครงการที่เลือก พร้อมเหตุผล | งานโครงการอื่น, แปลง, ราคา และรายการขาย |
| ปิด Lost ส่วนกลาง | Sales เจ้าของส่วนกลางหรือ Admin | ปิดได้เมื่อไม่มีความสนใจที่ยังเปิดอยู่และไม่มีประวัติจอง | ไม่ไล่ปิดโครงการอื่นตามไปด้วย |

Owner อ่านได้ตามกติกาเดิม แต่ใช้คำสั่งเขียนนี้ไม่ได้ ผู้ดูแลใหม่ต้องเป็น Sales ที่ active; Admin ช่วยย้ายงานจากผู้ดูแลเดิมที่ inactive ได้ ทุกคำสั่งต้องมีเหตุผล ไม่รองรับการเปิดกลับ/รวมลูกค้า/ยกเลิกจอง/ยืนยันโอนผ่านคำสั่งชุดนี้

Lost คือก่อนจองเท่านั้น: ตรวจประวัติการจองทั้งหมด รวมจองที่ยกเลิกหรือโอนแล้ว ไม่ใช้เพียงยอดจองที่ยัง active หากข้อมูลเก่ามี Sale ที่ยังไม่ได้เชื่อมเข้าความสนใจ ต้องตรวจการย้ายข้อมูลก่อน ไม่เดาว่าไม่เคยจอง

## 2. ย้ายงานโดยไม่ล้างประวัติ

- งานเปิดเดิมเปลี่ยนเป็น `superseded` แล้วสร้างรุ่นใหม่ที่มีผู้ดูแลคนใหม่ แต่คงข้อความงาน วันนัด และเวลาเริ่มแผนเดิม แม้งานเลยกำหนดแล้วก็รับช่วงได้
- รุ่นเก่ายังมีเจ้าของเดิม วันนัดเดิม เวลาเปลี่ยนและเหตุผล ไม่ถือว่าทำสำเร็จ ไม่สร้างกิจกรรมโทร/ติดต่อแทนการย้ายเจ้าของ
- เมื่อปิด Lost งานเปิดเปลี่ยนเป็น `cancelled` พร้อมเหตุผล ไม่ใช่ `done` หน้าแสดงประวัติแยกข้อความนี้แล้ว
- งาน SLA ที่ยังเปิดอยู่ในขอบเขตเดียวกันจะย้ายผู้รับผิดชอบโดยคง `obligation_started_at` และ `service_due_at` เดิม ส่วน `staff_due_at`/เวลาแจ้งเดิมถูกพักเพื่อทบทวนเวรและความรับผิดชอบของคนใหม่
- เก็บกำหนดประเมินเดิมในประวัติ เพิ่มเหตุผล `owner_change` และสถานะรอตรวจ `owner_change_pending_review` ไม่ให้คนใหม่รับคะแนนผิดของคนก่อนโดยอัตโนมัติ
- การปิด Lost ยุติงาน SLA เปิดเฉพาะขอบเขตนั้นพร้อมหลักฐานยกเลิก โดยเก็บวันกำหนดไว้ รายงานภายหลังต้องอ่านงานที่ยกเลิกและเวลาเคยเกินกำหนดด้วย ห้ามนับเฉพาะงานที่ยังเปิดแล้วสรุปว่าไม่เคยล่าช้า
- แจ้งเตือนเดิมที่ผูกงานเหล่านี้จะถูกระงับ ไม่ลบ ไม่ย้ายสถานะอ่านแล้วของคนก่อนให้คนใหม่ และไม่ส่งแจ้งเตือนใหม่ในรอบนี้

ส่วนนี้เป็นพฤติกรรมของร่างธุรกรรม ยังไม่ได้ทดสอบการบันทึก/สิทธิ์/การชนกันบน PostgreSQL จริง

## 3. คำสั่งและความปลอดภัย

`POST /api/sales-crm/lifecycle` รองรับ `reassign_owner` และ `close_lost` มีฟอร์มในหน้า `/sales-crm/[customerId]` แล้ว แต่หน้าและ API ยังปิดตามสวิตช์ทั้งสาม

`GET /api/sales-crm/lifecycle` ใช้สัญญา `lead_lifecycle_read_v1` คืนงาน/สิทธิ์/สถานะจาก snapshot เดียวกับบริบทเปลี่ยน Lead ตรวจขอบเขตและตัวตนให้ตรงผู้เข้าสู่ระบบ ไม่อ่านงานสองครั้งแยกกันจนเจ้าของหรือสถานะไม่ตรงกัน ไม่ใช้ช่องทางเก่าแทนเมื่ออ่านไม่ได้ ร่างอ่านไม่มีการอัปเดตข้อมูลหรือ last_seen

### 3.1 หน้าตรวจทานก่อนยืนยัน

- Admin เลือก Sales ผู้ดูแลใหม่ผ่านช่องค้นหาและรายการเลือกเฉพาะ Sales ที่ active ไม่รับ UUID ที่กรอกอิสระและไม่เลือกคนเดิม รายการส่งเฉพาะ Admin จำกัด 200 คน ถ้ามีมากกว่านั้นมีข้อความเตือนว่ารายการไม่ครบ ยังไม่มีการค้นหาทั้งฐาน
- Sales เจ้าของขอบเขตหรือ Admin ปิด Lost ได้ตามเงื่อนไขก่อนจองเท่านั้น Owner/ฝ่ายขายคนอื่นอ่านได้แต่ส่งคำสั่งไม่ได้; Admin ยังช่วยย้ายจากเจ้าของเดิมที่ inactive ได้
- ต้องกรอกเหตุผล แล้วตรวจลูกค้า/โครงการ เจ้าของเดิม–ใหม่ งานนัดที่รับช่วง จำนวนงาน SLA และแจ้งเตือนที่จะถูกระงับก่อนกดยืนยันอีกครั้ง จำนวนเป็นข้อมูล ณ เวลาโหลด ไม่ใช่การรับประกันจำนวนตอนบันทึก Server ตรวจเงื่อนไขซ้ำในรายการจริง
- จำนวนแจ้งเตือนครอบคลุมรายการที่ยังไม่ถูกระงับของงาน SLA เปิดในขอบเขตนั้น รวมรายการอ่านแล้ว เพราะการย้ายเจ้าของไม่ส่งต่อสถานะอ่านให้คนใหม่ ไม่ใช่ตัวเลข unread badge
- หากข้อมูล/สิทธิ์/สถานะเปลี่ยนหลังตรวจทาน ต้องตรวจทานใหม่ก่อนส่งครั้งแรก คำขอที่เคยส่งแล้วแต่ไม่ทราบผลยังต้องใช้ข้อมูลและรหัสเดิม ไม่สร้างคำขอใหม่จาก snapshot ใหม่
- งานติดตามกับเปลี่ยน Lead ใช้พื้นที่เขียนร่วม เปิดฟอร์มได้ครั้งละอย่าง ตรวจคิวทั้งสองก่อนสลับและก่อนส่ง ล็อกทันทีเมื่อเตรียมส่ง ไม่รอผลเครือข่าย ถ้าพบคิวค้างสองแบบ/ข้อมูลคิวเสียให้ Admin ตรวจ ไม่เลือกทิ้งเอง
- คิวแยกบัญชี/ลูกค้า/โครงการ เก็บใน sessionStorage ของแท็บก่อนส่ง หากปิดฟีเจอร์ใหม่ภายหลังแต่ยังมีคำขอค้าง จะไม่ยอมให้บันทึกงานติดตามแทนเพื่อลัดคิว การบันทึกสำเร็จแยกจากผลรีเฟรชหน้า ไม่ส่งซ้ำเพราะโหลดข้อมูลล่าสุดไม่ได้

คิวนี้ไม่ใช่ offline queue ข้ามอุปกรณ์และไม่รับประกันกู้หลังปิดแท็บ/ล้างข้อมูลเบราว์เซอร์ ต้องจด requestId ให้ Admin ตรวจใบรับก่อนเริ่มใหม่ ไม่ใส่ชื่อ เบอร์ หรือข้อมูลส่วนบุคคลในช่องเหตุผลโดยไม่จำเป็น และไม่เก็บ token ในคิว

### 3.2 ข้อตกลงคำสั่ง

คำขอมี `requestId`, `customerId`, `interestId` (null สำหรับส่วนกลาง), `expectedRevision`, `expectedActionId`, `reason`; เฉพาะย้ายเจ้าของเพิ่ม `newOwnerUserId` ไม่รับผู้ทำรายการ บทบาท วันที่ Lead กำหนดเวลา สถานะที่แต่งเอง หรือคะแนนจากฟอร์ม

- ตรวจสวิตช์ส่วนตัวฝั่ง Server ทั้ง `SALES_CRM_V2_ENABLED`, `SALES_CRM_LEAD_WORK_ENABLED`, `SALES_CRM_LIFECYCLE_ENABLED` ก่อนสร้างตัวเชื่อมฐาน และมีสวิตช์ฐานสามชั้นตรงกัน ค่าใหม่เริ่มปิด ไม่มีการแก้ env
- ตัวตนจาก session ที่ยืนยันจริง บทบาทจากตารางสิทธิ์ ไม่ใช้ metadata/service-role; คำสั่งฐานตรวจเจ้าของ/สิทธิ์ซ้ำ
- ใช้รหัสรุ่น `lifecycle_revision` แยกตามส่วนกลาง/ความสนใจและรหัสงานเปิด กันฟอร์มเก่าเขียนทับ แม้เจ้าของเคยเปลี่ยนไปแล้วกลับเป็นคนเดิม
- ช่องทางอ่านงานปรับเป็น `lead_work_read_v2` คืน `lifecycleRevision` และรองรับประวัติ `cancelled`; แอปจะไม่ยอมอ่านฐานที่ประกาศสัญญารุ่นเก่าอย่างเงียบ ๆ
- ใช้ตารางใบรับและลำดับล็อกร่วมกับคำสั่งติดตามเดิม ไม่สร้างระบบกันซ้ำอีกชุด ตรวจสิทธิ์ก่อนคืนผลคำขอเก่า แต่คืนผลเดิมก่อนตรวจสถานะที่เปลี่ยนไปแล้วจากคำขอสำเร็จ
- ยึดบทบาทผู้ทำรายการและ Sales เป้าหมายจากแถวที่ล็อกจริงจนจบรายการ ไม่ใช้แถวบทบาทใหม่ที่เพิ่งปรากฏระหว่างตรวจมาอนุญาตโดยไม่ได้ล็อก
- บันทึกงาน เจ้าของ/สถานะ ผลต่องาน SLA การระงับแจ้งเตือน ประวัติและใบรับในรายการเดียว ไม่ยอมเหลือครึ่งรายการ
- ผลตอบกลับไม่แน่ชัดต้องใช้ requestId และข้อมูลเดิม ไม่สร้างรหัสใหม่เดาว่าคำขอเก่าล้มเหลว การเปลี่ยนสิทธิ์หลังจากนั้นก็ไม่พิสูจน์ว่าครั้งแรกไม่ได้บันทึก

ร่าง [04](D:/buildtrack/buildtrack-mvp-main/sql/sales/04_lead_work_foundation_draft.sql) เพิ่ม revision/เวลาเริ่มแผนและปรับสัญญาอ่าน; ร่าง [05](D:/buildtrack/buildtrack-mvp-main/sql/sales/05_lead_lifecycle_draft.sql) เพิ่มคำสั่งเปลี่ยนผู้ดูแล/ปิด Lost ทั้งคู่มีตัวหยุดก่อนเปลี่ยนฐานและลงท้าย ROLLBACK **ห้ามถอดตัวหยุดเพื่อนำไปรันเอง** ต้องออก migration ติดตั้งที่ตรวจรับแยก

## 4. ตัวคำนวณเวลาที่เตรียมไว้

[slaClock.ts](D:/buildtrack/buildtrack-mvp-main/lib/sales/slaClock.ts) เป็นตัวคำนวณอิสระ ยังไม่เชื่อมฐาน หน้าจอ หรือตัวส่งแจ้งเตือน

| มาตรฐานบริการ | จุดเริ่มที่ต้องมีหลักฐาน | ค่าเริ่มต้น |
|---|---|---|
| ติดต่อครั้งแรก | วันที่ Lead เข้าเดิม | 24 ชั่วโมงจริง |
| ติดตามต่อเนื่อง | เวลาเกิดจริงของกิจกรรมล่าสุดที่ผ่านเกณฑ์จากฝั่ง Server | 48 ชั่วโมงจริง |
| Hot หลัง Visit | เวลาลูกค้ากลับจริง `departed_at` | 24 ชั่วโมงจริง |

กำหนดเวลาเปลี่ยนได้ด้วยนโยบายที่มีรุ่น แต่ไม่ย้อนเปลี่ยนหลักฐานเดิม ตัวคำนวณไม่เลือกเองว่ากิจกรรมใดเข้าเกณฑ์ และไม่ปิด SLA/ให้คะแนนจากผล `no_answer` หากไม่ทราบเวลาเก่าหรือเวลาออกจาก Visit ให้คืน “ขาดหลักฐาน” ไม่ใช้วันบันทึก/วันส่ง QR แทน และไม่ปัดเศษ microseconds

เวลาประเมิน Sales รองรับเฉพาะกติกาที่ตกลงชัดแล้ว: Lead เข้านอกเวลางาน → เริ่มจากช่วงทำงานจริงถัดไป → นับ 120 นาทีทำงาน ข้ามพัก/ลาได้ โดยต้องส่งช่วงเวรที่ตัดลา/พักแล้ว มีขอบเขตข้อมูลครบและตรง Sales คนนี้ ไม่มีเวร = ยังไม่คำนวณ ไม่สมมติ 09:00–18:00 หรือวันหยุดเอง

ตัวอย่างทดสอบใช้เวรสมมติเท่านั้น: เข้า 21:00 จันทร์ / เริ่มเวรอังคาร 09:00 → กำหนด Sales 11:00 แต่กำหนดบริการยังเป็น 21:00 อังคาร; ถ้ามีช่วงทำงานก่อนพักเพียง 30 นาที ให้นับอีก 90 นาทีจากช่วงหลังพัก

### 4.1 ตัวเตรียมเวรและตัววางแผนแจ้งเตือนที่เพิ่มล่าสุด

[slaCalendar.ts](D:/buildtrack/buildtrack-mvp-main/lib/sales/slaCalendar.ts) รับ snapshot เวรที่ระบุ Sales/รุ่น/ช่วงข้อมูลครบชัดเจน นำช่วงลาและพักที่ได้รับอนุมัติแล้วมารวมก่อนหักออกจากเวรจริง เก็บเวลาระดับ microseconds และที่มาของช่วงเวรโดยไม่ส่งรายละเอียดเหตุผลลา/เอกสาร HR ออกมา เวรซ้อน เจ้าของปะปน ข้อมูลไม่ครบ หรือไม่มีหลักฐานให้ไม่พร้อม ไม่เดาวันทำงานหรืออนุมัติลาแทนระบบบุคลากร

[slaReminder.ts](D:/buildtrack/buildtrack-mvp-main/lib/sales/slaReminder.ts) วางแผนเฉพาะรายการแจ้งเตือนในแอป `due_soon` / `overdue` โดยยังไม่บันทึกหรือส่งจริง:

- ต้องเป็นงานเปิดของผู้ดูแลปัจจุบันที่ active และผลคำนวณพร้อม ตรงเจ้าของ/รุ่น lifecycle/ปฏิทินทั้ง ID และรุ่น กรณีเปลี่ยนเจ้าของรอตรวจไม่แจ้งแทนคนใหม่
- ใช้ `staff_due_at` จำแนกใกล้กำหนด/เกินกำหนด ส่ง `service_due_at` เป็นบริบทเวลารอลูกค้าเท่านั้น ไม่ตีเป็น Sales ผิดหรือคะแนน KPI
- ต้องมีนโยบายระบุรุ่นและจำนวนนาทีแจ้งล่วงหน้าอย่างชัดเจน ไม่มีค่าเดาตายตัว แจ้งได้เฉพาะช่วงทำงานจริงหลังหักลา/พักและเมื่อถึงเวลาเริ่มแจ้งแล้ว
- เตรียมรหัสกันซ้ำที่คงเดิมเมื่อประมวลผลซ้ำ ไม่ใช้เวลาประมวลผลเป็นรหัสรอบใหม่ ไม่มีข้อมูลลูกค้า เหตุผลลา หรือคะแนนในผลลัพธ์
- ตัวส่งจริงในอนาคตต้องตรวจสถานะ/เจ้าของ/รุ่น/เวรซ้ำในธุรกรรม บังคับกันซ้ำต่อผู้รับ ไม่คืนชีพรายการ withdrawn และไม่ส่งต่อสถานะอ่านของคนก่อน ตัววางแผนนี้เพียงอย่างเดียวรับประกันการส่งครั้งเดียวไม่ได้

ทั้งสองโมดูลเป็นตัวคำนวณอิสระ ยังไม่เชื่อมตารางเวรจริง งานเบื้องหลัง หรือตัวส่ง หน้าแสดงแจ้งเตือนเตรียมแยกแล้วแต่ยังไม่มีตัวผลิตรายการให้ ไม่ได้ตั้งเวลาทำงาน/นโยบายในฐานให้ฝ่ายขาย และไม่ได้คิด Attendance

## 5. สิ่งที่ต้องต่อก่อนเปิดใช้งานจริง

1. ตรวจรับหน้าตรวจทาน/คำสั่งกับฐานแยก และเพิ่มทางตรวจใบรับโดย Admin สำหรับคำขอที่ผลไม่แน่ชัด ปัจจุบันมีรหัสและคำแนะนำแต่ยังไม่มีหน้าตรวจใบรับโดยเฉพาะ
2. แหล่งเวรยืนยันแล้วว่า Admin จัดในแอป และมีหน้า/API เตรียมไว้ ต่อแหล่งนี้เข้าการคำนวณ/บันทึก SLA พร้อมยืนยันวิธีประเมินช่วงเปลี่ยนเจ้าของ/ช่วงในเวลางาน กรณีไม่ทราบต้องยังไม่ลงโทษ หน้าจัดเวรไม่ใช่ระบบอนุมัติลา
3. คำสั่งบันทึกประวัติย้อนหลัง/correction ที่ไม่เลื่อนงานใหม่; การเปิดกลับ/รวมลูกค้า และเหตุการณ์ขายหลังจองต้องมีกฎเฉพาะ ไม่ใช้ close_lost แทน
4. เตรียม [คำสั่งหลังบ้านติดต่อครั้งแรก](D:/buildtrack/buildtrack-mvp-main/docs/sales-v2-first-contact-processing.md) และร่าง 09 สำหรับงานส่วนกลางเดิมแล้ว ตรวจหลักฐานกิจกรรมพร้อม audit/งานถัดไปก่อนจบงาน คำนวณ/กันซ้ำในธุรกรรม ไม่คืนชีพรายการ withdrawn ยังไม่รัน SQL/ส่งจริง ไม่สร้าง SLA ใหม่ และยังไม่รวม Follow-up/Hot/Warm/Customer Voices/Checklist หรือการให้คะแนน
5. ทดสอบธุรกรรม/RLS/คำสั่งชนกันในฐานแยก โดยเฉพาะเปลี่ยนเจ้าของชนการบันทึกติดตาม/จอง/ปิด Lead และการปิดบัญชีระหว่างทำรายการ; แก้ช่องเขียนเดิมที่กว้างก่อน cutover
6. ตรวจ mapping/backfill/สำรอง/ย้อนระบบ แล้วจึงออก SQL ติดตั้งให้ผู้ใช้ตรวจและรันเอง ไม่ใช้ร่าง 04/05 เป็น migration

KPI ยังคงยอดจองยืนยันหักยกเลิก และไม่เปลี่ยน Master/เครดิต Piwe=PIEW ที่ยืนยันแล้ว รอบนี้ไม่สร้างคะแนน HR ไม่ใช้เวลางานแทน Attendance และไม่รวมยอดโอนเพิ่มเป็นยอดขายอีกครั้ง

## 6. ผลตรวจในเครื่อง

- รอบล่าสุดก่อนแก้ผ่าน 1,155 ข้อใน 29 ไฟล์; หลังเพิ่ม UI/read/คิวร่วม/เวรและตัววางแผนแจ้งเตือน ชุดรวมผ่าน 1,608 ข้อใน 36 ไฟล์ (`--maxWorkers=1 --no-file-parallelism`)
