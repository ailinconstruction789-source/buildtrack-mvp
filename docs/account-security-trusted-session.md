# ตรวจบัญชีและบทบาทที่เชื่อถือได้ — ขั้น 2b (ในเครื่อง ยังปิดอยู่)

วันที่ 25 กันยายน 2569 ต่อจาก [รายชื่อก่อนล็อกอิน ขั้น 2a](./account-security-login-directory.md)

## สิ่งที่เตรียมแล้ว

- คงเลือกรายชื่อและ PIN 4 หลักเหมือนเดิม ไม่เปลี่ยนวิธียืนยันรหัสกับ Supabase Auth
- เพิ่มโหมดใหม่สำหรับหน้าแอปหลัก: ยืนยันตัวตนกับ Auth แล้วอ่านบทบาทจากช่องตรวจเฉพาะบัญชีที่เรียก ไม่ใช้ `user_metadata`, `app_metadata` หรือป้ายบทบาทเดิมเป็นหลักฐานสิทธิ์
- รองรับ Admin, Owner, Sales, Foreman, Site Engineer, QC, Project Planner, Procurement และ Store
- ตรวจอีกครั้งตอนคืน session, มีเหตุการณ์ Auth, กลับมาที่แท็บ และประมาณทุก 60 วินาที หากตรวจไม่ได้จะปิดหน้าใช้งาน ไม่กลับไปเชื่อบทบาทเก่า
- ถ้าผลตรวจไม่เปลี่ยน จะรักษาตัวอ้างอิงผู้ใช้เดิม เพื่อไม่กระตุ้น hook ข้อมูลเดิมให้โหลดทุกตารางใหม่ทุกนาที
- รองรับ logout ระหว่างกำลังอ่านสิทธิ์/ล็อกอิน ผลที่มาช้าไม่คืนผู้ใช้เข้าหน้าแอป และไม่สั่งออกจาก session ใหม่คนละ token โดยอาศัยผลเก่า
- รักษาการพักใช้งาน 60 นาทีในหน้าจอ พร้อมข้อความให้เข้าระบบใหม่; เวลาจาก localStorage เป็นเพียง UX ไม่ใช่ข้อบังคับความปลอดภัยฝั่งฐานข้อมูล
- บันทึกออนไลน์ผูกกับรหัสบัญชีที่ตรวจแล้วเท่านั้น ไม่รับชื่อบัญชีอื่นจากหน้าจอ; ช่องเดิมที่รับชื่อจะตรวจว่าตรงกับตัวผู้เรียก
- Admin ที่ยังไม่ผ่านการรับรองสิทธิ์จัดการบัญชีเห็นข้อความอธิบายแทนฟอร์มว่าง/ฟอร์มจัดการบัญชี การซ่อน UI ไม่ใช่ตัวควบคุมสิทธิ์ฝั่งเซิร์ฟเวอร์

## สถานะสวิตช์และ SQL

`NEXT_PUBLIC_ACCOUNT_TRUSTED_AUTH_ENABLED` เปิดเฉพาะค่า `true` เท่านั้น ค่าเริ่มต้นปิด รอบนี้ไม่เพิ่ม/เปลี่ยน env, ไม่ Deploy และไม่ติดต่อ/เขียน Supabase จริง

เมื่อสวิตช์ปิด แอปยังใช้เส้นทาง session/บทบาทเดิม จึง **ยังไม่ถือว่าปิดช่องโหว่ของระบบจริง** เมื่อเปิดแล้ว หาก RPC ใหม่หายหรือบัญชียังไม่รับรอง จะเข้าแอปหลักไม่ได้ ไม่มี fallback
สวิตช์นี้เป็นค่าที่ฝังตอน build ไม่ใช่สิทธิ์ฝั่งฐานข้อมูล และไม่ได้ครอบทุกหน้า standalone/API/RLS ของแอป

`sql/security/trusted_actor_draft.sql` เป็น DESIGN ONLY มีคำสั่งหยุดและ ROLLBACK ห้ามนำไปรันจริงหรือถอดตัวหยุดเพื่อใช้งาน
ต้องอาศัยขั้น 1 และ 2a ก่อน ร่างเพิ่มตารางส่วนตัว `reviewed_roles` ผูก Auth UUID กับ legacy user id แบบหนึ่งต่อหนึ่ง ค่าเริ่มต้น disabled พร้อมหลักฐานรับรอง ไม่มีการนำเข้าป้ายบทบาทเดิมอัตโนมัติ

ตัวตรวจฝั่งฐานข้อมูลยืนยันบัญชีไม่ถูกลบ/แบน/เป็น anonymous และ session มีอยู่ตรงบัญชียังไม่เกิน `not_after` ล็อกแถวบทบาท/บัญชี/session ระหว่าง transaction และคืนเฉพาะข้อมูลผู้เรียก
การเป็น Admin ไม่เท่ากับสิทธิ์จัดการบัญชี: ต้องตรงกับรายการ `reviewed_admins` ที่ enabled ด้วย ตัว dispatch ของขั้น 1 ตรวจทั้งสองเงื่อนไขในรอบนี้ เพื่อไม่ให้ allowlist เก่าคงสิทธิ์หลังลดบทบาท
private table เปิด RLS และถอนสิทธิ์ client; public façade เป็น SECURITY INVOKER เรียกแกน SECURITY DEFINER ที่กำหนด search_path ว่าง

การลดสิทธิ์มีผลกับคำสั่งใหม่เมื่อ transaction ที่แก้สิทธิ์ commit แล้ว ไม่ย้อนยกเลิกคำสั่งที่ได้รับอนุญาตและกำลังทำอยู่
UI รู้การเปลี่ยนสิทธิ์เมื่อการตรวจถัดไปสำเร็จ ไม่รับรอง 60 วินาทีในแท็บที่ถูกพัก/เครื่อง offline; ทุกคำสั่งธุรกิจจึงต้องตรวจสิทธิ์ฝั่งเซิร์ฟเวอร์เอง

## สิ่งที่ยังต้องทำก่อนเปิดจริง

อัปเดต: [ขั้น 3a รับรองบัญชีและกู้สิทธิ์](./account-security-role-review.md) เตรียมคำสั่งส่วนตัวและทดสอบในเครื่องแล้ว ไม่มีบัญชีจริงรับรอง และยังหยุดเมื่อพบ CRM registry ที่ไม่เชื่อม งานเปิดจริงต่อไปนี้ยังไม่เสร็จ

1. เตรียมขั้นตอนรับรองคู่บัญชี/บทบาท และผู้ดูแลกู้คืนให้ผู้ใช้ตรวจ โดยไม่คัดลอก role เดิมเป็นสิทธิ์ใหม่อัตโนมัติ ทดสอบป้องกันล็อกผู้ดูแลทุกคนออก
2. ทำเส้นทางสร้าง/เปลี่ยนบทบาท/ปิดบัญชีให้ครบ ตอนนี้สร้างบัญชีผ่านตัวเก่าไม่สร้างสิทธิ์ trusted ให้เอง และการเขียนข้อมูล Foreman จาก UI เดิมยังไม่เป็น transaction เดียวกับคำสั่งบัญชี
3. ตรวจและปรับ RLS/grants/RPC/view/trigger และผู้เรียกทุกโมดูล รวมหน้า standalone, Storage, Realtime และแหล่งบทบาท Sales V2 ให้สอดคล้องกัน อย่าเปิดโหมดใหม่โดยคิดว่าการตรวจบทบาทหน้าแอปแทนสิทธิ์ตารางได้
4. ตรวจ overload/สิทธิ์สืบทอด/เจ้าของฟังก์ชัน/search_path และ dependency จากฐานจริงก่อนจัด migration ที่ติดตั้งได้ แยกจากไฟล์ร่างเหล่านี้
5. ทดสอบ Supabase แยกจริงด้วยบัญชีสมมติ ครบ Auth login/refresh/logout, PostgREST/JWT, เก้าบทบาท, หน้าแอปทั้งเส้นทาง, rollback/กู้คืน และ public endpoint abuse protection ก่อนขออนุมัติติดตั้ง/เปิด

ฐานที่เชื่อมอยู่เป็นฐานใช้งานจริงแม้มีข้อมูลทดสอบฝ่ายขาย จึงไม่ใช่พื้นที่ทดสอบเขียนข้อมูลที่ปลอดภัยโดยอัตโนมัติ ไม่มีการย้ายลูกค้า/มอบสิทธิ์บัญชีจริงในขั้นนี้

## ผลตรวจรอบนี้

- Vitest 10 ไฟล์ **192/192 ผ่าน** รวม login UI/reader, hook ข้อมูลเดิม, trusted actor/session และความปลอดภัยตัวทดสอบ
- TypeScript เฉพาะ reader/hook/login UI และ tests: **0 diagnostics**, จำกัด heap 512 MiB ไม่ใช่ตรวจชนิดข้อมูลทั้ง app/page.tsx หรือทั้ง repository
- ESLint ผ่านสำหรับ trusted reader/hook/tests และ runtime helpers ที่เปลี่ยน
- Native PostgreSQL 17.11: ขั้น 1 **73**, ขั้น 2a **21**, ขั้น 2b **58 assertions ผ่าน** รวม **152**
- ฐานจำลองตรวจครบเก้าบทบาท, ไม่มี seed, สิทธิ์อ่าน/เขียนตาราง private, ลดสิทธิ์ Admin แต่ค้าง allowlist, session/account ใช้ไม่ได้, self-only presence ทั้งช่องใหม่และเก่า, การเปลี่ยนชื่อยังผูก id เดิม
- รายงานฐานจำลอง `node_modules/.cache/buildtrack-sales-runtime/runs/run-Ob9D48/report.json`: ผ่าน, ปิด cluster แล้ว, source files ไม่เปลี่ยนระหว่างรัน, productionChanged=false, realSupabaseAuthTested=false
- ยังไม่ได้ full production build, browser E2E หรือ Supabase Auth/PostgREST จริง ผลจำลองไม่ใช่หลักฐานผ่านของส่วนเหล่านั้น
