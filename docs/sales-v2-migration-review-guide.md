## หลักตรวจกรณีอื่นและรายการที่ยังต้องยืนยันก่อนติดตั้ง

### เบอร์ซ้ำ

สำหรับชุด 895 แถวนี้ใช้ข้อยืนยันเบอร์แทนค่าด้านบนแล้ว ไม่ต้องพิสูจน์แยกทีละเบอร์เพื่อให้ย้ายเป็นไม่ทราบได้ หลักต่อไปนี้ใช้เมื่อพบเบอร์จริงซ้ำหรือขอรวมคนภายหลัง

Admin ใช้ Lead ID จากรายงานเปิด `public.leads` ใน Table Editor แล้วกรอง `id` เท่ากับรหัสนั้นเพื่อดูชื่อ/ข้อมูลจริงในระบบของตนเอง ตรวจร่วมกับประวัติติดต่อ
สรุปเป็นหนึ่งในกรณีต่อไปนี้ พร้อมเหตุผล ผู้ยืนยัน และเวลา โดยยังไม่กดลบหรือแก้แถวเดิม:

- คนเดียวหลายโครงการ: เตรียมลูกค้ากลางหนึ่งคน เชื่อม Lead เก่าแต่ละแถวด้วย legacy ID และคงความสนใจ/ผู้ดูแลรายโครงการตามผลยืนยัน
- คนเดียวโครงการเดียวซ้ำ: ตรวจ Sales/ประวัติทุกแถวก่อนเลือกลูกค้ากลางและความสนใจที่เชื่อมร่วมกัน ไม่ทิ้งรายการขายหรือกิจกรรม
- คนละคนใช้เบอร์ร่วมกัน: แยกลูกค้ากลาง พร้อมข้อยืนยันเบอร์ร่วม ไม่สร้าง unique constraint เบอร์โทร
- ยังพิสูจน์ไม่ได้: พักเฉพาะรายการในกลุ่มไว้ใน import review ไม่รวมอัตโนมัติ และไม่ใช้สถานะผ่านของแถวอื่นมากลบกลุ่มที่ยังค้าง

จำนวนชื่อสะกดต่างกันไม่พิสูจน์ว่าเป็นคนละคน และชื่อเหมือนกันไม่พิสูจน์ว่าเป็นคนเดียวกัน

### ผู้ดูแล

สำหรับชื่อ Sales เดิมแต่ละชื่อ Admin ยืนยัน `legacy_agent_label → auth_user_id` และเหตุผลด้วยตนเอง
`candidate_requires_admin_verification` ยังไม่ใช่ผ่าน; metadata แก้ได้และไม่ใช่แหล่งอนุญาตสิทธิ์ใหม่
ชื่อไม่ตรง/ตรงหลายบัญชี/บัญชีลาออก ให้ Admin ระบุผู้รับผิดชอบที่ยังทำงาน ห้ามใช้บัญชีผู้รัน migration หรือ UUID ที่ระบบสุ่มมาแทน
ชื่อผู้ทำรายการและผู้ปิดการขายในอดีตเก็บเป็น snapshot แยกจากผู้รับผิดชอบปัจจุบัน ไม่โอนเครดิต KPI ย้อนหลังตามเจ้าของใหม่

### เงินและวันที่

ตามข้อตกลง “มูลค่าจอง” ใน Excel คือราคาขายบ้าน ไม่ใช่เงินมัดจำ ส่วนเงินจองจริงต้องตรวจหลักฐานรับเงินแยก
ตัวนำเข้าเดิมใน `lib/salesImportHelper.ts` มีทั้งการใช้ช่องเงินเดียวกัน และ fallback 10,000/50,000 บาท รวมถึงเติมวันที่ Lead/ติดต่อ จึงต้องเทียบกับต้นฉบับหรือเอกสาร
ยอด 10,000/50,000 บาทหรือเวลาที่ตรงกันอาจเป็นเรื่องจริง ห้ามสรุปว่าเป็นข้อมูลเดาและล้างทิ้งจากเงื่อนไขนี้อย่างเดียว
เก็บยอดดิบ/วันดิบพร้อมที่มาและผลยืนยัน แยกค่าที่ตรวจแล้วออกมาเพื่อย้าย; ไม่ทราบให้ unknown ไม่เปลี่ยนเป็นศูนย์หรือวันปัจจุบัน
Customer Voices 0 แถวไม่ใช่หลักฐานว่าไม่เคยมี Visit; เก็บวันเข้าชมเก่าเป็นประวัติ legacy ไม่สร้างคำตอบหรือ Visit completed ปลอมย้อนหลัง

## แผนย้ายระบบหลังปิดประเด็นตรวจ

1. ล็อก mapping ที่ Admin ยืนยัน: customer/legacy IDs, ความสนใจรายโครงการ, เจ้าของ, สถานะ และแหล่งข้อมูลเงิน/วันที่ พร้อมเวอร์ชันของ mapping
2. เตรียม migration เฉพาะรุ่นฐานที่ตรวจแล้ว แยก foundation, backfill, การสลับสิทธิ์/ช่องทางเขียน และการเปิด feature ออกจากกัน ร่างใหญ่เดิมยังไม่ใช่ไฟล์ติดตั้ง
3. กำหนดสิทธิ์ตารางส่วนกลางที่ฝ่ายก่อสร้างใช้ร่วม โดยทดสอบ Sales/Admin/Owner และบทบาทหน้างานทุกกลุ่ม ไม่ถอนสิทธิ์ทั้งหมดแบบเดา
4. สำรองและทดสอบการกู้คืนบนฐานแยก ทดลอง backfill แบบ idempotent ด้วย legacy ID ไม่ใช้ importer เก่าที่เดายอด/วันที่
5. Reconcile จำนวน Lead เก่าที่มีปลายทางครบ 895 แถวตาม snapshot นี้ โดยตั้งต้นหนึ่งลูกค้าต่อ legacy ID (จะลดได้เฉพาะการรวมที่ Admin ยืนยันภายหลัง), Sale เดิม 289 แถว, แปลง 306 แถว และยอดดิบ/ยอดยืนยัน/จำนวนไม่ทราบแยกตามสถานะ
6. แถวที่พักต้องอยู่ในรายงานค้างครบ ไม่ทำให้รายการขายเดิมหายจากการดูแล; หากยังไม่ปิดกลุ่มที่เกี่ยวกับการขายต้องไม่เปิด cutover เต็มชุด
7. เปลี่ยนช่องทางเขียนเดิมและ RLS พร้อมกันหลังทดสอบ จอง/ยกเลิก/โอน/Visit/แบบสอบถาม/นำเข้า ห้ามเปิดสองระบบเขียนซ้อน และไม่ fallback ไปตารางเก่าเมื่อ V2 ล้มเหลว
8. ก่อนเปิดใช้ทดสอบซ้ำทั้งสิทธิ์เจ้าของ การจองชนกัน ยื่นกู้ใหม่ Visit ซ้ำ และ import ซ้ำ; การคืนระบบต้องปิด DB write switch ด้วย ไม่ใช่ปิดเฉพาะ env ของแอป

ยังไม่มี deploy migration ที่อนุมัติ ผล 01–03 เป็นรายงานที่ผู้ใช้รันและส่งกลับมา ส่วน SQL ร่างผ่านเพียงการอ่าน/static checks ไม่ถือว่า unit tests ของแอปพิสูจน์ SQL/RLS หรือการย้ายข้อมูลจริงแล้ว
