# พักสิทธิ์ฝ่ายขายเมื่อ Auth แบนบัญชี — ขั้น 3d (ร่างในเครื่อง)

วันที่ 25 กันยายน 2569 ต่อจาก [ขั้น 3c](./account-security-workflow-integration.md)

ผู้ใช้ยืนยัน: **หลังปลดแบน ให้ Admin ตรวจและเปิดสิทธิ์ฝ่ายขายใหม่ ไม่คืนสิทธิ์อัตโนมัติ**

ต่อเนื่อง: มี [หน้าทดลองในเครื่องผ่าน npm run dev](./account-security-local-demo.md) ที่ `/dev/account-access` แล้ว ใช้บัญชีสมมติเท่านั้น ยังไม่ใช่หน้า Admin ที่เชื่อมคำสั่งรับรองบัญชีจริง ขอบเขตร่าง SQL ด้านล่างไม่เปลี่ยน

## ปัญหาที่ตรวจยืนยันในฐานจำลอง

ร่างขั้น 3b/3c ตรวจบัญชีและ session ของผู้เรียกแล้ว แต่การแบนใน Auth ไม่ได้เปลี่ยน `crm_user_roles.is_active` ซึ่ง QR/ตัวเลือกเจ้าของ/worker ใช้ตรวจเจ้าของงาน ชุดทดสอบใหม่จำลองก่อนติดตั้งร่าง 3d แล้วพบว่า caller ถูกปฏิเสธจริง แต่ชื่อเจ้าของยังอยู่ในตัวเลือก และ QR ของงานยังเปิดได้

เป็นการยืนยันกับ **ข้อมูลสมมติและร่างใน repository** ไม่ใช่หลักฐานว่าเกิดการใช้สิทธิ์ผิดใน Supabase จริง รอบนี้ไม่ได้อ่านหรือแก้บัญชี/ลูกค้าจริง

## สิ่งที่เตรียม

`sql/security/crm_auth_revocation_draft.sql` มี DESIGN ONLY + ROLLBACK เช่นเดิม ต้องทำ migration ที่ได้รับอนุมัติแยกภายหลัง ผู้ใช้ยังไม่ต้องรันไฟล์นี้

- เพิ่ม trigger หลัง UPDATE บัญชี Auth เฉพาะเมื่อบัญชีมีสถานะแบนที่ยังมีผล, soft-delete หรือ anonymous เพื่อปิด `is_active` ของ CRM ใน transaction เดียวกับการเปลี่ยน Auth
- เก็บหลักฐานพักสิทธิ์ส่วนตัวแบบ append-only หนึ่งรายการต่อบัญชี/รุ่นสิทธิ์ เก็บเหตุแรกที่ทำให้พัก ไม่เก็บชื่อ เบอร์ อีเมล token หรือ metadata และไม่ใช่ประวัติ Auth ทุกเหตุการณ์
- เมื่อปลดแบนหรือ ban timestamp หมดอายุ CRM ยัง inactive การเปลี่ยนเพียง `is_active=true` ถูกปฏิเสธ ต้องผ่านคำสั่งรับรองขั้น 3a ที่ตรวจบัญชียังใช้งานได้และเพิ่มรุ่นสิทธิ์ใหม่
- ขณะเตรียมติดตั้ง พัก CRM ของบัญชีที่ unavailable อยู่แล้วด้วย ไม่อนุมานประวัติการแบนที่หมดอายุและไม่มีหลักฐาน การทำจริงต้องหยุดงานเขียนที่เกี่ยวข้องก่อน
- ไม่สร้าง trigger ที่ `auth.sessions`: ออกจากระบบ/หมด session ปิดเฉพาะสิทธิ์ของคำขอนั้น ไม่หยุดความรับผิดชอบงานของ Sales หรือ QR ของลูกค้า
- ไม่แก้ Auth fields จากตัว trigger, ไม่แก้ canonical reviewed roles, ไม่ย้ายเจ้าของ Lead, ไม่แก้วันที่/เงิน/ข้อมูลลูกค้า/หลักฐานเดิม และไม่ลบรายการสิทธิ์ที่ใช้เก็บชื่อในประวัติ
- ตรวจว่าตัวหยุดสิทธิ์ยังติดตั้งและ enabled ก่อนรับรองบัญชีใหม่ การตรวจชื่อ/ชนิด trigger นี้ไม่ใช่การป้องกัน DBA ที่มีสิทธิ์แก้ระบบเอง

## ขอบเขตการคืนสิทธิ์

ขั้นนี้เจาะจง **สิทธิ์ฝ่ายขาย/CRM** ตามคำตอบผู้ใช้ ไม่เปลี่ยนบทบาทหลักหรือสิทธิ์โมดูลอื่น หลังปลดแบน ระบบ Auth อาจยอมให้ล็อกอินและอ่านโปรไฟล์บทบาทหลักได้ แต่ `crm_v2_role()` ยังคืนค่าว่างและคำสั่ง CRM ยังใช้ไม่ได้จนผ่านการรับรองใหม่

คำว่า Admin ตรวจและเปิดสิทธิ์ในร่างนี้หมายถึงการตัดสินใจรับรองตามขั้น 3a ซึ่งยังเป็นคำสั่ง operator ที่มีการตรวจหลักฐาน **ยังไม่มีหน้าจอ/ปุ่มให้ Admin เรียกคำสั่งนี้โดยตรง** ไม่ส่ง SQL owner หรือคีย์ลับไปให้ browser

การลบ Auth แบบ hard-delete ของบัญชีที่ผูกกับฝ่ายขายยังถูก FK เดิมปฏิเสธเพื่อรักษาประวัติ ทดสอบว่าข้อมูลไม่หายเมื่อถูกปฏิเสธ ไม่อ้างว่าร่างนี้ทำให้ลบบัญชีเหล่านั้นได้

## วิธีทดสอบ

ต่อชุด `node scripts/sales-runtime/run.mjs --account-security-only` ด้วยฐานใหม่ที่ยืนยัน loopback/data directory/ชื่อฐาน/ผู้ใช้ของตัวเอง ไม่อ่าน `.env` หรือเชื่อมฐานที่มีอยู่

ชุดใหม่:

1. ยืนยันช่องว่างก่อนติดตั้งร่าง แล้วทดสอบว่าร่างรันตรง ๆ ไม่ได้ และเมื่อติดตั้งเฉพาะในฐานจำลอง บัญชีถูกพักทันที
2. ตรวจ Admin เลือกเจ้าของ/รับ Lead ให้บัญชีถูกแบนไม่ได้, QR เปิด/ส่งไม่ได้, worker พักงานที่ needs_owner และถอนแจ้งเตือนโดยเก็บกำหนดบริการลูกค้าเดิม
3. ตรวจแบนซ้ำ, ban timestamp ที่หมดอายุ, soft-delete, anonymous, metadata ปลอม, การ rollback และการรับรองใหม่หลังบัญชีกลับมาใช้ได้
4. ตรวจ sign-out แยกจาก ban: caller ใช้ session เดิมไม่ได้ แต่ตัวเลือกเจ้าของ/QR/worker ยังทำงาน ไม่มีหลักฐานพักสิทธิ์ใหม่
5. ใช้บทบาท Auth operator สมมติที่แก้เฉพาะคอลัมน์จำเป็น ไม่มีสิทธิ์อ่าน/เขียนตาราง CRM ภายใน เพื่อยืนยันว่า trigger ทำงานได้โดยไม่ให้ Auth caller เข้าถึงข้อมูลลูกค้า บทบาทนี้ไม่ใช่การจำลองสิทธิ์ Supabase Auth ทั้งหมด
6. เทียบข้อมูลธุรกิจก่อน–หลังเปลี่ยน Auth ต้องเหมือนเดิม (แยกการปรับ SLA/ถอนแจ้งเตือนที่ worker ทำภายหลังออกจากการแบนเอง)
7. สังเกต backend ที่รอ lock จริงทั้งสองลำดับสำหรับ QR submit ↔ Auth ban และ operator review ↔ Auth ban ไม่ใช้เพียงการยิงคำขอพร้อมกันแล้วสมมติว่าเกิดการแข่งขัน

งานที่ถือสิทธิ์และเริ่มทำก่อนการแบนอาจเสร็จก่อนคำสั่งแบน commit ส่วนคำขอที่รอการแบนหรือมาหลัง commit ต้องถูกปฏิเสธ ไม่อ้างว่าย้อนยกเลิกธุรกรรมที่สำเร็จแล้ว

ผลรอบสุดท้าย:

- Vitest บัญชี/ล็อกอิน/ความปลอดภัยตัวทดสอบ: **221/221 ผ่าน** จาก 14 ไฟล์
- Native PostgreSQL 17.11: ชุดก่อนหน้า 342 + Auth revocation 83 = **425 assertions ผ่าน**
- รายงาน `node_modules/.cache/buildtrack-sales-runtime/runs/run-cIOk4f/report.json`: `status=passed`, `stopped=true`, `productionChanged=false`, `sourceFilesUnchanged=true`
- รอบแรก `run-BcaJgs` ผ่านก่อนเพิ่มกรณีแบนซ้ำ/หมดอายุ/พร้อมกัน จากนั้นรันชุดใหม่ครบอีกครั้งผ่าน ฐานจำลองทั้งสองรอบปิดแล้ว
- ESLint ของไฟล์ที่เพิ่ม/แก้ผ่าน และ `git diff --check` ของเอกสาร rollout ผ่าน
- ไม่ได้รัน production build/browser E2E หรือ Supabase Auth จริง ผล native ไม่แทนผลเหล่านั้น

## ยังห้ามเปิดจริง

ยังไม่แก้ Supabase จริง, ไม่ติดตั้ง migration, ไม่ Deploy, ไม่เปลี่ยน environment/feature flags/PIN/UI, ไม่ติดตั้ง cron และไม่อ่านข้อมูลลูกค้าจริง

ก่อนติดตั้งจริงยังต้อง:

- ทดสอบกับ **Supabase Auth ในระบบแยก**: signup/login/logout, ban/unban/soft-delete ผ่าน Admin API จริง, สิทธิ์/เจ้าของ trigger และปฏิสัมพันธ์กับ trigger เดิม รวมกรณีหลายบัญชีพร้อมกัน
- ตรวจว่า Auth API ไม่ล้มเหลวเพราะ trigger: trigger ผิดพลาดหรือรอ lock นานอาจทำให้การเปลี่ยน Auth rollback ได้ ต้องดูผล API/บันทึกระบบ ไม่ถือว่ากดแบนแล้วสำเร็จโดยไม่มีหลักฐาน
- ตรวจ grants/default privileges ของโครงการที่จะติดตั้งจริง โดยเฉพาะ schema ส่วนตัวและสิทธิ์ `supabase_auth_admin`; ชุด local ไม่ใช่ Supabase security advisor หรือระบบ Auth จริง
- เตรียม migration/แผนคืนค่า/ช่วงหยุดเขียน/บัญชีกู้ระบบและแนวทาง Admin รับรองใหม่ก่อนเปิด ไม่ลบหลักฐานหรือเปิด permissive policy คืนเพื่อกู้ระบบ
- ทำเส้นทางที่เหลือจากขั้น 3c และตรวจ legacy modules/Storage/Realtime/หน้าจอและ Auth จริงต่อ ไม่ถือว่ารอบนี้จบการรักษาความปลอดภัยทั้งแอป

## แนวทางอ้างอิง

ใช้หลักสิทธิ์ขั้นต่ำของ Supabase แยก Auth operator, browser และ worker และไม่ใช้ user metadata อนุมัติสิทธิ์ ออกแบบ trigger ให้ไม่ล็อกหรือเขียน canonical role ย้อนลำดับกับคำสั่งรับรอง

- [Supabase User Management](https://supabase.com/docs/guides/auth/managing-user-data): trigger ที่ผูกกับ Auth ต้องทดสอบอย่างระมัดระวัง และการลบผู้ใช้ไม่ได้ทำให้ JWT เก่าหมดอายุทันที
- [Supabase Sessions](https://supabase.com/docs/guides/auth/sessions): session ใช้แยกสิทธิ์คำขอออกจากความพร้อมของบัญชี/ความรับผิดชอบงาน
