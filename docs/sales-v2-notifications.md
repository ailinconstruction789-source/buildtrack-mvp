# กล่องแจ้งเตือนฝ่ายขาย — เตรียมในโค้ด ยังไม่เปิดใช้

สถานะ 17 กันยายน 2569: ผู้ใช้เลือก **เตือนล่วงหน้า 30 นาที ปรับภายหลังได้** บันทึกข้อตกลงนี้ในแผนแล้ว ยังไม่ตั้งค่าในฐานหรือเปิดตัวส่งจริง รอบนี้เพิ่มกล่องรับแจ้งเตือนและการกดอ่านแล้ว ไม่รัน SQL/RPC ไม่เปลี่ยน Supabase/env/บัญชี และไม่มี SQL ติดตั้งให้ผู้ใช้รัน

## 1. สิ่งที่เพิ่ม

- หน้า `/sales-crm/notifications` และทางเข้าจาก Lead ส่วนกลาง เมื่อเปิดสวิตช์ครบและตรวจสิทธิ์แล้ว ซ่อนทางเข้าใหม่ขณะฟอร์มรับ Lead เปิดอยู่
- แสดงเฉพาะแจ้งเตือนของผู้ใช้งานเอง แยกงานส่วนกลาง/รายโครงการ พร้อมลิงก์ไปงานติดตาม ไม่เลือกรับดูแทน Sales คนอื่น
- แสดงกำหนดรับผิดชอบของ Sales และกำหนดบริการลูกค้าแยกกัน เวลาไทย พร้อมจำนวนยังไม่อ่านทุกหน้าที่เข้าเกณฑ์ หน้าละ 50 รายการ โหลดใหม่ด้วยตนเอง ไม่ polling หรือเปิดหน้าแล้วอ่านให้อัตโนมัติ
- กดอ่านแล้วทีละรายการ ไม่ใช่ปิดงาน ติดต่อสำเร็จ หรือได้คะแนน KPI การบันทึกผลติดตามยังทำผ่านหน้างานตามจริง
- Admin/Owner เปิดกล่องของตัวเองได้ แต่แจ้งเตือน SLA ที่รองรับขณะนี้ต้องเป็นงานของ Sales ที่ active จึงไม่เห็นกล่องของพนักงานคนอื่น และไม่ได้เพิ่มสิทธิ์แก้ CRM ให้ Owner

หน้านี้เป็น **กล่องรับ ไม่ใช่ตัวสร้างแจ้งเตือน** หากยังไม่มีผล SLA ที่มีหลักฐานพร้อม จะไม่มีแจ้งเตือนให้เอง ไม่ใช้รายการว่างสรุปว่าทุกงานเสร็จหรือทุกคนตรงเวลา

## 2. ข้อมูลและความเข้ากันได้

ใช้ `crm_notifications` เดิม ไม่สร้างตารางแจ้งเตือนซ้ำ เพิ่มข้อมูลอ้างอิงรุ่น lifecycle/เวรและกำหนดสองชนิดแบบ nullable ในร่าง 07 แถวเดิมที่ยังไม่ผูกหลักฐานจะไม่แสดง ไม่ backfill หรือเดาว่าพร้อม

รายการที่จะอ่านได้ต้องตรงทั้งหมด: ผู้รับ/ผู้ดูแลปัจจุบันเป็น Sales ที่ active, งานเปิด, ลูกค้าไม่ถูกรวม/ปิด Lost, โครงการตรงขอบเขต, ผลคำนวณพร้อมและรุ่น lifecycle/หัวเวร/รุ่นเวรปัจจุบันตรงกัน, กำหนดเวลาตรง snapshot และไม่ถูก withdrawn ต้องมีหลักฐานว่าเวลาสร้างอยู่ในช่วงทำงานจริงหลังหักพัก/ลาและในช่วงเวรที่ยืนยันครบแล้ว

ผลคำนวณในอนาคตต้องบันทึก `evaluation_snapshot.notificationBinding` ที่มี `state: ready`, `ownerUserId`, `lifecycleRevision`, `calendarId`, `calendarVersion` จากแหล่งที่เชื่อถือได้ **รอบนี้ไม่ได้เติมหลักฐานนี้ให้ผ่านเอง** งานเปลี่ยนคนที่ยังรอตรวจไม่เข้าเกณฑ์

การอ่านแจ้งเตือนที่ส่งถูกต้องแล้วทำได้นอกเวลางาน ไม่ใช่ส่งใหม่ตอนนอกเวร เมื่อเวรเปลี่ยนรุ่น รายการรุ่นเก่าจะไม่แสดงเป็นงานปัจจุบัน จนกว่ากระบวนการคำนวณ/ส่งที่ตรวจรับแล้วจะจัดการ ไม่มีการย้ายสถานะอ่านจากผู้ดูแลคนเก่า

ร่างฐานเดิมอนุญาต SELECT แจ้งเตือนของตัวเองโดยตรง ซึ่งยังเห็นแถวอนาคต/ถอน/เก่าได้ จึงออกแบบให้ร่าง 07 ถอนสิทธิ์ตรงและอ่านผ่าน RPC ที่คัดข้อมูลเท่านั้น **ยังไม่ได้เปลี่ยนสิทธิ์จริง** ไม่ส่งข้อความอิสระเดิม เบอร์โทร รายได้ เหตุผลลา หรือข้อมูลประเมินบุคลากรในผลตอบกลับ

## 3. ช่องทางและการรับผล

| ช่องทาง | ขอบเขต |
|---|---|
| GET `/api/sales-crm/notifications?page=0` | อ่าน snapshot เดียวสำหรับรายการและจำนวนยังไม่อ่าน ไม่เขียน last_seen/read_at |
| POST `/api/sales-crm/notifications` | รับเพียง `notificationId` เพื่อทำเครื่องหมายอ่านแล้วของผู้รับปัจจุบัน |
| `crm_v2_notifications_capabilities` | ตรวจสัญญา `notifications_v1` และสวิตช์ฐาน |
| `crm_v2_notifications_snapshot` | ตรวจบทบาทและคัดรายการของ auth.uid() ไม่รับรหัสผู้รับจาก browser |
| `crm_v2_mark_notification_read` | ล็อก/ตรวจสถานะปัจจุบัน แล้วตั้ง read_at เฉพาะครั้งแรก |

API ตรวจ token จริงกับ Auth และบทบาทจากฐาน ใช้ public key ไม่ใช้ service-role; คัดผลตอบกลับและผูกกับบัญชี/หน้าที่ร้องขอ ตัดข้อความ error ภายใน ไม่ fallback ไป CRM เก่า ไม่ลองส่งซ้ำเอง

เมื่อออกจากระบบหรือเปลี่ยนบัญชี หน้า inbox ล้างข้อมูลคนเดิมและไม่รับผลคำขอเก่ามาแสดง ต้องตรวจบัญชีใหม่อย่างชัดเจนก่อนอ่านต่อ คำขออ่านแล้วที่ส่งไปก่อนหน้าอาจสำเร็จอยู่แล้ว ไม่ส่งใหม่ให้บัญชีใหม่อัตโนมัติ

คำสั่งอ่านแล้วทำซ้ำกับ **notificationId เดิม** ได้โดยไม่เลื่อนเวลาอ่านเดิม ไม่ต้องมี requestId หรือตารางใบรับอีกชุด หากรายการถูกถอน/เปลี่ยนคน/ปิดงานแล้ว จะไม่คืนข้อมูลเดิมเพียงเพราะเคยอ่านสำเร็จ ผลไม่แน่ชัดให้โหลดใหม่หรือลองรายการเดิม ไม่สรุปว่าครั้งก่อนล้มเหลว การอ่านสำเร็จแต่โหลดใหม่ไม่ได้แสดงข้อความแยกกัน

ล็อกตามลำดับที่เข้ากับ lifecycle/เวร: settings → customer → interest (ถ้ามี) → calendar head → actor role → SLA task → notification แล้วตรวจเงื่อนไขอ่านเดียวกับหน้า inbox อีกครั้ง ก่อนเปลี่ยน read_at เท่านั้น ไม่มีการแก้ Lead, SLA, เวร, การขาย หรือ KPI

## 4. สวิตช์และข้อห้าม

ต้องเปิดครบห้าสวิตช์ Server: `SALES_CRM_V2_ENABLED`, `SALES_CRM_LEAD_WORK_ENABLED`, `SALES_CRM_LIFECYCLE_ENABLED`, `SALES_CRM_SCHEDULE_ENABLED`, `SALES_CRM_NOTIFICATIONS_ENABLED` และห้าสวิตช์ฐานที่คู่กัน (`central_intake_enabled`, `lead_work_enabled`, `lead_lifecycle_enabled`, `work_schedule_enabled`, `notifications_enabled`) ค่าใหม่เริ่มปิดทั้งหมด หน้าอาจถูกสร้างตามค่า Server ตอน build; API ตรวจซ้ำทุกคำขอ การเปิดจริงต้องอยู่ในแผน build/deploy ไม่ใช่แก้ฐานอย่างเดียว

ร่าง [07_notifications_draft.sql](D:/buildtrack/buildtrack-mvp-main/sql/sales/07_notifications_draft.sql) ยังมีตัวหยุดก่อน DDL และ ROLLBACK ต้องออก migration ติดตั้งแยกหลังตรวจรับ **ห้ามถอดตัวหยุดเพื่อนำไปรัน** ไม่แก้ร่าง foundation/04/05/06 หรือสิทธิ์ฐานจริงในรอบนี้

## 5. ขั้นต่อไปก่อนส่งแจ้งเตือนจริง

1. ผู้ใช้ยืนยันกติกาเข้าในเวรแล้ว: ใช้ 24 ชั่วโมงจริง ถ้ากำหนดตกนอกเวรให้นับ 2 ชั่วโมงทำงานจากช่วงถัดไป โดยไม่เปลี่ยนกำหนดบริการ ระยะเตือน 30 นาทีคงเดิม ส่วนเปลี่ยนเจ้าของ/ลูกค้าขอเลื่อนยังพักรอตรวจ ไม่ลงโทษข้อมูลที่ยังไม่ทราบ
2. ต่อแหล่งเวรและหลักฐานเข้าตัวคำนวณติดต่อครั้งแรกแบบจำลองและหน้า Admin แล้ว ดู [หน้าตรวจแผน SLA](D:/buildtrack/buildtrack-mvp-main/docs/sales-v2-sla-preview.md) ยังต้องต่อการสร้าง/จบงานและการบันทึกรุ่นนโยบาย/เวร/เจ้าของ ไม่ให้ browser รับรองข้อมูลเอง
3. เตรียม [คำสั่งหลังบ้านประมวลผลติดต่อครั้งแรก](D:/buildtrack/buildtrack-mvp-main/docs/sales-v2-first-contact-processing.md) พร้อมร่าง 09 แล้ว ตรวจซ้ำในธุรกรรม กันซ้ำตามรุ่นเวรและคำขอ ไม่คืนชีพรายการ withdrawn ไม่เขียน notification จากการเปิด inbox ยังไม่ผูกปุ่ม/ตั้งเวลา/ส่งจริง และยังไม่รวม Follow-up/Hot/Customer Voices/Checklist
4. ทดสอบ PostgreSQL/RLS/ธุรกรรมชนกันในฐานแยก รวมเปลี่ยนผู้ดูแล/ปิดงาน/เปลี่ยนเวร/ถอนสิทธิ์ชนการกดอ่านแล้ว จากนั้นจัดการช่องเขียนเดิม นำเข้าที่ตรวจแล้ว และออก SQL ติดตั้งให้ผู้ใช้ตรวจและรันเอง

การเตรียม UI/API และร่าง SQL ไม่ได้แปลว่ามีการส่งจริงหรือเปิดประเมิน SLA/KPI แล้ว ดู [แผน rollout](D:/buildtrack/buildtrack-mvp-main/docs/sales-v2-compatibility-and-rollout.md) สำหรับผลทดสอบและงานเดิมที่รักษาไว้
