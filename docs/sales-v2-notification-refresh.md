# ขั้น1: หน้าแจ้งเตือนอัปเดตอัตโนมัติ — 23 กันยายน 2569

เพิ่มเฉพาะโค้ดหน้าจอและการทดสอบในเครื่อง ไม่เชื่อม Supabase ไม่แก้ SQL/ข้อมูล/บัญชี/ไฟล์ env ไม่เปิดสวิตช์หรือ Cron และไม่ Deploy ผู้ใช้ยังไม่ต้องรัน SQL ฟีเจอร์เดิมต้องผ่านการตรวจรับและเปิดอย่างได้รับอนุมัติก่อนใช้งานบนเว็บจริง

## พฤติกรรมที่เพิ่ม

- หน้า `/sales-crm/notifications` อ่านรายการใหม่ประมาณทุก15วินาที **หลังคำขอก่อนหน้าจบ** เฉพาะเมื่อเปิดหน้า แท็บมองเห็นและเบราว์เซอร์ไม่รายงานออฟไลน์ ไม่ใช่ timer ฝั่งเซิร์ฟเวอร์หรือการสร้างแจ้งเตือน
- พักรอบอัตโนมัติเมื่อซ่อนแท็บ/ออฟไลน์ เมื่อกลับมาครบทั้งสองเงื่อนไขจึงอ่านใหม่หนึ่งครั้ง ไม่สะสมรอบที่พลาด ถ้างานเดิมยังค้างให้รอจนจบก่อน ไม่ยิงซ้อน
- อ่านหน้าที่กำลังเปิดอยู่ ไม่กระโดดกลับหน้าแรก ไม่รวมรายการข้ามหน้า จำนวนยังไม่อ่านยังเป็นยอดทุกหน้า ปุ่ม “โหลดล่าสุด” ยังคงเป็นคำสั่งของผู้ใช้ให้กลับหน้าแรก
- ไม่ทำเครื่องหมายว่าอ่านแล้ว ไม่ปิดงาน ไม่ให้คะแนน KPI ไม่เรียก worker และไม่ลอง POST ซ้ำอัตโนมัติ
- ใช้ช่องทางอ่าน/client/API เดิมที่ตรวจผู้รับและสิทธิ์ ไม่สร้างเส้นทางอ่านข้อมูลข้ามบัญชีขึ้นมาใหม่

## การป้องกันข้อมูลและคำสั่งซ้อน

[NotificationsView](D:/buildtrack/buildtrack-mvp-main/components/sales/NotificationsView.tsx) ใช้ตัวล็อกเดียวครอบ automatic GET, manual GET และ POSTอ่านแล้วจนถึง GETยืนยันผล รหัสรุ่นคำขอกันผลตอบกลับเก่า ไม่เพิ่มรุ่นเมื่อ timer ต้องข้ามเพราะยังมีงานอยู่

การรีเฟรชอัตโนมัติคงรายการเดิมขณะรอ พร้อมแสดงว่ากำลังตรวจและหยุดปุ่มแก้สถานะ หากอ่านล้มเหลวจะซ่อนรายการเดิม ไม่ทิ้งแจ้งเตือนที่ถูกถอนสิทธิ์ไว้ให้กด และไม่ใช้ความผิดพลาดแสดงว่า “ไม่มีงาน” ลิงก์นำทางแบบอ่านยังอยู่ระหว่าง background GET เพื่อไม่ให้ผู้ใช้คีย์บอร์ดเสียตำแหน่งโฟกัส การออกจากหน้าจะทิ้งผล GET ที่มาช้า ส่วนคำสั่งเขียนยังล็อกการนำทางตามเดิม

- เปลี่ยนบัญชี/ออกจากระบบ/ยืนยัน session ไม่ได้/401/403: ล้างเนื้อหา หยุดรอบอ่าน และรอตรวจบัญชีใหม่อย่างชัดเจน
- ระบบถูกปิดหรือการติดตั้งไม่พร้อม: ซ่อนข้อมูล หยุดรอบอ่าน และให้กดตรวจสิทธิ์อีกครั้ง ไม่วนเรียกทุก15วินาทีต่อไป
- ทุกผลอ่านยังตรวจบัญชี บทบาท และหมายเลขหน้า บัญชีเดิมที่เปลี่ยนบทบาทก็ไม่รับข้อมูลมาแสดง
- เปลี่ยน API instance หรือเริ่มตรวจบัญชีใหม่: ถอด session เดิมและ timer/listener ของเดิมก่อน ไม่เอาข้อมูลที่สำเร็จจากตัวเรียกเก่ามาใช้
- ออฟไลน์: รายการที่เคยอ่านอาจยังแสดงพร้อมคำเตือนว่าไม่ล่าสุด แต่ไม่ให้กดอ่านแล้ว/เปลี่ยนหน้า/เปิดงานจากรายการนั้นจนตรวจต่อได้
- การอ่านแล้วสำเร็จแต่ GETตามหลังล้มเหลว: เก็บข้อความสำเร็จไว้ เมื่อ GET รอบถัดไปสำเร็จค่อยล้างข้อผิดพลาดการอ่าน ส่วนผล POST ที่ไม่แน่ชัดยังมีคำเตือนเดิม ไม่ถูกล้างเพียงเพราะ GET สำเร็จ

[useNotificationRefresh](D:/buildtrack/buildtrack-mvp-main/components/sales/useNotificationRefresh.ts) แยกการฟัง visibility/online/offline และการตั้งรอบอ่านออกจากกติกา inbox ใช้ timer เดียวและล้างเมื่อออกจากหน้า/ปิดสิทธิ์ รองรับ React Strict Mode และคำขอที่เร็วมากจน React รวม busy=true/false ไว้ใน render เดียว

## ขอบเขตที่ยังไม่รับรอง

1. 15วินาทีคือช่วงรอหลังคำขอจบ ไม่ใช่เพดานการตอบกลับจาก API เบราว์เซอร์อาจหน่วง timer และ client เดิมยังไม่มี timeout สำหรับ GET ที่ค้าง จึงไม่เริ่มคำขอซ้อนเพื่อทำตัวเลขให้ดูเร็วขึ้น
2. ทำงานเฉพาะหน้า inbox นี้ ไม่ใช่แจ้งเตือนบนทุกหน้าแอป ไม่ใช่ push และไม่ทำงานเมื่อปิดหน้า/ออฟไลน์ การเปลี่ยน focus ของหน้าต่างโดยที่แท็บยัง visible ไม่ได้เป็นตัวกระตุ้นพิเศษ
3. การโหลดครั้งแรกที่ไม่สำเร็จยังต้องกดตรวจสิทธิ์ใหม่ ยังไม่ติดตั้ง timer ให้หน้า error ที่ไม่เคยยืนยันบัญชีสำเร็จ
4. การกดอ่านแล้วที่เริ่มโดยผู้ใช้ก่อนซ่อนแท็บ/ออฟไลน์ยังทำต่อและพยายาม GETยืนยันตามเดิม การพักหมายถึง **รอบอ่านอัตโนมัติ** ไม่ใช่การยกเลิกคำสั่งที่อาจบันทึกสำเร็จแล้ว
5. ผล4นาที31.239วินาทีของคิวในขั้นก่อนเป็นการอ่านพบข้อมูลในฐานจำลอง ไม่ใช่ผลเวลา DB→APIผู้รับจริง→หน้าจอ ห้ามบวก15วินาทีแล้วถือว่ารับรองเป้า5นาทีบนระบบจริงได้ ต้องทดสอบครบเส้นทางในขั้น4

## การทดสอบและขั้นตอนที่เหลือ

ก่อนแก้ ชุดรวม Vitest4,201ข้อ/89ไฟล์ผ่าน ชุดทดสอบใหม่ใช้ APIสมมติและนาฬิกาควบคุมในหน้าจอจริงของ React ไม่ใช้บัญชีหรือแจ้งเตือนจริง ตรวจการอ่านตามเวลา, hidden/offline/resume, คำขอช้า, pagination, session/role/APIเปลี่ยน, ข้อผิดพลาด/การฟื้นตัว, โฟกัสคีย์บอร์ด, Strict Mode/cleanup และคำสั่งอ่านแล้วทั้งผลสำเร็จและผลไม่แน่ชัด

ผลตรวจหลังแก้:

- ชุดรวม Vitest ผ่าน **4,234 ข้อ / 90 ไฟล์** รวมกรณีใหม่ 33 ข้อและหน้าแจ้งเตือนเดิม 24 ข้อ ใช้ `npm run test -- --maxWorkers=1 --no-file-parallelism --reporter=dot` มีคำเตือน React `act` เดิมจาก HouseHandoverView แต่ไม่มีข้อทดสอบล้มเหลว
- TypeScript `npx tsc --noEmit --incremental false` ผ่าน และ ESLint ของ component, hook และไฟล์ทดสอบทั้งสองผ่าน
- การตรวจ build `npm run build -- --webpack` **ยังไม่ผ่าน**: ครั้งแรกดาวน์โหลด Google Fonts ไม่ได้ (`EACCES`); เมื่อลองด้วยสิทธิ์เครือข่ายพบ `TypeError: Cannot read properties of null (reading '1')` ในตัวโหลด `next/font` ของ Noto Sans Thai ที่ `app/layout.tsx` จุดอ่านนามสกุล URL ฟอนต์ ยังไม่ได้แก้ layout/ฟอนต์/dependency เพื่อข้ามปัญหา จึงยังไม่รับรอง production build
- build ใช้ URL Supabase สมมติ `http://127.0.0.1:9`, key สมมติ, ปิด V2 และ telemetry เฉพาะ process ไม่แก้ไฟล์ env และไม่ได้เริ่มเซิร์ฟเวอร์ ผล/แคชจาก build รอบนี้ไม่ใช่ชุดสำหรับ Deploy
- `git diff --check` ผ่าน และตรวจ SHA-256 ของ SQL ทั้ง 14 ไฟล์กับรายงานฐานแยก `run-MoFYVc` แล้วไม่เปลี่ยน
- ไม่รัน native database suite ซ้ำในรอบนี้ เพราะไม่ได้แก้ SQL หรือเครื่องมือฐานแยก ไม่ใช้ผลทดสอบ mock แทนการตรวจรับ Supabase/สิทธิ์จริง
- ยังไม่ทดสอบ E2E ด้วยบัญชีจริง การตรวจ DB→API→เบราว์เซอร์และเป้า 5 นาทีอยู่ในขั้น 4
