# Next Action และผลติดตาม — foundation ในเครื่อง

สถานะ 16 กันยายน 2569: เตรียมหน้าแสดงงาน/ฟอร์มติดตาม ช่องทางอ่าน/บันทึกฝั่ง Server และร่างฐานข้อมูลแล้ว **ยังไม่เปิดใช้งานและไม่ใช่ SQL สำหรับนำไปรัน** ไม่เปลี่ยนข้อมูลจริง ไม่ย้ายข้อมูลเก่า ไม่แก้หน้า CRM รุ่นเก่า และยังไม่ให้คะแนน KPI

สถานะต่อเนื่องล่าสุด: มีหน้าตรวจทาน/ยืนยันย้ายผู้ดูแลและปิด Lost แล้ว ควบคุมร่วมกับคิวงานติดตามไม่ให้ส่งชนกัน เพิ่มตัวเตรียมเวรหักลา/พักและตัววางแผนแจ้งเตือน แต่ยังไม่ต่อเวรจริงหรือตัวส่งแจ้งเตือน อ่าน [ขอบเขตรอบ lifecycle/SLA](D:/buildtrack/buildtrack-mvp-main/docs/sales-v2-lifecycle-and-sla.md) ร่าง 04 ใช้สัญญาอ่าน v2 และร่าง 05 เพิ่ม GET บริบท lifecycle ทั้งหมดยังปิดใช้งานและห้ามรัน SQL

## 1. ขอบเขตที่ทำในรอบนี้

- เตรียมคำสั่งตั้ง/เปลี่ยนงานถัดไป และบันทึกผลติดตามพร้อมงานถัดไปในคำขอเดียว
- แยกงานส่วนกลางของลูกค้ากับงานของแต่ละโครงการที่สนใจ; เจ้าของโครงการหนึ่งไม่ใช่สิทธิ์แก้งานของอีกโครงการ
- Sales เจ้าของขอบเขตนั้นและ Admin บันทึกได้; Owner อ่านได้ตามสิทธิ์ฐานเดิม แต่ใช้คำสั่งเขียนนี้ไม่ได้
- เก็บโทรไม่รับเป็นความพยายาม ไม่เปลี่ยนเป็นติดต่อสำเร็จ/Qualified และไม่ปิด SLA อัตโนมัติ
- เก็บแผนงานเป็นรุ่น: เปลี่ยนวันนัดได้พร้อมเหตุผล แต่กำหนดเดิมและประวัติที่เลยกำหนดยังอยู่
- ป้องกันกดซ้ำ/ส่งซ้ำ และป้องกันฟอร์มเก่าเขียนทับงานที่คนอื่นเปลี่ยนไปแล้ว

ใช้ [SQL ร่างเสริม](D:/buildtrack/buildtrack-mvp-main/sql/sales/04_lead_work_foundation_draft.sql) คู่กับ [SQL foundation เดิม](D:/buildtrack/buildtrack-mvp-main/sales_workflow_v2_draft.sql) ซึ่งทั้งสองยังไม่ติดตั้งตามข้อมูลที่ได้รับ ไม่มีการตรวจฐานสดในรอบนี้

ไฟล์ชื่อ `04` เป็น **design draft** ไม่ใช่รายงานอ่านอย่างเดียวแบบ `01–03` และไม่ใช่ขั้นที่ให้ผู้ใช้ไปรันต่อ มีตัวหยุดก่อนเปลี่ยนโครงสร้างและลงท้าย ROLLBACK ห้ามถอดตัวหยุดเพื่อใช้จริง ต้องออก migration ที่ตรวจรับแยกก่อน

## 2. จัดเก็บโดยไม่สร้างระบบซ้ำ

| ข้อมูล | ใช้ที่ใด | หลักป้องกันความขัดแย้ง |
|---|---|---|
| ผลติดตาม/ความพยายาม | ขยาย `lead_activities` ใน foundation เดิม | ไม่สร้าง contact log อีกชุด; แยกเวลาเกิดจริงกับเวลาบันทึกและผู้ลงมือจริง |
| งานถัดไป | ตารางใหม่ `crm_next_actions` | งานเปิดหนึ่งรายการต่อขอบเขต, ผูกลูกค้า/โครงการเดียวกัน, รุ่นก่อนหน้าไม่ถูกลบ |
| เหตุผล/ประวัติเปลี่ยนแผน | `crm_audit_events` เดิม | ผู้ทำรายการจาก session พร้อมแผนเดิมและกำหนดใหม่ |
| ใบรับคำขอกันซ้ำ | `sales_private.lead_work_command_requests` | ผูกผู้ส่ง+รหัสคำขอ+ข้อมูลเดิม; browser อ่าน/เขียนตรงไม่ได้ |

ไม่มีการแก้ `leads`, `sales`, `plots`, ราคาขาย, การจอง, ส่วนลด, สถานะลูกค้า/โครงการ หรือเจ้าของ Lead จากคำสั่งนี้ ไม่สร้างข้อมูลย้อนหลังให้ 895 รายการและไม่เดาค่าที่ไม่ทราบ

เมื่อแทนที่แผนเดิม รุ่นก่อนคือ `superseded` (ถูกแทนด้วยแผนใหม่) **ไม่ใช่ `done`** รายงานต้องอ่านประวัติครบ ห้ามนับเฉพาะงานเปิดแล้วสรุปว่าไม่มีงานล่าช้า ตัวตรวจหลักฐานใช้เฉพาะรุ่นที่ `open` สำหรับ Next Action ปัจจุบัน ไม่แปลง superseded เป็นงานสำเร็จ

## 3. ข้อตกลงคำสั่ง

ช่องทางบันทึก: `POST /api/sales-crm/lead-work` เพิ่มช่องทางอ่าน `GET` และหน้า UI ในรอบถัดจาก foundation ตามหัวข้อ 6 ด้านล่าง ทั้งหมดยังปิดใช้งานจริง

ฟิลด์ร่วมที่ต้องมี:

- `requestId`: UUID ของคำขอ ใช้ส่งซ้ำด้วยข้อมูลเดิมเมื่อไม่แน่ใจว่าบันทึกสำเร็จหรือไม่
- `command`: `set_next_action` หรือ `record_attempt`
- `customerId`: รหัสลูกค้า; `interestId`: UUID โครงการที่สนใจ หรือ `null` ชัดเจนสำหรับส่วนกลาง
- `expectedActionId`: UUID งานเปิดที่อ่านมาก่อน หรือ `null` เมื่อยังไม่มีงานเปิด หากไม่ตรงของจริงจะไม่บันทึก
- `nextAction`: `action` ไม่เกิน 500 ตัวอักษร และ `dueAt` วันเวลาที่มี timezone
- `reason`: เหตุผลไม่เกิน 1,000 ตัวอักษร ทุกคำสั่งต้องมี

เฉพาะ `record_attempt` เพิ่ม `attempt` ที่มี `action` ไม่เกิน 500 ตัวอักษร, `channel` (`phone/chat/email/in_person/other`), `result` (`contact_success/no_answer/customer_requested_later/other`) และ `occurredAt` เวลาเกิดจริง

ข้อความเป็นบรรทัดเดียว ห้ามอักขระควบคุมและ U+2028/U+2029; นับความยาว Unicode code points ไม่รับฟิลด์แทรกทั้งชั้นหลักและชั้นย่อย ไม่รับผู้ดูแล/บทบาท/ผู้ทำงาน/เวลาบันทึก/คะแนนจากฟอร์ม วันที่ต้องมีจริง ระบุ `Z` หรือ `±HH:mm` เศษวินาทีได้ถึง 6 หลักโดยไม่ปัดทิ้ง

ผู้ลงมือและผู้บันทึกมาจากผู้เข้าสู่ระบบจริง หาก Admin บันทึกจะระบุผู้ลงมือเป็น Admin ไม่สวมชื่อ Sales และไม่ให้เครดิต Sales อัตโนมัติ ผู้รับผิดชอบงานถัดไปยังเป็น Sales เจ้าของขอบเขตนั้น

ต้องระบุ due ใหม่ที่ยังไม่ถึงกำหนดตามเวลาฐานข้อมูล; `occurredAt` ห้ามเป็นอนาคต งานเปิดเดิมที่เกินกำหนดยังตรวจพบได้ **กิจกรรมที่เกิดก่อนสร้างงานเปิดล่าสุดจะถูกปฏิเสธในคำสั่งนี้** เพื่อไม่ให้สายเก่าไปเลื่อนกำหนดใหม่ เช่น โทรเมื่อวาน แต่วันนี้ตั้งแผนแล้ว ต้องใช้ช่องทางบันทึกประวัติอย่างเดียวในอนาคต ไม่เปลี่ยนเวลาให้ผ่าน

คำสั่งคืนเฉพาะ `{ nextActionId, activityId, replayed }`: ตั้งงานไม่มี activityId; บันทึกผลติดตามมี activityId ส่งซ้ำสำเร็จคืนใบรับเดิม ไม่เพิ่มกิจกรรมอีก

## 4. สิทธิ์และการป้องกันการชนกัน

1. ก่อนสร้างตัวเชื่อมฐาน ต้องผ่านทั้ง `SALES_CRM_V2_ENABLED` และ `SALES_CRM_LEAD_WORK_ENABLED`; ค่าไม่ใช่ `true` คือปิด ไม่ได้เปลี่ยน env ในรอบนี้
2. ใช้ public/anon key กับ Bearer ผู้ใช้รายคำขอ ตรวจตัวตนด้วย Auth และบทบาทจาก `crm_v2_role` ไม่ใช้ metadata เป็นสิทธิ์ ไม่ใช้ service-role
3. ต้องพบ capability `lead_work_v1` ที่เปิดแล้ว; ฐานต้องเปิดทั้ง `central_intake_enabled` และ `lead_work_enabled` จึงป้องกัน RPC ตรงข้ามช่องทางแอปได้ ค่าร่างเริ่มต้นปิดทั้งหมด
4. ธุรกรรมเดียวล็อกคำขอ ลูกค้า โครงการ และบทบาท ตรวจเจ้าของปัจจุบันยังเป็น Sales ที่ active; Sales คนอื่นหรือ Owner เขียนไม่ได้
5. ตรวจสิทธิ์ปัจจุบันก่อนคืนใบรับเก่า ผู้ที่เสียสิทธิ์เจ้าของไปแล้วใช้การส่งซ้ำข้ามสิทธิ์ไม่ได้
6. คำขอใหม่ต้องมี `expectedActionId` ตรงของจริง ถ้าชนกันคืน `STALE_ACTION` ให้โหลดใหม่ ไม่เขียนทับ
7. บันทึกกิจกรรม (ถ้ามี), ปิดรุ่นแผนเดิม, สร้างรุ่นใหม่, เพิ่มประวัติและใบรับคำขอในธุรกรรมเดียว หากส่วนหนึ่งพลาดต้องไม่เหลือครึ่งชุด
8. ส่งซ้ำหลังวันนัดเดิมผ่านไป ใช้ใบรับเดิมก่อนตรวจ due ใหม่ ไม่สร้างแผนซ้ำหรือบังคับเปลี่ยน requestId

UI เก็บ requestId+payload เดิมก่อนส่ง เมื่อขาดการเชื่อมต่อ/ผลสำเร็จอ่านไม่ได้จะพักคำขอไว้และให้ส่งซ้ำด้วยข้อมูลเดิม ห้ามสร้างรหัสใหม่อัตโนมัติ รหัสเดิมแต่เปลี่ยนข้อมูลจะถูกปฏิเสธเป็น `IDEMPOTENCY_CONFLICT` รายละเอียดการเก็บในแท็บเบราว์เซอร์อยู่ในหัวข้อ 6

## 5. สิ่งที่ยังไม่เปิดและขั้นถัดไป

- มีหน้าอ่านงาน/ฟอร์มใหม่ใน V2 แล้วแต่ยังปิดไว้ ไม่ต่อ LeadTracker/Kanban รุ่นเก่าและไม่มี dual-write/fallback ลงตารางเก่า
- มีฐานคำนวณ SLA 24/48/Hot 24 และหน้าจอย้ายเจ้าของ/ปิด Lost แล้ว แต่ยังไม่เชื่อมเวร/นโยบายที่ยืนยันจริง การส่งแจ้งเตือน, first_contacted_at, Qualified หรือการปิดงานหลังจอง ต้องทำก่อนเปิดจริง
- ร่าง 05 ใช้ลำดับล็อกสอดคล้องกับคำสั่งนี้ ย้ายงานเปิดโดยไม่ทับเจ้าของเดิมหรือวันนัด; คำสั่งเปิดกลับ/รวมลูกค้า/จองในอนาคตต้องใช้กติกาล็อกและ revision เดียวกัน
- ต้องมีช่องทางแก้หลักฐานผิดด้วย correction และบันทึกประวัติอย่างเดียว รอบนี้ไม่มี API แก้/ลบ/นำเข้ากิจกรรมเก่า
- ยังไม่ผูกโปรไฟล์บุคลากร ไม่หักคะแนนและไม่สร้าง KPI รายเดือน ผู้ใช้ยืนยันยอดจองสุทธิและ Piwe=PIEW แล้ว ไม่ต้องถามซ้ำ
- ต้องตรวจสิทธิ์เดิมที่กว้างเกินไป, การตัดระบบเขียนเดิมพร้อมกัน, mapping/import preview และสำรอง/ย้อนระบบก่อนออก deployment migration

รอบนี้ใช้ unit tests และ Supabase mock เท่านั้น SQL ตรวจข้อความและสัญญาข้อมูลแบบ static **ไม่ได้ execute PostgreSQL, ทดสอบ RLS หรือพิสูจน์ concurrency จริง** การผ่านชุดทดสอบไม่ได้แปลว่าติดตั้งหรือพร้อมเปิดฐานจริง

ผลตรวจ: ชุดเดิมก่อนแก้ 489 ข้อผ่าน; ชุดรวมหลังเพิ่มคำสั่ง/สัญญาข้อมูลและ static guards ผ่าน 671 ข้อใน 20 ไฟล์ พร้อม ESLint ของไฟล์ใหม่ ตัวตรวจ API ครอบคลุมการปิดก่อนเชื่อมฐาน, ฟิลด์/สิทธิ์แทรก, ขนาด/รูปแบบข้อมูล, วันเวลา/Unicode, คำขอส่งซ้ำและผลตอบกลับที่ยืนยันไม่ได้ ไม่ใช้ผล mock นี้แทนการทดสอบฐานจริง

TypeScript noEmit ผ่าน และ production build ฉบับสุดท้ายผ่าน รวม route ใหม่ รอบแรกติดการดาวน์โหลด Google Fonts ในเครือข่ายจำกัด แล้วผ่านเมื่ออนุญาตดาวน์โหลดฟอนต์ ไม่เปลี่ยนฟอนต์หรือ env ไม่เปิดหน้าแอปที่เข้าสู่ระบบและไม่รัน E2E กับข้อมูลจริง

ขั้นถัดไปที่แนะนำหลังรอบหน้าจอ: ทำ lifecycle งาน/หลักฐานย้อนหลังและ correction ที่ไม่แก้กำหนดใหม่ พร้อมเชื่อมกฎ SLA และเตรียมชุดทดสอบฐานแยก เมื่อ lifecycle/SLA และ security cutover พร้อมจึงออก SQL ติดตั้งให้ผู้ใช้พิจารณารันเอง

## 6. หน้าแสดงงานและฟอร์มติดตามที่เตรียมเพิ่ม — ยังไม่เปิดจริง

เส้นทาง `/sales-crm/[customerId]` เป็นงานส่วนกลาง; เพิ่ม `?interestId=...` สำหรับงานของโครงการหนึ่ง หน้า Lead ส่วนกลางมีลิงก์แยกสองขอบเขตเมื่อเปิดสวิตช์ทั้งสองเท่านั้น ไม่ได้ย้าย Lead หรือเปิดโครงการจากการคลิกลิงก์ หน้าใหม่เช็กสวิตช์ก่อนแสดงส่วนที่อ่านข้อมูล และ API/ฐานยังตรวจสวิตช์ซ้ำ ไม่มีการแก้ env ในรอบนี้

- อ่านชื่อ/เบอร์/เจ้าของ ขอบเขตสถานะ งานเปิด และประวัติจาก `crm_v2_lead_work_snapshot` ซึ่งเป็นคำสั่งอ่านอย่างเดียว ไม่อัปเดต last_seen หรือเรียกคำสั่งบันทึกจากการเปิดหน้า
- Sales/Admin/Owner ที่ active อ่านได้ทุกโครงการ; `canWrite` ใช้แสดงฟอร์มแก่ Sales เจ้าของขอบเขตหรือ Admin เท่านั้น ขอบเขตปิดหรือเจ้าของไม่ active จะอ่านอย่างเดียว คำสั่ง POST ตรวจสิทธิ์จริงซ้ำ ไม่เชื่อ `canWrite` จาก browser
- API ผูกตัวผู้ใช้ที่คืนมากับ session ที่ยืนยัน และผูกทุกแถวกับ customerId/interestId ที่ขอ ปฏิเสธความสัมพันธ์ผิด/ข้อมูลซ้ำ/เวลาไม่สอดคล้อง ไม่ส่งรายได้หรือ personal_data รวมมาใน snapshot
- ประวัติแผนงานและกิจกรรมคืนอย่างละไม่เกิน 20 รายการล่าสุด เรียงตามเวลาบันทึกและ ID มีธงบอกข้อมูลเก่าที่ยังไม่แสดง จึงไม่ใช่ประวัติครบสำหรับคำนวณ KPI
- แสดงกำหนดของงานปัจจุบันและงานที่ถูกแทนที่ พร้อมเหตุผล; กิจกรรมเก่าที่ไม่ทราบช่องทาง/ผู้ลงมือยังแสดงไม่ทราบ ไม่สรุปว่า Sales เป็นผู้ทำแทน
- ฟอร์มแยกตั้งงานถัดไปกับบันทึกผลติดตามพร้อมงานใหม่ วันที่กรอกและแสดงใช้กรุงเทพฯ UTC+07 ไม่ขึ้นกับ timezone ของเครื่อง ไม่เติมเวลาเกิดกิจกรรมให้เองเพื่อสร้างหลักฐานเทียม
- ตรวจผู้เข้าสู่ระบบปัจจุบันก่อน POST ว่าตรงกับผู้ที่เปิดฟอร์ม ป้องกันคำขอค้างของคนเดิมไปบันทึกในชื่อบัญชีใหม่; ตัวตนและสิทธิ์ที่ใช้จริงยังตรวจจาก Bearer ฝั่ง Server

การกันคำขอซ้ำบนหน้าจอ:

1. สร้างรหัสคำขอหนึ่งครั้ง เก็บข้อมูลที่ผ่านตัวตรวจใน sessionStorage ของแท็บก่อนส่ง โดยแยกคีย์ตามผู้ใช้/ลูกค้า/โครงการ ไม่เก็บ token ชื่อหรือเบอร์ลูกค้า
2. หากเก็บหรืออ่านกลับไม่ได้ ให้หยุดก่อนส่งและแจ้งผู้ใช้ ไม่ทิ้งคิวเดิมเงียบ ๆ เพื่อเริ่มคำขอใหม่
3. เมื่อผลไม่แน่ชัด ล็อกข้อมูลและการเปลี่ยนขอบเขตในหน้าจอ โหลดหน้าใหม่ในแท็บเดิมแล้วกู้คำขอเดิมได้ ส่งซ้ำด้วยรหัส/ข้อมูลเดิมแม้งานเปิดปัจจุบันเปลี่ยนไปแล้ว
4. หลังเคยมีผลไม่แน่ชัด หากลองอีกครั้งแล้วสิทธิ์หาย/ระบบปิด ก็ยังไม่สรุปว่าครั้งแรกไม่ได้บันทึก ต้องคงคิวและให้ Admin ตรวจรหัสคำขอ
5. ถ้าคำขอแรกถูกปฏิเสธแน่นอนเพราะงานเปลี่ยน ให้โหลดข้อมูลล่าสุดก่อนสร้างคำขอใหม่ ไม่เขียนทับด้วยรหัสเดิมหรือเปลี่ยน expectedActionId อัตโนมัติ
6. เมื่อยืนยันว่าบันทึกสำเร็จแล้ว จึงล้างคิวและโหลดหน้าใหม่ หากโหลดล้มเหลว แสดงผลสำเร็จแยกจากปัญหาการอ่าน ไม่บันทึกซ้ำ

sessionStorage อยู่เฉพาะแท็บ/เซสชันนี้ ไม่ใช่ระบบสำรองหรือที่เก็บข้อมูลถาวร มีข้อความเตือนก่อนออกขณะคำขอค้าง แต่ไม่รับประกันการกู้หลังปิดแท็บ/ล้างข้อมูลเบราว์เซอร์ กรณีผลไม่แน่ชัดควรเก็บรหัสคำขอให้ Admin ตรวจ ห้ามเริ่มคำขอใหม่โดยเดาว่าของเก่าล้มเหลว ข้อความงาน/เหตุผลที่ค้างมีข้อมูลที่ผู้ใช้กรอก จึงควรหลีกเลี่ยงการใส่ข้อมูลส่วนบุคคลเกินจำเป็น

ผลตรวจรอบหน้าจอ/GET: ก่อนแก้ 671 ข้อผ่าน; ชุดรวมล่าสุดผ่าน 832 ข้อใน 25 ไฟล์เมื่อจำกัดงานทดสอบพร้อมกันที่ 2 พร้อม TypeScript noEmit และ ESLint ของไฟล์ที่เปลี่ยน มีการทดสอบสิทธิ์อ่าน/เขียน ขอบเขตข้อมูล คำขอค้างหลังโหลดใหม่ เปลี่ยนบัญชี กดซ้ำ สถานะเปลี่ยน เวลา UTC+07 และบันทึกสำเร็จแต่โหลดใหม่ล้มเหลว โดยใช้ mock ทั้งหมด ไม่เปิดหน้าแอปกับข้อมูลจริง ผล unit/static tests ยังไม่ใช่ผลทดสอบ SQL/RLS/การทำรายการพร้อมกันใน PostgreSQL

Production build รอบหน้าจอ/GET ผ่านแล้ว รวมหน้า `/sales-crm/[customerId]` และ API ที่เกี่ยวข้อง ไม่เปลี่ยน env หรือเปิดสวิตช์ฟีเจอร์ ไม่รัน SQL/RPC และยังไม่มี SQL ติดตั้งให้ผู้ใช้นำไปรันในรอบนี้
