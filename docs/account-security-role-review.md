# รับรองบัญชีและกู้สิทธิ์ผู้ดูแล — ขั้น 3a (ในเครื่องเท่านั้น)

วันที่ 25 กันยายน 2569 ต่อจาก [การตรวจบทบาทและ session ขั้น 2b](./account-security-trusted-session.md)

อัปเดตต่อเนื่อง: [ขั้น 3b เชื่อมสิทธิ์ CRM](./account-security-crm-alignment.md) เตรียมร่างให้ CRM ปรับตามรายการรับรองใน transaction เดียวกัน พร้อมทดสอบคำสั่ง Lead บางส่วนแล้วในเครื่อง เงื่อนไขหยุดเมื่อพบ CRM ด้านล่างยังใช้เมื่อมีเฉพาะขั้น 3a หรือยังไม่ติดตั้ง guard ชุดเชื่อมครบ ไม่ได้เปิดใช้ฐานจริง

## ผลงานรอบนี้

เตรียม `sql/security/role_review_draft.sql` และชุดทดสอบฐานจำลองสำหรับการรับรอง/เปลี่ยน/ปิดสิทธิ์ทีละบัญชี โดยไม่เพิ่มบัญชีจริง ไม่เปลี่ยน PIN ไม่เปลี่ยน UI และไม่เปิดสวิตช์ใด
ไฟล์ยังเป็น **DESIGN ONLY + ROLLBACK** ไม่ใช่ migration พร้อมติดตั้ง ห้ามถอดตัวหยุดเพื่อนำไปรันจริง

ร่างเพิ่ม:

- คำสั่งส่วนตัว `account_security_private.review_account_role` แบบ SECURITY INVOKER สำหรับเจ้าของตารางในฐานข้อมูลเท่านั้น ไม่ใช่สิทธิ์ Admin ในแอป ไม่เปิด public RPC และไม่ให้ anon/authenticated/service_role เรียก
- ระบุ Auth UUID และ legacy user id ที่รับรองแล้วอย่างชัดเจน พร้อมชื่อและอีเมลที่คาดว่าจะพบ ถ้าเปลี่ยนชื่อ/อีเมลหรือผูกคนละรหัสจะหยุด ไม่จับคู่จากชื่อคล้ายกันเอง
- ระบุหนึ่งในเก้าบทบาท, เปิด/ปิด, สิทธิ์จัดการบัญชี, ผู้ตรวจ, เอกสารอ้างอิง และเลขรุ่นที่ตรวจ ถ้ามีคนแก้รายการก่อนจะปฏิเสธผลตรวจเก่า
- สิทธิ์จัดการบัญชีให้ได้เฉพาะ Admin ที่ enabled และต้องมีอ้างอิงการตรวจทางกู้คืน ข้อมูลอ้างอิงเป็นบันทึกการตรวจของคน ไม่ใช่การที่ระบบพิสูจน์ตัวบุคคล/ทดสอบ recovery ให้แล้ว
- เปลี่ยนสองรายการ `reviewed_roles` และ `reviewed_admins` พร้อมบันทึกประวัติใน transaction เดียว หากไม่ผ่านให้ย้อนทั้งคำสั่ง
- ป้องกันปิด/ลดบทบาท/ถอดสิทธิ์จัดการบัญชีจนไม่เหลือ Admin ที่เปิดใช้งานและไม่ถูกลบ/แบน/เป็น anonymous ผ่านคำสั่งนี้ รวมเมื่อถอนพร้อมกันสองบัญชี
- เก็บก่อน/หลัง, ผู้ดำเนินการ SQL, ผู้ตรวจและอ้างอิงใน `role_review_events` ไม่คัดลอก PIN/password/token/email เข้า history; ป้องกัน UPDATE/DELETE/TRUNCATE ปกติ และประวัติไม่หายตามการลบบัญชี
- ใช้ล็อกกลางและ READ COMMITTED เพื่อให้คำสั่งพร้อมกันเห็นผลล่าสุด; ไม่รองรับ snapshot isolation สำหรับช่องรับรองนี้

ไม่มี seed หรือการเลือก Admin จากป้ายบทบาทเดิม ร่างไม่เขียน `auth.users`, metadata, `public.users.role` หรือข้อมูลลูกค้า และไม่อ้างว่าทำสิทธิ์ทั้งแอปสอดคล้องแล้ว

## ข้อจำกัดที่ต้องเข้าใจ

- การป้องกัน Admin คนสุดท้ายครอบคลุมคำสั่งรับรองนี้เท่านั้น การแบน/ลบบัญชีจาก Supabase Auth, SQL โดยตรง, การแก้ ACL/trigger ของ DBA หรือการสูญเสียรหัสยังทำให้เข้าไม่ได้ จึงต้องมีผู้ดูแลแพลตฟอร์มกู้คืนที่ตรวจแล้ว
- ไม่มี session เดิมก็ทำ bootstrap/recovery ได้ แต่ต้องเป็นผู้ดำเนินการฐานข้อมูลที่ได้รับอนุญาตและตรวจตัวบุคคลแล้ว ไม่ใช่ช่อง bypass ให้ผู้ใช้ในแอป
- history ป้องกันการแก้ปกติ ไม่ใช่บันทึกที่ DBA ปลอมแปลงไม่ได้; ยังต้องออกแบบการส่งออก/เก็บหลักฐานภายนอกตามนโยบายจริง
- การ retry หลังคำตอบหายไม่เขียนทับอัตโนมัติ: อ่าน revision/history แล้วตรวจผลก่อน หากส่ง revision เก่าจะได้ `ROLE_REVIEW_STALE_REVISION`
- การรับรองใหม่ไม่ย้าย binding เดิมเป็นคนอื่น ถ้าจับคู่ผิดต้องหยุดและทบทวนเป็นเหตุการณ์เฉพาะ ไม่ล้าง FK หรือทับรายการเพื่อผ่าน
- แถว reviewed_admins เดิมแม้ disabled ยังคง FK ป้องกันการลบตามแบบขั้น 1; ไม่ได้เพิ่มคำสั่งลบผู้ดูแลถาวร
- **ถ้ามี `sales_private.crm_user_roles` แล้ว คำสั่งหยุดด้วย `ROLE_REVIEW_CRM_ALIGNMENT_REQUIRED`** จนกว่าจะทำการเชื่อมสิทธิ์ร่วมกัน ไม่ปล่อยให้ลดสิทธิ์แอปหลักแต่ยังค้างสิทธิ์ CRM การติดตั้ง Sales ในภายหลังยังต้องผ่าน gate นี้ ไม่ถือว่าร่างนี้รองรับการเปิดทั้งสองระบบแล้ว

## ใบรับรองที่จะต้องให้ผู้ใช้ตรวจในขั้นเปิดจริง

เตรียมผ่านผู้ดูแลที่ได้รับอนุญาตเท่านั้น ไม่เก็บรายชื่อจริงไว้ใน git หรือในตัวอย่าง SQL

| รายการ | ต้องตรวจอะไร |
|---|---|
| บัญชีและคู่รหัส | Auth UUID + legacy user id + ชื่อ/อีเมลปัจจุบันเป็นคนเดียวกันจริง ไม่เดาจากชื่อ |
| บทบาท | หนึ่งในเก้าบทบาทตามหน้าที่ ไม่ใช้ metadata เก่าเป็นหลักฐานอนุมัติ |
| สิทธิ์จัดการบัญชี | ตัดสินใจแยกจากการเห็นหน้าจอ Admin |
| ผู้รับรอง/หลักฐาน | ผู้ใช้อนุมัติใคร บทบาทอะไร และเอกสาร/เลขอ้างอิงใด |
| เลขรุ่น | อ่าน revision ล่าสุดก่อนทำรายการ; ทบทวนใหม่เมื่อมีการแก้ระหว่างทาง |
| ทางกู้คืน | ผู้ดูแล Supabase ที่เข้าถึงโปรเจกต์ได้จริงและผ่านการซ้อมกู้คืนในระบบแยก ห้ามใส่รหัสหรือ key ในช่องอ้างอิง |

ชื่อ TAEW/TEAW และ Piwe/PIEW ที่เคยยืนยันใช้เป็นข้อมูลประกอบตรวจคู่บัญชีได้ แต่ไม่ใช่การอนุมัติให้เป็น Admin หรือสั่งเปลี่ยนชื่อบัญชีรอบนี้

## ขั้นตอนกู้คืนที่เสนอ (ยังไม่ดำเนินการ)

1. หยุดการเปลี่ยนสิทธิ์และยืนยันปัญหาว่ามาจากบทบาท, session, บัญชีถูกระงับ หรือรหัส อย่าเปิดสิทธิ์ตาราง/PUBLIC EXECUTE เพื่อแก้ชั่วคราว
2. ผู้ดูแลแพลตฟอร์มที่ได้รับอนุญาตยืนยันคู่บัญชีและหลักฐาน ถ้าบัญชีถูกแบน/ลบต้องจัดการผ่านกระบวนการ Auth ที่อนุมัติแยก ร่างนี้ไม่ปลดแบน
3. ใช้ช่องรับรองส่วนตัวสร้าง/เปิดคู่บทบาท Admin และสิทธิ์จัดการบัญชีพร้อมกัน ในขณะที่ไม่พึ่ง session Admin เดิม
4. ตรวจ history และ revision แล้วทดสอบ login ใหม่จริง รวมคำสั่งที่ควรอนุญาต/ปฏิเสธ จากนั้นค่อยเปลี่ยนผู้ดูแลเดิม ห้ามลดคนเดิมก่อนยืนยันว่าทางใหม่ใช้ได้
5. ทบทวนสาเหตุและสิทธิ์ทุกโมดูล โดยเฉพาะ CRM registry ที่ยังไม่เชื่อม ห้ามถือว่าแก้ role แอปหลักเท่ากับเพิกถอนทุกช่องทางแล้ว

## ผลตรวจความสอดคล้องกับโมดูลเดิม

อ่านโค้ด/SQL ใน repository เท่านั้น ไม่อ่านรายชื่อพนักงานจริงหรือข้อมูลลูกค้า และไม่รันตรวจฐานจริงซ้ำในรอบนี้
SQL เก่าหลายไฟล์ขัดกัน จึง **ไม่สรุปว่าทุก policy ในไฟล์ถูกติดตั้งอยู่จริง** ต้องเทียบ catalog ในระบบแยก/ฐานที่อนุญาตก่อนจัด migration

| จุดเชื่อม | หลักฐานใน repository | งานที่ต้องทำก่อนเปิด |
|---|---|---|
| หน้าแอปหลักและบัญชี | `app/page.tsx` ยังมี metadata ในเส้นทาง legacy ที่สวิตช์ใหม่ปิดไว้; `hooks/useSessionTimeout.ts` ยังมี metadata แต่ไม่พบจุด import ใช้งานจาก app/components/hooks | ตรวจทางเข้าทุกหน้า; ไม่อ้างว่ามี hook ใหม่แล้ว legacy ทั้งหมดปลอดภัย |
| Lead/จอง/รายงานส่วนกลาง | `sales_workflow_v2_draft.sql` นิยาม `crm_user_roles`/`crm_v2_role`; `lib/sales/centralServer.ts` ตรวจ Auth แล้วเรียก role/capabilities แยกจาก reviewed_roles | รวมแหล่งบทบาทและวงจรถอนสิทธิ์ พร้อมทดสอบไม่ให้ข้อมูลเจ้าของ Lead/ประวัติ/เครดิต KPI เปลี่ยนตามการแก้สิทธิ์ |
| หน้า Sales/Owner โดยตรง | `app/sales/page.tsx`, `app/owner/page.tsx` เรียก entry ของตน ไม่ผ่าน hook หน้าแรก; entry เลือก legacy หรือ central | ทดสอบ URL ตรง/refresh/logout; navigation gate ไม่ใช่ authorization gate |
| legacy ฝ่ายขาย | `components/sales/SalesKanban.tsx` ยังเขียน leads/sales/plots/status_history โดยตรง รวม import/delete; `sales_system_migration.sql` ใช้ JWT user_metadata ใน policy | ปิด legacy writers พร้อมการย้าย ไม่ใช้การซ่อนแท็บแทนการถอนสิทธิ์ |
| โครงการ/แปลง/งานก่อสร้าง | `supabase_security_migration.sql`, `patch_rls_roles.sql`, `fix_rls_final.sql` ใช้ user_metadata และมี broad policy บางตาราง; `ultimate_fix.sql` ใช้ latest_role ในแถวแทนผู้เรียก | ตรวจนโยบายจริงรวมทุก permissive policy; ทำ matrix ตามบทบาท/งานที่มอบหมาย ไม่เพิ่ม restrictive policy แบบเหมารวมจนทีมก่อสร้างหยุดทำงาน |
| จัดซื้อ/สโตร์/แจ้งเตือนเดิม | `add_task_material_requests.sql`, `add_material_receipts.sql`, `database_migrations.sql` มี USING/WITH CHECK true; hook กรองผู้รับแจ้งเตือนใน client | บังคับผู้รับและผู้แก้ที่ฐานข้อมูล แยกแจ้งเตือนเดิมจาก inbox Sales V2 |
| ไฟล์และข้อมูล realtime | `fix_rls_final.sql` จำกัด Storage ด้วย bucket task_images แต่ไม่แยกเจ้าของ; `app/page.tsx` สร้าง public URL; hook อ่าน views และ subscribe task_updates | ตรวจ bucket public/private, object ownership, view security_invoker, publication/RLS; ไม่สรุปจาก UI ว่าไฟล์ส่วนตัวปลอดภัย |
| การสร้างบัญชี/Foreman | หน้า app เพิ่ม/ลบ foremen ก่อนเรียก account RPC; บัญชีใหม่ยังไม่มี reviewed role โดยอัตโนมัติ | ทำ provisioning/ปิดบัญชีแบบ atomic และแสดงสถานะรอรับรอง ไม่แอบให้สิทธิ์จาก role ที่ส่งมาจากฟอร์ม |

ลำดับถัดไปที่แนะนำ: **เชื่อมแหล่งสิทธิ์แอปหลักกับ Sales V2 ก่อน** แล้วจึงเปลี่ยน policy/caller ที่เกี่ยวข้องเป็นชุด พร้อม regression ของฝ่ายขายและก่อสร้าง ยังไม่เปิดใช้ระบบใหม่

## การตรวจในเครื่อง

- Vitest เฉพาะบัญชี/ล็อกอิน/ความปลอดภัยตัวทดสอบ: 11 ไฟล์ **198/198 ผ่าน**
- Native PostgreSQL 17.11: ขั้น 1/2a/2b เดิม 152 assertions และชุด role review เพิ่ม 48 assertions รวม **200 ผ่าน**
- รายงาน `node_modules/.cache/buildtrack-sales-runtime/runs/run-RRiX1N/report.json`: status=passed, stopped=true, productionChanged=false, sourceFilesUnchanged=true; ฐานจำลองรอบก่อนหน้าก็ปิดแล้ว
- ESLint ผ่านเฉพาะ runtime helpers/tests ที่แก้ ไม่ใช่ lint ทั้ง repository
- ทดสอบทั้ง bootstrap ว่าง, recovery ไม่มี session, ปิด/ลด Admin คนสุดท้าย, backup ถูกแบน, สองคำสั่งถอนสิทธิ์พร้อมกัน, สองคำสั่ง revision เดียวกัน, ACL/service-role denial, เก้าบทบาท, audit rollback/append-only/คงอยู่หลังลบบัญชี และ gate CRM
- ไม่ได้เปลี่ยน TypeScript/UI ในรอบนี้ ไม่รัน production build/browser E2E ไม่ได้ทดสอบ Auth/PostgREST จริง และไม่ได้รัน advisors กับฐานจริงเพราะไม่ติดตั้ง schema ใหม่ที่นั่น
