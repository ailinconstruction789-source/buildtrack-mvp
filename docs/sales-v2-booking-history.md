# การจองจาก Lead ส่วนกลางและประวัติทุกครั้ง

23 กันยายน 2569 — เตรียมในเครื่องเท่านั้น ยังไม่เปิดใช้งานจริง

รอบต่อเนื่อง: เพิ่ม [ตัวอ่านลูกค้าจองรายโครงการและทางเข้าสำหรับเปลี่ยนระบบ](D:/buildtrack/buildtrack-mvp-main/docs/sales-v2-project-sales-reader.md) ในเครื่องแล้ว ข้อ “ต้องเปลี่ยนตัวอ่าน” ด้านล่างเป็นสถานะก่อนรอบต่อเนื่อง; ยังไม่เปิดสวิตช์หรือยุติ legacy ทั้งระบบ

## สิ่งที่เชื่อมแล้ว

- หน้า `/sales-crm/bookings` เปิดจากลูกค้าคนเดิมใน Lead Tracker หรือค้นชื่อ/เบอร์จากทุกโครงการก่อนสร้างใหม่ ผลค้นหาแบ่งหน้า 25 คน ไม่รวมลูกค้าจากชื่อ/เบอร์อัตโนมัติ
- ลูกค้าเดิม: เลือกโครงการและแปลงว่าง พร้อมราคาก่อนส่วนลด ส่วนลด เงินจอง วิธีชำระ และเหตุผล บันทึกเป็น sale ใหม่ที่เชื่อม customer/interest เดิม
- ลูกค้าใหม่มาจองเลย: สร้าง Lead ส่วนกลาง ความสนใจ และการจองใน transaction เดียว ถ้าแปลงไม่ว่างหรือขั้นใดล้มเหลว ให้ยกเลิกการบันทึกทั้งชุด ไม่สร้าง legacy Lead อีกชุด
- Sales สร้างลูกค้าใหม่เป็นเจ้าของเอง; Admin ต้องเลือก Sales ผู้ดูแล; โครงการที่มี interest อยู่แล้วตรวจเจ้าของ interest ไม่ใช้สิทธิ์เจ้าของลูกค้าทับสิทธิ์รายโครงการ
- ราคาขายบ้าน = ราคาก่อนส่วนลด − ส่วนลด ใช้จำนวนเต็มสตางค์ในคำสั่ง ไม่ปัดเศษเงียบ ๆ เงินจองแยกจากราคาขาย ไม่มีขั้นอนุมัติส่วนลด
- จองหลัง Visit ใช้หลักฐาน Visit ของความสนใจเดียวกันที่ส่ง Customer Voices แล้วเท่านั้น; ถ้าจองโดยไม่มี Visit สำเร็จ ต้องมีเหตุผล ไม่สร้าง Visit ปลอม
- ยกเลิก: เปลี่ยน sale นั้นเป็น cancelled เก็บวัน เหตุผล ประเภท ราคา แปลง และ audit ไว้ คืนแปลงเฉพาะเมื่อไม่มีรายการขายอื่นครอบครอง ห้ามยกเลิกหลังโอน/ส่งมอบผ่านคำสั่งนี้
- กลับมาติดตาม: ผู้ใช้เลือกเอง ใส่เหตุผล งานถัดไป และกำหนดเวลา ไม่เปลี่ยน sale ที่ cancelled แม้แต่ revision ไม่รีเซ็ตวันที่เป็น Lead ไม่กระทบการจองแปลงอื่น
- จองใหม่ต่อจากรายการยกเลิก: sale ID และ booking round ใหม่ อ้าง previous_sale_id โดยผู้ใช้เลือกเอง ไม่แก้ทับรอบก่อน
- หน้าประวัติอ่านทุกรอบทั้งที่ยังจองและยกเลิก แบ่งหน้า 50 รายการ ราคา/วันที่/แปลงเก่าที่ไม่มีหลักฐานแสดง “ไม่ทราบ”

## ป้องกันการบันทึกซ้ำและสิทธิ์

API รับ JWT ของผู้เรียก ตรวจตัวตนและบทบาทจากฐาน ไม่เชื่อ role/owner ที่ browser ส่ง ไม่ใช้ service-role key ไม่เขียนตารางจาก browser แทนเมื่อระบบใหม่ไม่พร้อม

คำสั่งจองใช้รหัสคำขอเดิมเมื่อกดซ้ำ/ตอบกลับขาด บันทึกผลกับ audit ใน transaction เดียว และตรวจสิทธิ์ปัจจุบันอีกครั้งเมื่อขอผลเดิม สถานะ/งานถัดไปที่เปลี่ยนระหว่างเปิดฟอร์มถูกปฏิเสธแทนการทับข้อมูลใหม่

คำขอค้างเก็บเฉพาะใน sessionStorage ของบัญชีและแท็บนั้น ไม่เก็บ token หรือ snapshot; กรณีสร้างลูกค้าพร้อมจองมีข้อมูลชื่อ/เบอร์ในคำขอชั่วคราว และล้างเมื่อยืนยันผลแล้ว ถ้าพื้นที่เก็บเสียหรือผลยังไม่แน่ชัด จะล็อกคำสั่งใหม่ ไม่ล้างคำขอทิ้งเอง การโหลดประวัติล้มเหลวหลังบันทึกสำเร็จไม่ส่งคำสั่งจองซ้ำ

SQL18 มี trigger ป้องกัน direct legacy writer แก้/ลบ sale ที่เชื่อม V2 โดยใช้สิทธิ์เขียนภายใน transaction ไม่ใช่ตัวแปรที่ caller ตั้งเองได้ ประวัติ cancelled ห้ามแก้กลับเป็น booked

## ยังไม่ใช่การเปิดระบบจริง

ร่าง `sql/sales/18_booking_history_draft.sql` มีตัวหยุดรันทันทีและ ROLLBACK **ผู้ใช้ยังไม่ต้องนำไปรันบน Supabase**

สวิตช์ใหม่เริ่มปิด: ฝั่งแอป `SALES_CRM_BOOKING_ENABLED` ต้องใช้ร่วมกับ V2/Lead Work/Lifecycle; ฝั่งฐาน `booking_enabled` และ `booking_cutover_reviewed` ต้องใช้ร่วมกับ central/lead_work/lifecycle เช่นกัน ไม่มีการแก้ env หรือเปิดสวิตช์ในรอบนี้

ยังต้องทำก่อนเปิดใช้แทนระบบเดิม:

1. เปลี่ยนตัวอ่านหน้าลูกค้าจองในโครงการจาก legacy lead_id ไปอ่าน customer→interest→sale ทุกรอบ (sale ใหม่ไม่สร้าง legacy Lead และจึงยังไม่แสดงในตัวอ่านเดิม)
2. เปลี่ยนทางเข้าและถอดแท็บ Lead ในโครงการ พร้อมยุติ direct writers เดิมทั้งหมดที่เกี่ยวข้อง; ไม่ให้ V2 กับ legacy เขียนแข่งกัน
3. ตรวจ RLS/trigger/ข้อบังคับ schema จริงและ backfill ข้อมูลเก่าที่อนุมัติ โดยรักษา 895 identity และค่า “ไม่ทราบ”; ตัวอ่าน/คำสั่งใหม่หยุดเมื่อยังมี legacy sale ที่ไม่ได้เชื่อมของลูกค้านั้น
4. ทดสอบ staging ครบเส้นทาง แล้วจัด migration ที่ผ่าน review ให้ผู้ใช้รันเอง ก่อนอนุมัติเปิดสวิตช์/Deploy แยกกัน

การทดสอบใช้ข้อมูลสมมติเท่านั้น ฐานแยกไม่จำลอง legacy trigger/RLS ทุกตัว จึงไม่ถือว่าผ่าน production cutover ส่วนงานแจ้งเตือนที่พักไว้ยังไม่เปิดใช้งานจากรอบนี้
