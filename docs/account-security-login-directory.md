# รายชื่อก่อนล็อกอิน — ขั้น 2a (ในเครื่อง ยังไม่เปิดระบบจริง)

วันที่ 25 กันยายน 2569 ต่อจาก [การป้องกันคำสั่งจัดการบัญชี ขั้น 1](./account-security-phase-1.md)

อัปเดต 28 กันยายน: client `f404377` เผยแพร่แล้วและผู้ใช้ตรวจรับ Admin/รายชื่อครบแล้ว; เตรียม SQL candidate แยกพร้อมทดสอบ แต่ยังไม่ติดตั้ง grants จริง ดู [สถานะ cutover ล่าสุด](./account-login-directory-cutover.md) ข้อความ “ยังไม่ deploy” ด้านล่างเป็นประวัติขั้นเตรียมเดิม

อัปเดตถัดมาในวันเดียวกัน: ผู้ใช้ยืนยันบัญชีพนักงานใช้งานปกติและอนุมัติ SQL เฉพาะ directory แล้ว ติดตั้ง remote `20260928082516` สำเร็จ ตรวจ REST จริงอ่านชื่อได้ 18 รายการและขอข้อมูลภายในถูกปฏิเสธ รายละเอียด/ขอบเขตตรวจในรายงาน cutover ข้างต้น ไม่ใช่การเปิดระบบ trusted-role ทุกฝ่าย

## ผลที่เตรียมไว้

- คง **เลือกรายชื่อ → PIN 4 หลัก → เข้าสู่ระบบ** ไม่เปลี่ยนรหัสหรือวิธียืนยันกับ Supabase Auth
- หน้าล็อกอินใช้ `LoginScreen` แยกจากรายชื่อทีมงาน/หน้าจัดการบัญชี ขอเฉพาะ `username` และเรียงตามชื่อ ไม่ขอ id, role, วันที่สร้าง หรือเวลาออนไลน์
- ใช้ตารางผู้ใช้เดิมเป็นแหล่งข้อมูลเดียว ไม่คัดลอกชื่อไปอีกตาราง ไม่ต้องมี trigger หรืองานตั้งเวลาปรับรายชื่อ
- รายชื่อพร้อมบทบาทใน `useBuildTrackData` โหลดหลังมีผู้ใช้ล็อกอินเท่านั้น เลือกคอลัมน์ภายในอย่างชัดเจน และละทิ้งผลคำขอเก่าที่มาหลัง logout
- ช่วงโหลด/ผิดพลาด/ไม่มีชื่อ/ชื่อที่เลือกไม่อยู่ในรายการ/กำลังล็อกอิน จะไม่ส่งคำขอเข้าระบบทั้งปุ่มและ Enter
- มีข้อความกำลังโหลด, รายชื่อว่าง, ปุ่มลองใหม่ และข้อความผิดพลาดทั่วไป ไม่แสดงรายละเอียดฐานข้อมูล
- อ่านเป็นหน้าโดยนับจำนวนจริง ไม่ตัดรายชื่อเงียบ ๆ ตามเพดานแถว API; หากจำนวนเปลี่ยนระหว่างอ่าน ข้อมูลซ้ำ/ผิดรูปแบบ หรือเกินเพดาน 10,000 ชื่อ ให้ลองใหม่/ติดต่อ Admin ไม่ถอยไปอ่าน `users.*`

การเลือกรายชื่อไม่ให้สิทธิ์ใด ๆ รายชื่อเหล่านี้ตั้งใจเป็นข้อมูลสาธารณะตามที่ผู้ใช้เลือก: ใครเปิดหน้าล็อกอินหรือเรียกช่องอ่านชื่อโดยตรงก็เห็นชื่อได้

## การจำกัดสิทธิ์ฐานข้อมูลที่ยังเป็นร่าง

`sql/security/login_directory_draft.sql` เป็น DESIGN ONLY มีตัวหยุดและ ROLLBACK ไม่ใช่ migration พร้อมใช้ ห้ามนำไปรัน/ถอดตัวหยุดเพื่อใช้งานจริง

ร่างนี้ทำหลังขั้น 1 โดยถอนสิทธิ์ SELECT ของ `PUBLIC`/`anon` ทั้งระดับตารางและคอลัมน์ แล้วให้ `anon` อ่านได้เฉพาะ `username`
มีการตรวจสิทธิ์ที่สืบทอดมา และใช้ RLS ร่วมด้วย ไม่ถือว่าการซ่อนคอลัมน์ในหน้าจอเป็นการรักษาสิทธิ์เพียงพอ
ไม่ได้เพิ่ม SECURITY DEFINER, view ที่ข้าม RLS, ตารางรายชื่อซ้ำ หรือแถวข้อมูลจริง

ผู้ล็อกอินยังอ่านรายชื่อภายในและบทบาทเพื่อใช้งานเดิมได้ตามสิทธิ์เดิมในรอบนี้ นี่ไม่ใช่การปรับสิทธิ์ทุกตารางหรือการแก้แหล่งบทบาทที่เชื่อถือได้ครบแล้ว
ต้องตรวจเส้นทางอื่นที่อาจเปิดเผยข้อมูลผ่าน view/RPC ก่อนรับรองความเป็นส่วนตัวทั้งระบบ

## ลำดับนำไปใช้ในอนาคต

1. ตรวจและรับรอง Admin/ทางกู้คืน รวมข้อค้างขั้น 1 ก่อนจัด migration จริง
2. ตรวจ Supabase แยกจริงด้วยบัญชีสมมติ รวม Data API exact count, pagination, Auth login และ session refresh
3. เปิด frontend ที่ขอเฉพาะชื่อก่อน แล้วค่อยจำกัดสิทธิ์ฐานข้อมูลในช่วงที่อนุมัติ; frontend ใหม่ยังอ่านฐานเดิมได้โดยไม่ต้องมี RPC ใหม่
4. หลังปิดสิทธิ์แล้ว frontend เก่าที่อ่าน `users.*` หรือเรียงตาม role จะใช้ไม่ได้ ห้าม rollback ไปใช้ชุดเก่าโดยคืนสิทธิ์อ่านทั้งหมดแก่ anon

**ยังไม่ได้ deploy/เปลี่ยน grants/policies ใน Supabase จริง** และไม่มีการอ่านรายชื่อจริงหรือข้อมูลลูกค้าเพื่อทดสอบรอบนี้
การแก้ frontend ในเครื่องอย่างเดียวไม่ได้ปิดการเรียกข้อมูลผ่าน API ของระบบจริง

## ขั้นถัดไป

เตรียม [โหมดตรวจบทบาทและ session ขั้น 2b](./account-security-trusted-session.md) ในเครื่องแล้ว ครอบคลุมทุกฝ่ายพร้อม self-only last-seen แต่สวิตช์ยังปิด และยังไม่มีชุดรับรองบัญชีจริง
ขั้นถัดไปเป็นขั้นตอนรับรอง/กู้สิทธิ์และตรวจเส้นทางสิทธิ์ทุกโมดูลก่อนจัด migration จริง ไม่กำหนด Admin จากป้ายบทบาทเดิมอัตโนมัติ

อ้างอิงแนวทางที่ใช้: [Supabase Column Level Security](https://supabase.com/docs/guides/database/postgres/column-level-security) ระบุว่า RLS จำกัดแถว ไม่ได้จำกัดคอลัมน์ และการถอนสิทธิ์คอลัมน์อย่างเดียวไม่หักล้างสิทธิ์อ่านทั้งตาราง
