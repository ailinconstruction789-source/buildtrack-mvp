## ยังจับคู่รหัสขายเดิมอัตโนมัติไม่ได้

- ทั้ง 289 รายการไม่มีวันจองที่อ่านจาก `leads.booking_date`; วันสร้างแถวไม่ใช่วันจอง ห้ามใช้แทน
- ยกเลิกเดิม 77 รายการไม่มี `sales.plot_id` จึงเทียบกับประวัติยกเลิกในชีตจากแปลงไม่ได้ ชุดใหม่มีประวัติยกเลิกไม่ทราบแปลงอีก 1 แถว (171) ตามที่พักไว้
- ไม่ได้อ่านชื่อ/เบอร์จากฐานจริง และไม่ถือว่าชื่อ แปลง หรือวันที่คล้ายกันพิสูจน์คนเดียวกัน ไม่คืน sale ID สำหรับนำกลับมาใช้
- เก็บหลักฐานชุดเดิมและชุดใหม่แยกกันพร้อม provenance แล้วทำแผนสลับชุดอ่าน แทนการจับคู่ด้วยชื่อเล่นหรือการลบข้อมูลเก่าทันที

## ผลกระทบที่ตรวจพบ

ฐานจริงมี trigger `sync_plot_customer_status()` หลัง insert/update/delete sales: เปลี่ยน `plots.has_customer` และตั้ง `sale_status=transferred` เมื่อพบยอดโอน แต่ไม่ล้างค่า transferred เดิมเมื่อไม่พบโอน การนำเข้าโดยตรงจึงอาจทำให้แปลงค้างสถานะหรือกระทบหน้าหน้างาน

FK ของ `sales.lead_id` และ `customer_voices.lead_id` เป็น ON DELETE CASCADE; `house_visit_checklists.lead_id` เป็น SET NULL ปัจจุบัน Voices 0 และ checklist ที่ผูก Lead 0 แต่ต้องตรวจใหม่ตอนสลับจริง ไม่มี FK ขาเข้า public.sales ใน metadata ที่อ่าน ไม่ได้แปลว่าไม่มีการอ้างอิงในแอป/JSON/บริการอื่น

โค้ดที่อ่านยืนยันว่า flags เป็นข้อมูลร่วม: `HouseDetailView` ใช้ has_customer ในการอนุญาตโอน และ sale_status ในการเริ่ม/พักงาน; `DailyActivityHub`, `OwnerAnalyticsDashboard`, `app/page.tsx` ใช้ sale_status/has_customer ในงานหน้างานและยอดสรุป ห้ามทับแถว plots ทั้งแถวเพื่อเปลี่ยนข้อมูลฝ่ายขาย

## สิ่งที่เตรียมเพิ่มและผลทดสอบ

- ตัวเปรียบเทียบ local แบบอ่านอย่างเดียว และ option `--booking-inventory` ในตัวตรวจชีต ไม่มี network client หรือ database writer
- ตรวจ hash แผนเดิม, โครงการ/แปลง, สถานะที่รู้จัก, วันที่จริง, รายการซ้ำ; ไม่จับคู่ null date/null plot และไม่ลด Contracted เป็น Booked โดยเงียบ
- รายงาน JSON คู่กับเอกสารนี้เก็บเฉพาะจำนวน แถวต้นทาง แปลง สถานะ hash และข้อจำกัด ไม่มีชื่อ เบอร์ รายได้ หรือ raw spreadsheet
- Vitest ส่วนเกี่ยวข้อง **129/129 ผ่านใน 4 ไฟล์** รวม 15 กรณีของตัวเทียบใหม่ ไม่ใช่ full build/E2E หรือการทดสอบนำเข้าจริง

แนวทาง Supabase/Postgres ใช้ตรวจ FK/trigger ก่อนวางแผนแทนข้อมูล ตาม [Cascade Deletes](https://supabase.com/docs/guides/database/postgres/cascade-deletes) ส่วนการตรวจ workbook ใช้แนวทางอ่านอย่างเดียว เก็บข้อมูลส่วนบุคคลไว้ในหน่วยความจำ ไม่แก้ Google Sheet หรือไฟล์ต้นฉบับ

## ขั้นต่อไป

อัปเดต: ทำ sealed booking preparation ในเครื่องต่อแล้ว ตาม `sales-external-booking-bridge.md` เก็บประวัติเดิมและ candidate ชุดใหม่แยกกัน ยังไม่สลับ public.sales หรือแปลงจริง

เตรียม booking bridge/cutover ในเครื่องให้เก็บประวัติเดิมแยกจากชุดใหม่ ไม่สร้าง active booking ซ้ำแปลง ไม่แตะความคืบหน้า/ส่งมอบ/เวลาเดิมของฝ่ายอื่น และทดสอบยอด 304 ประวัติ/220 แปลงที่มีการขาย โดยยังคง 6 source holds และ 1 booking unknown-plot hold

ก่อนนำเข้าจริงยังต้องตรวจชีตล่าสุด, binding บัญชี, backup/rollback, dependency และบัญชีแปลงที่อนุมัติ ปรับ guards ของรายงาน/lifecycle ให้รองรับ external history และขออนุมัติชุดสลับจริงแยก ไม่ใช่เปิด flag จากผล audit นี้
