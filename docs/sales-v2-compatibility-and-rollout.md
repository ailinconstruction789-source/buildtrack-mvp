# ฝ่ายขาย V2: ผลตรวจความเข้ากันได้และขั้นตอนถัดไป

วันที่ตรวจ: 15 กันยายน 2569

## ข้อสรุปสำคัญ

มีจุดซ้ำและขัดแย้งจริงในโค้ด/SQL ที่อยู่ในเครื่อง จึงยังห้ามนำ `sales_workflow_v2_draft.sql` ไปรันเพื่อติดตั้ง
ไฟล์นั้นเป็นแบบข้อมูล มีตัวหยุดการรันและ ROLLBACK โดยตั้งใจ ไม่ใช่ migration รุ่นใช้งานจริง

ได้รับอนุญาตให้แก้โค้ดในเครื่อง ผู้ใช้จะเป็นผู้รัน SQL บน Supabase เอง ผู้ช่วยไม่ติดต่อฐานจริง; รอบ 17 กันยายนเพิ่มเติมเฉพาะการรัน SQL/RPC ด้วยข้อมูลสมมติใน PostgreSQL แยกในเครื่องตามรายละเอียดด้านล่าง ไม่ใช่การรันบน Supabase
ผลตรวจจาก repository เพียงอย่างเดียวไม่ยืนยัน migration ที่ติดตั้ง แต่ได้รับรายงาน 01–03 ที่ผู้ใช้รันเองแล้ว พร้อมคำยืนยันการเก็บประวัติ 895 รายการ ตามหัวข้อถัดไป

## อัปเดตล่าสุด: durable dispatcher 18 กันยายน 2569

เพิ่ม [SQL14จองคำขอถาวรก่อนประมวลผล](D:/buildtrack/buildtrack-mvp-main/docs/sales-v2-durable-dispatcher.md) แบบสองtransaction พร้อมattempt fencing/budget/backoffและอ่านสถานะกู้ผล ไม่เปลี่ยนSQL09/13หรือกติกาธุรกิจ ยังไม่ผูกNOLOGINroleกับCronจริง ไม่ตั้งjob/env ไม่Deploy ไม่เปลี่ยนSupabase ผู้ใช้ยังไม่ต้องรันSQL

ขั้นถัดไปตรวจรูปแบบติดตั้ง/สิทธิ์/launcher binding/timeout ความจุและmonitoringในสภาพแวดล้อมที่อนุญาตก่อนจัดmigrationและลงทะเบียนjobแบบปิด SQL12คงautomationReady=falseพร้อมเหตุผลCRON_BINDING_NOT_VALIDATED ไม่มีผลทดสอบใดในเครื่องเป็นการอนุมัติเปิดproduction

### รอบก่อนหน้า: แกนร่วมและ system worker 18 กันยายน 2569

เพิ่ม [system worker13 และแยกแกนประมวลผลร่วมใน09](D:/buildtrack/buildtrack-mvp-main/docs/sales-v2-system-worker.md) แบบร่างในเครื่อง รักษา contract Admin เดิม แยกสิทธิ์/ใบรับ/auditระบบ ไม่สวม Admin ใช้ cursor/global lock เดิมพร้อม9สวิตช์ที่เริ่มปิด และทดสอบหลาย session/rollback/กู้หลังตอบกลับขาดแล้ว ไม่มี Cron หรือ dispatcher จริง ไม่เปลี่ยน base/04–08/10–11, UI/API, env หรือข้อมูลจริง

ในขณะจบรอบworker13ยังต้องทำdurable dispatcher ซึ่งเตรียมเพิ่มแล้วในรอบ14ข้างต้น ส่วนการตรวจผู้เรียก/ความจุในstagingและการอนุมัติติดตั้งยังไม่เสร็จ รายงานความเข้ากันได้ทั้งหมดด้านล่างยังไม่ใช่การอนุมัติเปิดระบบ

### รอบก่อนหน้า: เตรียม Supabase Cron 18 กันยายน 2569

ผู้ใช้ยืนยัน Vercel Hobby และ Supabase Pro เพิ่ม [SQL12 preflight และแผนเชื่อม Cron](D:/buildtrack/buildtrack-mvp-main/docs/sales-v2-supabase-cron-preparation.md) แบบ operator-only/read-only พร้อมตรวจชื่อซ้ำ/สิทธิ์มองเห็นและจำนวน candidate แบบมีเพดาน ไม่ใช่ scheduler ที่ติดตั้งได้ ยังไม่มี worker ระบบ/การลงทะเบียน job; automationReady=false เสมอจนกว่า shared core และ system provenance จะตรวจรับ ไม่ใช้บัญชี Admin/service role เป็นทางลัด ไม่เปลี่ยน base/04–11 หรือข้อมูลจริง

### รอบประมวลผลจำกัดขอบเขต 17 กันยายน 2569

เตรียม [คำสั่งหนึ่งรอบไม่เกิน 10 งาน](D:/buildtrack/buildtrack-mvp-main/docs/sales-v2-bounded-cycles.md) พร้อมใบรับรอบ/ตำแหน่งอ่านส่วนกลางและสวิตช์ใหม่ที่เริ่มปิด ใช้ตัวประมวลผล SQL09 เดิม ร่าง SQL11 ยังไม่ใช่ migration และไม่แก้ base/04–10 ไม่ตั้ง cron/worker ไม่เปลี่ยน env/Supabase จริง ขั้นต่อไปต้องวัดความจุและออกแบบตัวเรียกที่เก็บรหัสรอบอย่างทนทาน ก่อนกำหนดความถี่และซ้อม staging ไม่ใช่เปิดระบบทันที

### หลักฐานรอบก่อนหน้า: ฐานแยกและหน้า Admin

รอบถัดจากฐานแยก: เตรียม [หน้า Admin ตรวจใบรับ/ยืนยันประมวลผล](D:/buildtrack/buildtrack-mvp-main/docs/sales-v2-admin-processing.md) และ API อ่านใบรับเฉพาะบัญชี พร้อม SQL10 แบบอ่านอย่างเดียวแล้ว ยังปิดฟีเจอร์ ไม่แก้ env/SQL09 หรือ Supabase จริง ไม่เพิ่มระบบประมวลผลอัตโนมัติ

- PostgreSQL 17.11 แบบพกพาบน loopback กับฐาน/user/password/port ใหม่ต่อรอบ ไม่ติดตั้งบริการ Windows ไม่อ่าน env/ข้อมูลจริง และหยุดฐานเมื่อจบ
- SQL base + 04–09 ผ่านการสร้างบนฐานสมมติ; 91 assertions ด้านคำสั่ง/สิทธิ์/ธุรกรรม, 80 กรณี clock และ 9 กลุ่มหลาย session/29 assertions ผ่าน SQL ร่างทั้ง 7 ไม่เปลี่ยน และ guard เดิมยังอยู่
- ตัวรันปิดช่อง conninfo/psql metacommands, ตรวจ data_directory ที่สร้างเอง, ไม่รับ database URL และมี cleanup เมื่อจบ/รับ graceful signal พร้อม self-test
- ชุด Vitest รวมฉบับสุดท้ายผ่าน 3,249 ข้อใน 64 ไฟล์ รวม 72 ข้อของตัวป้องกันฐานทดสอบ; TypeScript noEmit และ ESLint ของเครื่องมือใหม่ผ่าน ไม่แก้ production runtime/SQL ร่าง/ข้อมูลเก่าหรือไฟล์ Master
- นี่เป็นหลักฐาน native PostgreSQL เพิ่มจาก unit/mock/static เดิม ไม่ใช่การรับรอง Supabase Auth/PostgREST, legacy policies/triggers, migration นำเข้า หรือทุกกรณี concurrency
- ยังไม่มี SQL ติดตั้ง ไม่เปิดฟีเจอร์/ประมวลผลจริง; เตรียมหน้าตรวจใบรับและยืนยันสำหรับ Admin ต่อจากรอบนี้แล้ว ขั้นถัดไปออกแบบรันตามรอบที่จำกัดขอบเขต
- คำสั่งทดสอบซ้ำและขอบเขตที่ยังค้างอยู่ใน [รายงานฐานทดสอบแยก](D:/buildtrack/buildtrack-mvp-main/docs/sales-v2-isolated-database-tests.md) หัวข้อเก่าด้านล่างเป็นบันทึกสถานะแต่ละรอบ ไม่ใช่การบอกว่าขั้นล่าสุดยังไม่เคยทดสอบฐานแยก

### เรื่องสิทธิ์ที่ต้องจัดการก่อนเปิดใช้

RLS เปิดอยู่ทั้ง 7 ตารางที่ตรวจในขั้น 01 แต่ `plots` และ `projects` มี policy แบบ PERMISSIVE `ALL TO public USING true WITH CHECK true` พร้อม grants ให้ `anon`/`authenticated` เขียนได้; ขั้น 03 พบการเปิดสิทธิ์กว้างของ `public.users` ด้วย
การมี policy แคบอีกอันไม่หักล้าง policy permissive ที่เปิดกว้าง จึงต้องทบทวนทั้ง grants และ policies
รายงานนี้เป็นหลักฐานการตั้งค่าสิทธิ์ ไม่ใช่การทดสอบเข้าถึงข้อมูลโดยบุคคลภายนอกหรือหลักฐานว่ามีข้อมูลรั่วแล้ว

`leads`/`sales` เดิมตรวจบทบาทจาก user_metadata และไม่ตรวจเจ้าของ ส่วน Customer Voices/Checklist อนุญาต authenticated กว้าง
จึงยังรับรองสิทธิ์ “Sales เจ้าของ + Admin แก้ได้ / Owner อ่านอย่างเดียว” สำหรับระบบเดิมไม่ได้
ต้องตรวจสิทธิ์ที่ฝ่ายก่อสร้าง/ฝ่ายอื่นใช้อยู่ก่อนทำ migration สิทธิ์ ห้ามลบ policy รวมแบบเดา และรอบนี้ยังไม่ได้เปลี่ยน policy/grant จริง

### หน้า Lead ส่วนกลางที่เตรียมเพิ่มหลังได้รับรายงาน

- เส้นทาง `/sales-crm` พร้อมทางเข้าเมนูฝ่ายขาย “Lead ส่วนกลาง (เตรียมเปิดใช้)” ใน Sidebar
- ฟอร์มชื่อ–เบอร์, ไม่บังคับโครงการ, เพิ่มความสนใจหลายโครงการและเลือกแปลงว่างแบบค้นหาได้; การเล็งไม่จอง/เปิดงานโครงการ
- Sales ผู้สร้างเป็นผู้ดูแลอัตโนมัติ; Admin ต้องเลือก Sales ที่ใช้งานอยู่; Owner อ่านได้ ไม่มีปุ่มสร้างที่ใช้งานได้
- รายการรอเข้าโครงการ/ทั้งหมด แสดงเจ้าของกลางและเจ้าของรายโครงการ แบ่งหน้าละ 50 พร้อมค้นหาเฉพาะหน้า; เข้า A แล้วความสนใจ B ยังแสดงส่วนกลาง
- API `/api/sales-crm/central` ตรวจ session ที่ยืนยันแล้ว, trusted-role RPC, รุ่น contract, ขนาดข้อมูลและสิทธิ์ ไม่เชื่อ role/owner จากฟอร์ม
- การสร้างใช้รหัสคำขอเฉพาะ; ถ้าไม่ทราบผลบันทึกจะพักฟอร์มและลองด้วยรหัส/ข้อมูลเดิม ไม่สร้างคำขอใหม่โดยอัตโนมัติ
- เบอร์ซ้ำให้ Admin ตรวจ ไม่รวมคน/เปลี่ยนเจ้าของอัตโนมัติ; การอนุมัติกรณีคนละคนใช้เบอร์ร่วมกันยังต้องพัฒนา
- รองรับเบอร์ NULL สำหรับข้อมูลเก่าบนหน้า/API ส่วนกลางแล้ว แสดง “ไม่ทราบ (ข้อมูลเก่า)” และค้นหาโดยไม่แปลง null เป็นข้อความ; Lead ใหม่ยังต้องมีชื่อ–เบอร์และส่ง flag นำเข้าผ่านฟอร์มสร้างทั่วไปไม่ได้
- ร่าง SQL เตรียม RPC snapshot/create พร้อม transaction สำหรับ customer/interests/audit/SLA และ idempotency ไม่มีการ dual-write ตารางเดิม

โค้ดนี้ยังไม่เปิดใช้งานจริง: `SALES_CRM_V2_ENABLED` ต้องเป็น `true` จึงผ่าน route ของแอป และ RPC ต้องมี trusted roles, contract ตรง และ `crm_settings.central_intake_enabled=true` ด้วย
**DB setting เป็นตัวปิดการเขียน RPC จริง** รวมถึงผู้เรียก Supabase ตรง ส่วน server env ปิดเฉพาะเส้นทางแอป; เมื่อหยุดเขียน/rollback ต้องปิด DB setting ด้วย
ทั้งสองส่วนมีค่าเริ่มต้นปิด ไม่มีการแก้ env หรือตั้งค่าใน Supabase โดยผู้ช่วย ห้ามเปิดก่อนแก้สิทธิ์ ย้ายข้อมูล และเลิกช่องทางเขียนเดิมครบ

ข้อจำกัดระยะนี้: ยังไม่มีหน้าแก้ Lead/เปลี่ยนเจ้าของ/จัดการเบอร์ร่วม/activation Visit/QR/จอง/นำเข้า V2; ปุ่มเดิมยังไม่ถูกยกเลิก และไม่มี migration พร้อมใช้งาน
รหัสคำขอที่พักระหว่างเน็ตขัดข้องเก็บในหน่วยความจำฟอร์ม ไม่ใช่ offline queue; หากปิด/รีเฟรชหน้าในช่วงไม่ทราบผล ต้องให้ Admin ตรวจรายการก่อนสร้างใหม่
ยังไม่เปลี่ยนการนำทางมือถือใน app/page.tsx; หน้ากลางเปิดด้วย URL ตรงได้และรองรับจอเล็ก แต่ยังไม่ได้ทดสอบ UI จริงกับฐานข้อมูล

## สิ่งที่ทำแล้วในรอบนี้

### ใช้กับหน้าจอเดิมได้โดยไม่เพิ่มตาราง

- เพิ่ม searchable dropdown “แปลงที่เล็งไว้ (ถ้ามี)” ร่วมกันในฟอร์มเพิ่ม Lead และเช็กอินของ LeadTracker
- ดึงแปลงตามโครงการที่เลือก ตรวจทั้ง `plots.has_customer` / `sale_status` และรายการ `sales` ของแปลง ไม่อาศัย Lead ที่แสดงบนหน้าจอเท่านั้น
- รองรับรหัสแปลงข้อความเดิม ไม่มีการบังคับแปลงเป็น UUID; รายการจองถูกปฏิเสธสินเชื่อยังถือว่าครองแปลง
- โหลดข้อมูลเป็นหน้า/ชุด ไม่สรุปว่าแปลงว่างจากข้อมูลหน้าแรกหรือเมื่ออ่านรายการจองผิดพลาด
- เลือกด้วยรหัสแปลง เก็บชื่อประกอบ ตรวจซ้ำก่อนบันทึก และไม่เขียน `plots` / `sales` จากการเลือกความสนใจ
- บังคับชื่อและเบอร์ ผู้บันทึกเป็นชื่อ Sales ผู้ดูแลในฟิลด์เดิม และไม่บันทึก “ติดต่อสำเร็จ” อัตโนมัติตอนสร้าง Lead
- Lost ก่อนจองไม่ปล่อยแปลงที่เพียงเล็งไว้ และปฏิเสธการใช้ Lost กับ Lead ที่มีประวัติการจอง
- เช็กอินภายหลังไม่ลดสถานะของ Lead ที่มีรายการขายกลับเป็น Visit; ตรวจข้อผิดพลาดจากการบันทึกก่อนปิดฟอร์ม

นี่เป็นการปรับความเข้ากันได้บางส่วน **ยังไม่ใช่การเปิด workflow V2 ครบชุด**:

- หน้า Lead ส่วนกลางหลายโครงการ, เจ้าของด้วย auth ID, การย้ายข้อมูล, สิทธิ์ฝั่งเซิร์ฟเวอร์/RLS ใหม่ ยังไม่เปิด
- Visit/CV/Checklist เดิมยังไม่เปลี่ยนเป็นข้อมูลราย Visit; ห้ามตีความวันที่เช็กอินเดิมว่าเป็นหลักฐานส่ง Customer Voices ตามกฎใหม่
- การตรวจแปลงสำหรับ “ความสนใจ” ไม่ใช่ transaction ล็อกการจอง มีโอกาสถูกจองหลังเลือกได้ตามธรรมชาติ
- ระบบจอง/ยกเลิก/นำเข้า/รายงานเดิมที่ระบุความเสี่ยงด้านล่าง ยังต้องปรับพร้อม migration; อย่านำเข้าข้อมูลเก่ารอบใหญ่ระหว่างเตรียมย้ายระบบ
- การเช็กอินที่ไม่เลือกแปลงใหม่คงความสนใจเดิมและแจ้งไว้ในฟอร์ม ไม่สร้างการจองจากค่าความสนใจเดิม

### ฐานกฎใหม่สำหรับพัฒนาฝั่งเซิร์ฟเวอร์ต่อ

`lib/sales/workflow.ts` แยกลูกค้ากลาง / ความสนใจโครงการ / รายการขาย และมีฟังก์ชันทดสอบได้สำหรับสิทธิ์เจ้าของ, Admin เปลี่ยนเจ้าของ,
เหตุผลเปลี่ยนสถานะ, เงินสดข้ามกู้, ยื่นใหม่ไม่ทับประวัติ, ห้ามยกเลิกหลังโอน, Customer Voices ตรง Visit และ Checklist แยกจาก Visit

## ลำดับย้ายระบบหลังได้ผลตรวจ

อัปเดต 16 กันยายน 2569: ผนวก [JD/KPI Master เข้ากับแผน](D:/buildtrack/buildtrack-mvp-main/docs/sales-v2-kpi-integration.md) แล้ว ต้องออกแบบจุดเก็บ Qualified/Next Action/Attempt/Visit/SOP/เครดิตและเวลาให้ครบก่อน freeze schema ที่เกี่ยวข้อง
ผู้ใช้ยืนยันยอด KPI เป็นจองยืนยันหักยกเลิก ไม่บวกโอนซ้ำ และ Piwe ใช้บัญชี PIEW เดิม; ยังไม่เปลี่ยนบัญชีหรือเปิดคะแนนจริง
เพิ่มรายการแก้รายงานเดิม: เป้าคงที่ 2 หลัง, ใช้ Sale แรกต่อ Lead, เดาวันจองจาก created_at, นับ Visit จากจอง, อนุมานกู้จากโอน และเวลา Checklist A ที่บันทึกพร้อม C ขัดกับนิยามประเมินใหม่
แผน KPI แยกงาน CRM ที่เก็บหลักฐานได้ก่อน ออกจากสูตร/สิทธิ์ประเมินบุคลากรที่ยังต้องยืนยัน ไม่ใช้การอ่าน CRM ทุกโครงการเปิดข้อมูลลาหรือคะแนนพนักงานทั้งหมด

1. สรุปชนิด key / object รุ่นที่ติดตั้ง / policy / trigger ที่เป็นเจ้าของการเปลี่ยนสถานะจริง
2. ออกแบบ migration เพิ่มเติมให้ตรงรุ่นเดิม สำรองและทดลองบน staging ก่อน ไม่ drop/recreate ตารางที่มีข้อมูล
3. จับคู่ Sales กับ auth ID ด้วย Admin; ย้ายข้อมูลด้วย legacy ID พร้อมรายงานยอดก่อน–หลัง เก็บ unknown และ pending review ตามจริง
4. เปลี่ยนช่องทางเขียน CRM พร้อมกัน: LeadTracker, Kanban, Visit, Customer Voices, Checklist, Import; ห้าม dual-write หรือ fallback insert ตารางเก่าเมื่อ V2 ล้มเหลว
5. เปิดหน้ากลางและงานรายโครงการหลัง API/RLS ผ่านทดสอบ แล้วค่อยเปิด SLA/แจ้งเตือน/รายงานตามนิยามเดียวกัน
6. ตรวจจองชนกัน, ยกเลิกหนึ่งแปลง, reject→resubmit, Visit ซ้ำ, import ซ้ำ, Owner เขียนไม่ได้, เปลี่ยนรหัสแปลง และแผนคืนระบบโดยไม่ลบประวัติใหม่
7. ทดสอบ shadow KPI จากเหตุการณ์จริงตามโปรไฟล์และวันเริ่มวัด: ยอดจองสุทธิ, ไม่ซ้ำ Qualified/Visit/บ้าน, denominator ครบ, unknown/N/A, รอบเดือน/6 เดือนและข้อมูลบุคลากร ก่อนอนุมัติใช้ประเมินจริง
