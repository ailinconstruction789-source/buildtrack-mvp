# รอบประมวลผล First-contact SLA แบบจำกัดขอบเขต

สถานะ 17 กันยายน 2569: เตรียมคำสั่งหลังบ้านสำหรับหนึ่งรอบและชุดทดสอบในเครื่อง **ยังไม่ติดตั้ง scheduler/cron ไม่เพิ่มบัญชี worker ไม่เก็บ token ไม่เปลี่ยน env ไม่เปิดฟีเจอร์ ไม่เชื่อมต่อหรือรัน SQL บน Supabase** ร่าง SQL11 มีตัวหยุดก่อน DDL และ ROLLBACK ไม่ใช่ migration ติดตั้ง

อัปเดต18กันยายน2569: ยืนยัน Vercel Hobby/Supabase Pro เพิ่ม [preflight และแผนเชื่อม Supabase Cron](D:/buildtrack/buildtrack-mvp-main/docs/sales-v2-supabase-cron-preparation.md) แล้ว ต่อด้วย [system worker13 และแกนร่วม09](D:/buildtrack/buildtrack-mvp-main/docs/sales-v2-system-worker.md) แบบร่างที่ทดสอบในเครื่อง ใช้ cursor/global lock เดียวกัน แต่ใบรับและ actor ระบบแยกจาก Admin ไม่เปลี่ยน SQL11 หรือ endpoint Admin นี้ ยังไม่มี dispatcher/การลงทะเบียน job หรือการเปิดจริง

รอบถัดมา: เพิ่ม [durable dispatcher14](D:/buildtrack/buildtrack-mvp-main/docs/sales-v2-durable-dispatcher.md) ที่เก็บรหัสรอบก่อนเรียกworker13และกู้ด้วยรหัสเดิมแล้ว ไม่ใช้endpoint Adminนี้เป็นCron ยังไม่ตรวจbinding/ความจุ/monitoringในระบบเป้าหมาย ไม่ลงทะเบียนjobหรือเปิดจริง

## ขอบเขตที่เพิ่ม

- หนึ่งคำสั่งทำได้ **ไม่เกิน 10 งาน** ติดต่อครั้งแรกของ Lead ส่วนกลางที่เปิดอยู่ ไม่มี project interest/source activity; ไม่รวม Follow-up/Visit/จอง/ส่วนลด/KPI
- ใช้ตัวประมวลผล SQL09 เดิมทุกงาน จึงไม่สร้างสูตร SLA หรือระบบแจ้งเตือนอีกชุด
- ฐานข้อมูลเป็นผู้เลือกงานตาม `(created_at, id)` ไม่รับรายการลูกค้า/งาน/ผู้ดูแล/เวลา/กำหนด/จำนวนงานจากผู้เรียก
- จดตำแหน่งอ่านส่วนกลางเพียงหนึ่งชุด งานที่พักตรวจหลักฐานไม่กักงานถัดไปไว้หน้าแรกตลอดไป เมื่อถึงท้ายชุดจึงเริ่มใหม่ใน **คำสั่งรอบถัดไป** ไม่วนซ้ำภายในคำสั่งเดียว
- คำสั่งทั้งรอบอยู่ใน transaction เดียว: งานย่อย แจ้งเตือน audit ตำแหน่งอ่าน และใบรับรอบสำเร็จพร้อมกัน หากงานใดล้มเหลวหรือรอล็อกเกินกำหนด ย้อนกลับทั้งรอบ ไม่ข้ามงานที่ผิดพลาดเงียบ ๆ
- ไม่มีปุ่มส่งเป็นชุดในหน้า Admin เดิม ไม่มีการส่งจาก GET/หน้าจำลอง/inbox ไม่มี timer, auto retry หรือการเรียก API นี้จากหน้าจอในรอบนี้

ตัวเลข 10 เป็นเพดานทางเทคนิคแบบอนุรักษ์นิยมสำหรับตรวจรับ ไม่ใช่การเปลี่ยน SLA 24/48 ชั่วโมง และยังไม่ใช่ข้อสรุปด้านความถี่/ความจุของระบบจริง

## การเรียกและตรวจผล

Endpoint `/api/sales-crm/sla-cycles` มีเพียง:

| คำขอ | ผลและสิทธิ์ |
|---|---|
| GET ไม่มี query | อ่านบัญชี Admin/ความพร้อม/เพดาน 10 ไม่เลือกงานหรือขยับตำแหน่งอ่าน |
| GET พร้อม `requestId` หนึ่งค่า | อ่านใบรับรอบเดิมของ Admin บัญชีนั้น; `found=false` ไม่พิสูจน์ว่าครั้งก่อนล้มเหลว |
| POST JSON `{requestId}` | ประมวลผลหนึ่งรอบ ไม่อนุญาต field/query อื่น ขนาด HTTP ไม่เกิน 4 KB |

GET ต้องผ่านสวิตช์อ่าน 6 ตัวเดิม สิทธิ์ Admin จากฐานที่เชื่อถือได้ และ contract `first_contact_cycle_v1`; POST ต้องเพิ่มสวิตช์เดิมตัวที่ 7 และ `SALES_CRM_SLA_CYCLE_ENABLED`/`crm_settings.sla_cycle_enabled` ตัวที่ 8 ด้วย ค่า DB ใหม่เริ่ม `false` และไม่ได้ตั้งค่า env จริง

ปิดการเขียนตัวที่ 7/8 แล้วยังอ่านใบรับได้เมื่อสวิตช์อ่านและสิทธิ์พร้อม แต่ไม่ใช้ GET เพื่อ replay การเขียน สวิตช์ DB ป้องกันผู้เรียก RPC ตรง; ปิดเฉพาะ server env ไม่ได้ปิด RPC โดยตัวมันเอง

ผู้เรียกใช้ session ที่ `getUser` ตรวจแล้ว + `crm_v2_role` + capability ที่ตรงรุ่น ผ่าน public anon key เท่านั้น ไม่รับ secret/service-role key และไม่ใช้ role ที่ผู้เรียกอ้างเอง ข้อมูลตอบกลับคัดเฉพาะฟิลด์ที่อนุญาตทั้งใบรับรอบและงานย่อย พร้อม no-store/Vary Authorization

### รหัสคำขอและผลไม่แน่ชัด

1. ตัวเรียกในอนาคตต้องบันทึก **Admin + requestId รอบ** อย่างทนทานก่อนส่ง ไม่สร้างรหัสใหม่เพื่อหนีผลไม่แน่ชัด
2. รหัสเดียวในบัญชีเดียวคืนใบรับเดิม ไม่เลือกงานใหม่/สร้างรหัสลูกใหม่/ขยับตำแหน่งอ่านอีก งานย่อยใช้ UUID ที่ฐานสร้างและเก็บในใบรับรอบ
3. ถ้าการเชื่อมต่อขาด ให้ GET ใบรับเดิมก่อน ไม่พบใบรับหรือ GET ผิดพลาดยังต้องเก็บรหัสเดิมไว้
4. หากจะลอง POST อีกครั้ง ให้ใช้รหัสเดิมเท่านั้น ไม่มีการ retry อัตโนมัติในโมดูลนี้ คำตอบว่าครั้งล่าสุดไม่ได้ประมวลผลไม่พิสูจน์ว่าครั้งก่อนหน้าไม่สำเร็จ
5. ใบรับ `startedAt`/`finishedAt`/`receipts` เป็นผลในอดีต ไม่รับรองสถานะปัจจุบัน ไม่ให้เครดิต KPI และไม่หมายถึงติดต่อสำเร็จทุกคน

`processedCount` รวมงานที่ held/scheduled/closed ด้วย ไม่ใช่จำนวนแจ้งเตือนที่ส่ง; `sweepFinished` หมายถึงหมดรายการหลังตำแหน่งอ่าน ณ snapshot ที่เลือก ไม่ใช่ “ทุก Lead ทำงานครบ” หรือ “ไม่มีงานใหม่เข้าอีก” ใบรับของแต่ละงานยังใช้ `processedAt` ของตัวประมวลผลเดิม ไม่บังคับทุกงานให้ใช้เวลารอบเดียวกัน

ฐานมีใบรับเฉพาะรอบที่ commit แล้ว แต่ยังไม่มี durable dispatcher ฝั่งตัวตั้งเวลาที่บันทึก intent ก่อน POST จึง **ยังไม่พร้อมต่อ cron/เปิดอัตโนมัติ** การตั้งเวลา/วิธีเก็บ intent/ตัวตน worker ต้องออกแบบและตรวจรับต่างหาก ห้ามใช้ refresh token ของ Admin หรือ service role เป็นทางลัด

## การทำพร้อมกันและขอบเขตล็อก

- รอบต่างรหัสใช้ global advisory แบบลองล็อก ถ้ามีรอบอื่นทำอยู่คืน BUSY ไม่ต่อคิวมาประมวลผลชุดใหม่ให้เอง รอบรหัสเดียวอาจรอล็อกใบรับเดิมแล้ว timeout; ให้ตรวจผลด้วยรหัสเดิม
- ก่อนเรียกงานย่อย ล็อกลูกค้าทั้งชุดตามลำดับ ตรวจเจ้าของใหม่หลังได้ล็อก จากนั้นล็อกเวร/บทบาท/งานทั้งชุดตามลำดับ ก่อนให้ SQL09 ตรวจอีกครั้ง ป้องกันการสลับลำดับกับคำสั่งทีละงานและ lifecycle เดิม
- ถอนสิทธิ์ Admin ระหว่างรอล็อกต้องไม่ผ่านการตรวจรอบสุดท้าย แม้เป็นใบรับ replay หรือรอบที่ไม่มีงาน
- `lock_timeout=500ms` จำกัด **การรอล็อกแต่ละครั้ง** ไม่ใช่เพดานเวลารวมของรอบ มี partial index ช่วยเลือกงาน แต่ LIMIT ไม่รับประกันเวลารวม ต้องวัดโหลด/กำหนด statement timeout ที่ staging ก่อนเปิด
- ความเป็นธรรมของการไล่งานขึ้นกับรอบที่ commit ได้ หากมีงานผิดโครงสร้างหรือ error ถาวร รอบจะไม่ขยับ ต้องให้ Admin ตรวจหลักฐานและแก้ด้วย workflow ที่อนุมัติ ไม่ข้าม/ลบงาน/ล้าง cursor เพื่อหลบข้อผิดพลาด
- การเขียนผ่านสิทธิ์สูงที่ข้ามล็อกลูกค้า/ประวัติ immutable ยังอยู่นอกสัญญานี้ ต้องปิดช่องเดิมก่อน rollout ไม่อ้างว่าคลุม trigger/สิทธิ์ legacy ที่ยังไม่ได้ตรวจจริง

## สิ่งที่ไม่ซ้ำกับของเดิม

ใช้ `crm_sla_tasks`, `crm_notifications`, audit และ receipt รายงานย่อยของ SQL09 เดิม เพิ่มเฉพาะ cursor ส่วนกลางและใบรับรอบใน `sales_private` ไม่สร้าง Lead/งานขาย/แจ้งเตือนอีกชุด ไม่แก้ SQL base/04–10 หน้าจอ Admin เดิมยังยืนยันทีละงานเหมือนเดิม

## ก่อนเปิดอัตโนมัติจริง

1. ผู้ใช้ยืนยันว่าแอป Deploy บน **Vercel Hobby** และฐานเป็น **Supabase Pro** แล้ว เสนอให้ตัวตั้งเวลาอยู่ฝั่งฐานโดยแยก core/ตัวตนระบบ/ใบรับจาก Admin ก่อน ต้องตรวจรับรูปแบบตัวเรียกและตัวตนที่ได้รับสิทธิ์อย่างจำกัด ออกแบบ durable intent/การกู้คำขอ/การปิดระบบ ไม่ใช้ endpoint นี้เป็น unauthenticated cron webhook; เงื่อนไขโฮสต์สำหรับใช้งานธุรกิจยังต้องจัดการแยกกัน
2. วัดจำนวนงานเปิดและเวลาจริงต่อรอบก่อนกำหนดความถี่ ตัวอย่าง 895 งานต้องอย่างน้อย 90 คำสั่งต่อหนึ่ง sweep ที่เพดาน 10; รันเพียงครั้งละรอบทุก 5 นาทีอาจใช้ราว 7.5 ชั่วโมง จึงยังรับประกันเตือนล่วงหน้า 30 นาทีไม่ได้ (เป็นตัวอย่างความจุ ไม่อ้างว่าข้อมูลเก่าทั้ง 895 เป็นงาน SLA ที่ต้องส่ง)
3. กำหนดจำนวนรอบ/เวลาต่อ tick, backoff เมื่อ BUSY/timeout, การหยุดเมื่อผลไม่แน่ชัด, สัญญาณ backlog/poison batch และ retention ของใบรับโดยไม่ทำลาย audit
4. ซ้อม real HTTP/PostgREST/JWT/connection loss และ concurrency กับสิทธิ์/trigger/schema ที่เทียบ production ใน staging ที่ได้รับอนุญาต
5. ตรวจ migration/cutover/สำรอง/นำเข้า/KPI และ workflow ที่ยังขาดตาม [แผนรวม](D:/buildtrack/buildtrack-mvp-main/docs/sales-v2-compatibility-and-rollout.md) ก่อนอนุญาตเปิดจริง

### ข้อพิจารณาสำหรับ Vercel ที่ยืนยันแล้ว

ตรวจเอกสารทางการวันที่ 17 กันยายน 2569 โดยไม่ได้เข้าบัญชี Vercel หรือดูค่าลับของโครงการ:

- Vercel Cron เรียก **GET** ไปยัง production deployment จึงห้ามนำ path GET อ่านใบรับ/preview/inbox ของเราไปใช้เป็นตัวส่ง หากเลือก Vercel Cron ต้องออกแบบ trigger แยกที่มีการตรวจสิทธิ์และเก็บ intent ก่อนเรียกคำสั่ง ไม่เปลี่ยนความหมายของ GET อ่านเดิม. [Vercel Cron overview](https://vercel.com/docs/cron-jobs)
- Cron อาจส่งซ้ำ/พลาดรอบ/รันซ้อน และไม่ retry ให้อัตโนมัติเมื่อ function ล้มเหลว จึงต้องเก็บรหัสรอบที่กู้คืนได้ ไม่สร้าง UUID ใหม่ทุก invocation; `CRON_SECRET` ช่วยยืนยันผู้เรียก trigger แต่ไม่ใช่ Supabase JWT หรือสิทธิ์ Admin ของ SQL11. [Managing Cron Jobs](https://vercel.com/docs/cron-jobs/manage-cron-jobs)
- Hobby จำกัด Cron วันละครั้งและความแม่นยำระดับชั่วโมง ส่วน Pro/Enterprise รองรับความถี่ถึงนาที ต้องทราบแพ็กเกจจริงก่อนออกแบบเตือนล่วงหน้า 30 นาที ไม่สมมติว่ามี Pro ไม่สมัคร/อัปเกรดหรือเสนอ cron ทุกนาทีที่ deploy ไม่ผ่าน. [Cron usage and limits](https://vercel.com/docs/cron-jobs/usage-and-pricing)

ยังไม่ได้สร้าง/เปลี่ยน `vercel.json`, Cron configuration, secret, service account หรือ deployment ใด ๆ

ผลทดสอบรวมรอบนี้: Vitest **3,830 ข้อ / 74 ไฟล์ผ่าน**; TypeScript/ESLint ของส่วนที่แก้และ production build ด้วย Webpack ผ่าน; native SQL11 94 assertions และ concurrency/loopback TCP fault 5 กลุ่ม / 24 assertions ผ่าน ชุดเดิมยังผ่านทั้งหมด รายละเอียดขอบเขตหลักฐานแยกไว้ในรายงานฐาน ไม่ตีความเป็น real Supabase/PostgREST E2E
