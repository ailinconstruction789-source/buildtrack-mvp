# ขั้น 2: Admin ตรวจคิวแจ้งเตือน — 23 กันยายน 2569

เตรียมหน้าจอ/API และร่างอ่านข้อมูลในเครื่องเท่านั้น ไม่เชื่อม Supabase ไม่อ่านข้อมูลจริง ไม่แก้ไฟล์ env ไม่เปิดสวิตช์หรือ Cron และไม่ Deploy ผู้ใช้ยังไม่ต้องรัน SQL

นี่คือ **ส่วนอ่านสถานะและแนวทางตรวจ Review ของขั้น 2** ไม่ใช่ตัวแจ้งผู้ดูแลอัตโนมัติ ไม่ใช่เครื่องมือปลดคิว และยังไม่ปิดงานตรวจความเร็วครบเส้นทาง

## สิ่งที่ Admin จะเห็นเมื่อผ่านการตรวจรับและเปิดใช้

ทางเข้า Lead ส่วนกลาง → “ตรวจคิวแจ้งเตือน (Admin)” → `/sales-crm/queue-monitor` ซ่อนเมื่อฟอร์มรับ Lead เปิดอยู่ และไม่แสดงให้ Sales/Owner หน้าอ่านเมื่อเปิดหรือกดโหลดล่าสุดเท่านั้น ไม่มี timer หรือคำสั่งส่งงาน

- จำนวนชุดงานติดต่อครั้งแรกที่ยังเปิดในส่วนกลางตามเงื่อนไขคิวเดิม รวมงานรอตรวจ/ยังไม่ถึงเวลา ไม่ใช่จำนวนแจ้งเตือนค้างส่งหรือจำนวนลูกค้าที่ผิด SLA
- อ่านตามลำดับเดิมไม่เกิน 901 งาน ถ้าพบ 901 ให้แสดง “อย่างน้อย 901” และไม่รับรองว่าเป็นยอดครบ ถ้าน้อยกว่านั้นเป็นยอดครบ ณ snapshot ที่อ่าน
- จำนวนผลประเมินเดิมที่เป็น held และจำนวนที่ไม่มีผลเดิมที่อ่านได้ในชุดตัวอย่างเท่านั้น ผลนี้อาจเก่าหลังเปลี่ยนเวร/ผู้ดูแล/สถานะ จึงไม่คำนวณสิทธิ์ส่งใหม่จากตัวเลขนี้
- คำขอปัจจุบันของตัวจัดส่ง: รหัสคำขอ/ครั้งที่ลอง จำนวนครั้ง สถานะ เหตุผลปลอดภัย และนโยบายของคำขอเดิม ไม่เปิดเนื้อหา error ภายใน ข้อมูลรายได้ เบอร์ลูกค้า หรือ receipt ทั้งก้อน
- หากหนึ่งรอบยืนยันแล้ว แสดงจำนวนงานที่ตรวจ/รอตรวจ/ผลระบุแจ้ง เฉพาะรอบนั้น ไม่ใช่ยอดทั้งคิวหรือหลักฐานว่าผู้รับเห็นแล้ว
- สวิตช์ประมวลผลที่เก็บในฐานและตำแหน่งอ่านคิว ไม่ใช่หลักฐานว่า Cron หรือตัวประมวลผลกำลังทำงาน

## แปลสถานะโดยไม่สั่งแก้เอง

| สถานะ | ความหมายและสิ่งที่ต้องตรวจ |
|---|---|
| `reserved` | มีหลักฐานจองแล้ว อาจกำลังทำหรือผลตอบกลับขาด ไม่ใช่หลักฐานว่าล้มเหลว |
| `retry_wait` | เคยผิดพลาดชั่วคราวและระบบเก็บช่วงพักไว้ หน้านี้ไม่สั่งลองซ้ำ |
| `review` | ระบบอัตโนมัติหยุดรอตรวจ รักษารหัสเดิมและประวัติ ห้ามรีเซ็ตจำนวนครั้งหรือสร้างคำขอใหม่หนีขีดจำกัด |
| `completed` | ผลของหนึ่งรอบบันทึกพร้อมใบรับแล้ว อาจมีงาน held ในรอบนั้น และไม่หมายถึงงานทั้งหมดเสร็จ |

ผ่าน `nextAttemptAt` ไม่ได้ยืนยันว่าเริ่มใหม่ได้ เพราะยังขึ้นกับล็อก นโยบาย เพดาน และงานที่อาจค้างอยู่ โดยเฉพาะคำขอ burst ที่ completed ฟิลด์นี้ไม่ใช่เวลาปลุกรอบถัดไป การไม่พบใบรับหรืออ่านไม่ได้ก็ไม่ใช่หลักฐานว่าคำขอเดิมไม่เคยบันทึก

เมื่อ request ยังไม่ completed และอายุจากเวลาสร้างถึงเวลา snapshot ≥ 300 วินาที จะแสดงเหตุให้ตรวจสอบ **ไม่เรียกว่าแจ้งเตือนล่าช้า 5 นาที** ไม่ใช้เวลาจากเครื่องผู้ใช้หรือใช้ตัดคะแนน Sales

## สิทธิ์และขอบเขตการอ่าน

- หน้าและ GET `/api/sales-crm/queue-monitor` ต้องผ่านหกสวิตช์อ่านเดิม พร้อม `SALES_CRM_QUEUE_MONITOR_ENABLED=true` ซึ่งยังไม่ได้ตั้งจริง
- [SQL17](D:/buildtrack/buildtrack-mvp-main/sql/sales/17_queue_monitor_draft.sql) เพิ่ม `sla_queue_monitor_enabled DEFAULT false` และต้องผ่านหกสวิตช์อ่านในฐานเดิมด้วย ไม่บังคับให้เปิด processing/worker/dispatcher เพื่ออ่านหลักฐาน
- API ตรวจ bearer กับ Auth และบทบาทจาก `crm_v2_role` ไม่เชื่อ role จาก browser ส่วน RPC ตรวจ Admin ซ้ำ ไม่มี service-role key หรือสิทธิ์ worker ให้หน้าเว็บ
- มีเพียง capabilities และ snapshot แบบอ่าน ไม่มี POST หรือ RPC retry/reset/clear-review ไม่เปิดตาราง private โดยตรง ไม่เรียกตัวประมวลผลจากการเปิดหน้า
- RPC อ่าน snapshot เดียวด้วย `STABLE` และเวลาฝั่งฐาน เฉพาะ control/request/attempt/worker receipt ที่เกี่ยวข้องผ่าน key และ candidate prefix ไม่กวาดประวัติใบรับทั้งหมด ไม่ตั้งล็อกคิว
- LIMIT จำกัดจำนวนแถวที่อ่านมาสรุป ไม่ใช่ hard timeout หรือเพดานเวลาทำงาน ต้องตรวจต้นทุน query/แผนดัชนีและ timeout ของผู้เรียกใน staging ก่อนเปิดจริง
- ไม่รับตัวเลือกผู้ใช้ รหัสคำขอ นาฬิกา limit หรือคำสั่งจาก query ผลตอบกลับคัดเฉพาะฟิลด์ที่อนุญาตทั้ง API และ client
- เปลี่ยนบัญชี/ออกจากระบบ/ถอนสิทธิ์/เปลี่ยน API instance: ซ่อนข้อมูลเดิมและทิ้งผลตอบกลับเก่า ต้องตรวจบัญชีใหม่เมื่อไม่ยืนยันสิทธิ์ โหลดล้มเหลวไม่แสดงข้อมูลเก่าหรืออ้างว่าคิวว่าง

SQL17 ยังมีตัวหยุดก่อน DDL และ ROLLBACK ท้ายไฟล์ **ไม่ใช่ migration สำหรับติดตั้ง ห้ามถอดตัวหยุดแล้วนำไปรัน** ไม่มีการแก้ SQL09–16 หรือเปลี่ยนสูตร SLA ในรอบนี้

## แนวทางตรวจ Review โดยรักษาหลักฐาน

1. บันทึกเวลา snapshot, requestId, attemptId, นโยบาย สถานะ และเหตุผลที่แสดง ไม่บันทึก token/raw error หรือข้อมูลส่วนบุคคลเกินจำเป็น
2. แยก dispatcher review ออกจากงานลูกค้าที่ held: การจัดเวรให้ครบอาจแก้งานขาดเวรได้ แต่ไม่ใช่อำนาจปลด dispatcher review
3. ผู้ดำเนินการที่ได้รับอนุญาตตรวจการตั้งเวลา/ตัวเรียก สิทธิ์ timeout ล็อก และใบรับเดิมในสภาพแวดล้อมที่อนุญาต ไม่ใช้การเปิดหน้าจอเป็นหลักฐานว่าผู้เรียกทำงานอยู่
4. เตรียมวิธีแก้สาเหตุและแผนย้อนกลับ ขออนุมัติแยก ก่อนสร้างคำสั่งกู้ที่รักษาประวัติและป้องกันการทำซ้ำ ไม่มีปุ่มนี้ในรอบปัจจุบัน
5. หลังแก้ตามขั้นตอนที่อนุมัติ จึงตรวจคำขอเดิมและผลถึงผู้รับ ไม่ลบ ledger/reset control/เปลี่ยน UUID เพื่อให้หน้าจอดูปกติ

## สิ่งที่ยังวัดไม่ได้และงานที่เหลือ

`deliveryLatencySeconds` และ `sweepAgeSeconds` คืน null โดยตั้งใจ: cursor ไม่มีเวลาที่เริ่มกวาดชุด, processingReview คือการประเมินรายงานเดิม และ `notify_at` ไม่ใช่จุดเริ่มช่วงเตือน จึงห้ามแปลงฟิลด์เหล่านี้เป็นอายุ sweep หรือความหน่วงส่งถึงผู้ใช้ `created_at - available_at` ของแจ้งเตือนที่สร้างแล้วก็ไม่พิสูจน์เวลาหลัง commit/แสดงผล และไม่ครอบคลุมงานที่ยังไม่ถูกสร้างแจ้งเตือน

ขั้น 2 ยังต้องเตรียมหลักฐานวัดเวลารอ/อายุการกวาดครบชุดจริง และช่องทางแจ้ง Admin อัตโนมัติ/กระบวนการกู้ Review ที่ตรวจรับก่อนเปิดจริง หน้านี้เป็นส่วนอ่านสำหรับตรวจด้วยตนเอง ไม่ถือว่าขั้น 2 ทั้งหมดเสร็จหรือระบบมีการเฝ้าดูเบื้องหลังแล้ว

หลังจากนั้นคงขั้น 3 ตรวจสิทธิ์/ความเข้ากันได้ (รวมผิวอ่านใหม่ของ SQL17), ขั้น 4 ทดสอบ staging ที่ได้รับอนุญาตครบ DB→API→หน้าจอและเป้า 5 นาที, ขั้น 5 migration/rollback/ตัวตั้งเวลาแบบปิดและการอนุมัติเปิดจริง ผู้ใช้ยังเป็นผู้รัน SQL ตามข้อตกลงเดิม ปัญหา build ฟอนต์ Noto Sans Thai จากขั้นก่อนยังต้องตรวจแยก ไม่ได้แก้หรือรับรองว่าหายแล้วในรอบนี้

## ผลตรวจในเครื่อง

ก่อนเริ่ม ชุดรวม Vitest ผ่าน 4,234 ข้อ / 90 ไฟล์ ไม่มีการต่อฐานจริง ชุดตรวจใหม่ใช้ข้อมูลสมมติ

การทดสอบฐานแยกรอบแรก `run-NdevUD` หยุดเมื่อเครื่องมือคอมไพล์ตัวตรวจ TypeScript ใหม่ต้องการ library `ES2022` สำหรับ `Object.hasOwn` จึงเพิ่ม library ให้เฉพาะตัวคอมไพล์ทดสอบ ไม่แก้ config/dependency ของแอป รอบ `run-sRjSyz` หยุดที่ assertion เดิม `Recovery lookup writes nothing` ของ worker13 ก่อนสร้าง SQL17 เพิ่มเฉพาะรายละเอียดแยกจำนวน POST และ field comparison โดยคงเงื่อนไขเดิมไว้ ยังไม่ถือว่าระบุสาเหตุหรือแก้ปัญหานี้แล้ว ทั้งสองฐานหยุดยืนยันแล้ว (`stopped=true`)

รอบ `run-pwtMbk` ผ่านชุดเดิมรวม worker recovery และ burst16 แล้วหยุดที่ fixture ของ monitor ใช้ UUID ผู้ใช้ซ้ำกับ fixture dispatcher เดิม จึงเปลี่ยนเฉพาะ prefix ข้อมูลสมมติเป็น `bc170000` ไม่แก้ SQL17 หรือ constraint รอบตรวจเฉพาะ monitor `run-BB3Zzj` ผ่าน 41 assertions พร้อมธุรกรรมอ่านอย่างเดียวจริงและตรวจว่าผล SQL ผ่านตัวตรวจ TypeScript (`projectionParity=true`) ทั้งสองฐานหยุดแล้วเช่นกัน ผลตรวจเฉพาะส่วนนี้ไม่ใช่ผลทดสอบรวม

ตัวเลือก `npm run test:sales-db -- --queue-monitor-only` มีไว้ตรวจปัญหาเฉพาะชุด monitor: ยังคงสร้างฐานสมมติใหม่ ตรวจปลายทาง หยุดฐาน และตรวจ hash ร่างครบ แต่ข้ามชุดธุรกิจ/หลาย session เดิม รายงานระบุ `mode=queue-monitor-only` จึงห้ามใช้แทนการทดสอบรวมแบบไม่ใส่ตัวเลือก

**ผลฐานแยกแบบรวม:** [run-9WPaWP/report.json](D:/buildtrack/buildtrack-mvp-main/node_modules/.cache/buildtrack-sales-runtime/runs/run-9WPaWP/report.json) ผ่าน `mode=full`, `stopped=true` สร้างครบ 15 ร่าง (base/04–17) ชุดเดิมทั้งหมดรวม burst42/concurrency56 ผ่าน พร้อม monitor41 assertions, ธุรกรรม `READ ONLY` จริง และ SQL→TypeScript projection parity ไม่รัน paced895 ซ้ำ และไม่ใช้ผลนี้รับรองเวลา5นาทีจริง

เทียบ SHA-256 กับ `run-MoFYVc` แล้ว SQL base/04–16 ทั้ง14ไฟล์ไม่เปลี่ยน ตรวจฐาน5รอบที่สร้างในงานนี้หยุดทั้งหมด ไม่มี `postmaster.pid` และไม่พบ process postgres/initdb ค้าง เก็บรายงานและฐานที่หยุดไว้ใน cache ไม่ลบข้อมูลผู้ใช้

ชุด Vitest รวมหลังเพิ่มครั้งแรกผ่าน4,557/4,559ข้อ มี2กรณีไม่ผ่าน: static assertion ของ capacity harness ยังอ้างตัวเลือกเก่าที่ไม่มี `queueMonitorOnly` จึงปรับ assertion ให้ตรวจตัวกันโหมดใหม่ด้วย และกรณี restore pending ของหน้า `SlaProcessingView` เดิมตรวจปุ่มก่อนรายการแสดงครบ ทดสอบสองไฟล์แยกแล้วผ่าน50ข้อ โดยไม่แก้หน้า SLA เดิม/ชุดทดสอบหน้าเดิม/timeout ไม่ใช้ผลแยกแทนผลรวม

รอบรวมถัดมาผ่าน4,558/4,559ข้อ เหลือกรณี restore pending เดิมเพียงข้อเดียว ตรวจโค้ดพบว่า helper รอหัวข้อหน้าและปุ่มโหลดที่เปิดให้ใช้ได้ก่อน effect เริ่มอ่านรายการ จึงปรับเฉพาะกรณีทดสอบนี้ให้รอปุ่มงานจริงด้วย `findByRole` ทั้งก่อนและหลัง remount พร้อมตรวจว่ายัง disabled และคง assertion ห้าม lookup/process/new request อัตโนมัติทุกข้อ ไม่แก้ production component ไม่ขยาย timeout และไม่ลดเงื่อนไข ทดสอบหน้าเดิมแยกแล้วผ่าน46ข้อ
