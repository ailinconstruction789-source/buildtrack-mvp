# Admin จัดเวรฝ่ายขาย — เตรียมในโค้ด ยังไม่เปิดใช้

สถานะ 16 กันยายน 2569: ผู้ใช้ยืนยันว่าไม่มีระบบเวรเดิม และให้ Admin จัดเวรในแอป จึงต่อแหล่งข้อมูลเวรก่อนเชื่อมตัวส่งแจ้งเตือนจริง รอบนี้เพิ่มหน้า/API และ SQL ออกแบบเท่านั้น **ไม่รัน SQL/RPC ไม่เปิดสวิตช์ ไม่เปลี่ยนข้อมูล Supabase และไม่มี SQL ให้ผู้ใช้นำไปรัน**

## 1. สิ่งที่เตรียมแล้ว

- หน้า `/sales-crm/work-schedule` สำหรับ Admin พร้อมลิงก์จาก Lead ส่วนกลางเมื่อเปิดฟีเจอร์และตรวจบทบาทแล้ว ไม่เพิ่มสิทธิ์ให้ Owner/Sales และไม่แก้หน้าระบบเก่า
- ค้นหาและเลือก Sales ที่ active จากรายชื่อที่โหลด ไม่กรอกรหัสคนเอง ไม่เลือกคนให้โดยอัตโนมัติ จำกัดรายชื่อ 200 คนพร้อมข้อความเมื่อยังมีมากกว่า
- กรอกช่วงข้อมูลที่ตรวจครบ และช่วง `ทำงาน / พัก / ลาที่อนุมัติแล้ว` ตามเวลากรุงเทพฯ รองรับช่วงทำงานข้ามวันและหักพัก/ลาซ้อนกันโดยไม่หักซ้ำ
- บังคับเหตุผลและการยืนยันว่าข้อมูลครบ ตรวจทานทั้งชุดก่อนบันทึกอีกครั้ง ไม่อนุมานว่าช่องว่างคือวันหยุดเพียงเพราะยังไม่ได้กรอก
- ไม่มีเวลาทำงานเริ่มต้น ไม่มีวันหยุดประจำสัปดาห์ที่ระบบเดาให้ และไม่อนุมัติลา/บันทึกเข้างานหรือคิด Attendance จากหน้านี้

## 2. วิธีใช้ที่ออกแบบ

1. Admin เลือก Sales → โหลดตารางรุ่นปัจจุบันหรือแสดงว่ายังไม่มีตาราง
2. กำหนดช่วงข้อมูลเริ่ม–สิ้นสุด โดย **ไม่นับเวลาสิ้นสุด** เช่น 1 ต.ค. 00:00 ถึง 1 พ.ย. 00:00 ครอบคลุมเดือนตุลาคม
3. ใส่เวลาทำงานทั้งหมด และพัก/ลาที่อนุมัติแล้วในช่วงนั้น เวรทำงานต้องไม่ซ้อนกันและต้องอยู่ภายในช่วงข้อมูล ส่วนพัก/ลาอาจคร่อมขอบช่วงได้ ตัวคำนวณตัดเฉพาะส่วนที่เกี่ยวข้อง
4. ตรวจความครบถ้วน ใส่เหตุผล แล้วตรวจทานจำนวนช่วงก่อน/หลังหักพักและลา
5. ยืนยัน → ตรวจสิทธิ์และรุ่นล่าสุดอีกครั้ง → บันทึกรุ่นใหม่พร้อมข้อมูลเวรและหลักฐานคำขอในธุรกรรมเดียว

หนึ่งครั้งเป็น **การแทนตารางปัจจุบันทั้งชุด** ไม่ใช่เพิ่มเฉพาะบางวัน ต้องคงวันที่ยังต้องการใช้ไว้ในชุดใหม่ด้วย รุ่นเดิมถูกเก็บไว้ ไม่แก้/ลบย้อนหลัง ไม่มีปุ่มย้อนรุ่นอัตโนมัติหรือหน้าประวัติทุกรุ่นในรอบนี้

ขอบเขตทางเทคนิคต่อชุด: ไม่เกิน 366 วันจริง, 400 ช่วง และคำขอ 64 KiB ไม่ใช่กติกาจำนวนวันทำงานของบริษัท หากยืนยันชุดที่ไม่มีช่วงทำงาน จะหมายถึงทราบแล้วว่าไม่มีเวลาทำงานในช่วงข้อมูลนั้น และตัวคำนวณจะยังไม่มีกำหนด Sales ไม่สร้างเวรสมมติให้

เวลาเก็บอย่างแม่นยำถึง microseconds ไม่อาศัย timezone เครื่องผู้ใช้ ช่องเวลาแบบปฏิทินใช้กับค่าปกติ ส่วนค่าเดิมที่มีเศษวินาทีเกิน 3 หลักจะแสดงข้อความเวลาเต็มเพื่อไม่ให้ช่องเวลาของเบราว์เซอร์ทำค่าหาย หากเวลาแปลงเป็นปีกรุงเทพฯ เกินขอบเขตที่แสดงได้ จะหยุดให้ตรวจ ไม่ปัดเวลา

## 3. ข้อมูลและสิทธิ์ ไม่สร้างตารางเวรซ้ำกับของเดิม

ใช้ `crm_work_periods` ที่ออกแบบไว้เดิม โดยเพิ่มการผูกกับรุ่นตาราง ส่วนหัวและหลักฐานรุ่นเก็บในพื้นที่ส่วนตัว:

| ข้อมูล | ที่จัดเก็บ | หลักการ |
|---|---|---|
| ตารางปัจจุบันของ Sales | `sales_private.crm_work_calendars` | หนึ่งหัวต่อ Sales มีรหัสตารางคงเดิมและชี้รุ่นล่าสุด |
| รุ่น/ช่วงข้อมูลครบ/ผู้บันทึก/เหตุผล | `sales_private.crm_work_calendar_versions` | เพิ่มรุ่นใหม่เท่านั้น มีรุ่นก่อนหน้าและหลักฐานคำขอกันซ้ำในแถวเดียว ไม่สร้างใบรับซ้ำอีกตาราง |
| ช่วงทำงาน/พัก/ลา | `public.crm_work_periods` | เพิ่มแถวของรุ่นใหม่ ไม่แก้ช่วงของรุ่นเก่า ไม่รับเหตุผลสุขภาพรายช่วง |

ข้อมูลเวรเก่าที่ไม่มีรุ่นยังไม่ถูกนำมารวม ไม่ backfill หรือเดาว่าครบ ต้องให้ Admin ตรวจยืนยันชุดใหม่อย่างชัดเจน ไม่แก้ Lead, การขาย, วันเริ่ม Lead หรือกำหนด SLA จากคำสั่งจัดเวร

ร่างเดิมมีสิทธิ์อ่าน `crm_work_periods` กว้างเหมือน CRM จึงออกแบบให้ร่าง 06 ถอนสิทธิ์อ่านตารางนี้โดยตรง และให้เฉพาะ Admin อ่านผ่านช่องทางที่คัดข้อมูลแล้ว **ยังไม่ได้เปลี่ยนสิทธิ์ฐานจริง** ไม่ส่ง reason เดิมของแต่ละช่วง/เอกสาร HR และไม่ใส่ข้อมูลสุขภาพในเหตุผลจัดเวร

## 4. ช่องทางและการกันคำขอชนกัน

- `GET /api/sales-crm/work-schedule` ไม่ระบุ Sales = โหลดรายชื่อและสิทธิ์เท่านั้น ไม่สร้างตาราง; ระบุ `salesUserId` = อ่านรุ่นปัจจุบันที่ตรงคน ไม่แก้ last_seen
- `POST /api/sales-crm/work-schedule` รับ `requestId`, `salesUserId`, `expectedVersion`, `coverage`, `periods`, `confirmedComplete: true`, `reason` ไม่รับบทบาท ผู้อนุมัติ ผู้บันทึก เวลาเผยแพร่ หรือรหัสแถวเวรที่แต่งเอง
- ตรวจ token จริงและบทบาท Admin จากฐาน ไม่เชื่อ metadata ไม่ใช้ service-role และคำสั่งฐานล็อกแถวบทบาทจริงก่อนให้สิทธิ์
- สวิตช์ Server ต้องเปิดครบ `SALES_CRM_V2_ENABLED`, `SALES_CRM_LEAD_WORK_ENABLED`, `SALES_CRM_LIFECYCLE_ENABLED`, `SALES_CRM_SCHEDULE_ENABLED`; ฐานต้องเปิดครบสามสวิตช์เดิมและ `work_schedule_enabled` ด้วย ทั้งหมดในร่างเริ่มปิด ไม่มีการแก้ env
- หน้าเว็บอาจถูกสร้างไว้ตามค่า Server ตอน build การเปิดจริงภายหลังต้องมีขั้น build/deploy ด้วย ไม่ใช่เปลี่ยนฐานอย่างเดียว ส่วน API ตรวจสวิตช์และสิทธิ์ซ้ำทุกคำขอ
- `expectedVersion` ป้องกัน Admin สองคนแก้ทับกัน รวมการสร้างครั้งแรก ส่วน requestId+payload เดิมคืนรุ่นที่บันทึกสำเร็จแล้วโดยไม่เพิ่มซ้ำ แม้หลังจากนั้นมีรุ่นใหม่หรือ Sales ถูกปิดบัญชี แต่ผู้ส่งยังต้องเป็น Admin ที่ active
- ฟอร์มตรวจคิว **หนึ่งคิวต่อ Admin ในแท็บ ครอบคลุม Sales ทุกคน** เก็บก่อนส่ง ล็อกการเปลี่ยน Sales ทันที หากไม่ทราบผลให้ส่งเฉพาะคำขอเดิม ไม่สร้างรหัสใหม่ กู้คำขอเดิมได้จากหน้าแรกโดยไม่ต้องอ่านตารางของ Sales ที่อาจ inactive ไปแล้ว
- ถ้าครั้งแรกถูกปฏิเสธแน่ชัด ต้องอ่านใหม่ก่อนเริ่มรายการใหม่ แต่หากเคยไม่ทราบผลแล้ว การถูกปฏิเสธภายหลังไม่ทำให้ล้างคำขอเดิม การโหลดหลังบันทึกสำเร็จล้มเหลวไม่ทำให้ส่งบันทึกซ้ำ

คิวเก็บเฉพาะข้อมูลคำขอและผู้ทำ ไม่มี token หรือชื่อที่อ่านจากระบบ ไม่รับประกันกู้หลังปิดแท็บ/ล้างข้อมูลเบราว์เซอร์ หากคิวเสียหรือสิทธิ์เปลี่ยนให้เก็บรหัสและให้ Admin ตรวจ ไม่ล้างเพื่อทดลองใหม่ ยังไม่มีหน้าตรวจใบรับแยกในรอบนี้

ร่าง [06_work_schedule_draft.sql](D:/buildtrack/buildtrack-mvp-main/sql/sales/06_work_schedule_draft.sql) มีตัวหยุดก่อน DDL และ ROLLBACK **ห้ามถอดตัวหยุดแล้วรันเอง** ต้องตรวจรับและออก migration ติดตั้งแยก ร่าง 04/05 และ foundation เดิมไม่ได้ถูกแก้ในรอบนี้

## 5. จุดต่อ SLA และแจ้งเตือนที่ยังค้าง

รูปแบบเวรใหม่ส่งตรงเข้า `prepareSlaWorkCalendar` ได้ ใช้ตรวจฟอร์มและช่องทางข้อมูลแล้ว รอบต่อเนื่องเพิ่มการคำนวณแบบจำลองจากแหล่งเวรฝั่ง Server ใน [หน้าตรวจแผน SLA](D:/buildtrack/buildtrack-mvp-main/docs/sales-v2-sla-preview.md) แต่ยังไม่มีการบันทึก `staff_due_at` หรือส่งแจ้งเตือนจริงจากการจัดเวร:

1. ตัวคำนวณฝั่ง Server ต้องอ่านหัวตารางและรุ่นล่าสุดจากแหล่งเชื่อถือได้พร้อมหลักฐานงาน ไม่รับคำรับรองเวรจาก browser ของ Sales
2. จัดเก็บรุ่นเวร/นโยบายและผลคำนวณคู่กับงาน เมื่อตารางเปลี่ยนห้ามใช้ผลรุ่นเก่าส่งแจ้งเตือนต่อโดยไม่ตรวจ; ไม่ย้อนเปลี่ยนหลักฐานหรือคะแนนเก่าอัตโนมัติ
3. กติกา Lead เข้านอกเวร 2 ชั่วโมงทำงานมีแล้ว และผู้ใช้ยืนยันกรณีเข้าในเวร: ใช้กำหนด 24 ชั่วโมงจริง ถ้าตกนอกเวรให้นับ 2 ชั่วโมงทำงานจากช่วงถัดไป โดยไม่เปลี่ยนกำหนดบริการ ส่วนเปลี่ยนคน/ลูกค้าขอนัดภายหลังยังพักรอตรวจ ไม่เดาค่าให้ ระยะเตือน 30 นาทีคงเดิม ยังไม่ตั้งค่าในฐาน
4. เตรียม [คำสั่งหลังบ้านติดต่อครั้งแรก](D:/buildtrack/buildtrack-mvp-main/docs/sales-v2-first-contact-processing.md) แยกจากการบันทึกเวรแล้ว ล็อกหัวเวรและอ่านรุ่นล่าสุด เก็บประวัติผลคำนวณ กันซ้ำ และตรวจหลักฐานจบงาน ไม่คืนชีพรายการที่ถูกระงับ ยังไม่ผูกปุ่ม/ตั้งเวลา/ส่งจริง และไม่สร้าง Follow-up/Hot ให้อัตโนมัติ
5. ทดสอบธุรกรรมและสิทธิ์ใน PostgreSQL แยก ก่อนนำเข้าข้อมูล ปิดช่องเขียนเก่าและออก SQL ติดตั้ง ไม่ใช้ผล mock/static เป็นหลักฐานพร้อมเปิดจริง

ข้อจำกัดนี้แยกจากการจัดเวรสำเร็จ: การมีหน้า Admin และรูปแบบข้อมูลแล้ว ไม่ได้แปลว่าฝ่ายขายจะได้รับแจ้งเตือนหรือเริ่มถูกวัด SLA ในรอบนี้

## 6. ผลตรวจและการรักษางานเดิม

- ก่อนแก้: 1,608 ข้อใน 36 ไฟล์ผ่าน หลังผนวก: 2,029 ข้อใน 44 ไฟล์ผ่าน โดยรันทีละชุดเพื่อลดการใช้หน่วยความจำ ไม่ขยาย timeout หรือข้าม test
- TypeScript noEmit ผ่านหลังระบุชนิด headers ของ test ให้ชัด และ ESLint ของไฟล์ที่เปลี่ยนผ่านหลังแก้คำเตือนการใช้ ref ใน cleanup
- Production build ผ่าน รวมหน้าและ API work-schedule โดยอนุญาตดาวน์โหลด Google Fonts เดิม ไม่แก้ฟอนต์/env ไม่เปิดแอปกับข้อมูลจริงหรือรัน E2E สด ตรวจลิงก์เอกสารที่ปรับทั้ง 5 ไฟล์แล้วไม่พบเป้าหมายหาย
- API ทดสอบด้วย mock ไม่มีคำขอไป Supabase; SQL 06 ตรวจแบบ static 25 ข้อ ไม่ได้ execute หรือพิสูจน์ transaction/RLS/คำขอชนกันบน PostgreSQL จริง
- ไม่พบคำสั่ง PostgreSQL/Docker/Supabase CLI ใน PATH ของการตรวจรอบนี้ จึงยังไม่มีฐานแยกที่ยืนยันพร้อมทดสอบ ไม่ชดเชยด้วยการใช้ฐานจริง
- ตรวจ hash ไฟล์เดิม 90 ไฟล์ เปลี่ยนเฉพาะทางเข้า V2/ทดสอบ/เอกสารที่เกี่ยวข้อง 7 ไฟล์ อีก 83 ไฟล์คงเดิม รวม Master, app/page.tsx, Sidebar, LeadTracker/Kanban, หน้านัด/Checklist และ SQL foundation/01–05
- ไม่แก้ env ไม่เปิดสวิตช์ ไม่ทำ import/backfill ไม่แตะข้อมูลหรือสิทธิ์จริง และไม่มี SQL ให้ผู้ใช้รันในรอบนี้
