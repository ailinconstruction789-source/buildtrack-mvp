# ทดสอบสิทธิ์ร่วมกับกระบวนการฝ่ายขาย — ขั้น 3c

วันที่ 25 กันยายน 2569 ต่อจาก [ขั้น 3b](./account-security-crm-alignment.md)

ต่อเนื่อง: [ขั้น 3d พักสิทธิ์ฝ่ายขายเมื่อ Auth แบน/ปิดบัญชี](./account-security-auth-revocation.md) เพิ่มร่างและการทดสอบในเครื่องตามการยืนยันให้ Admin รับรองใหม่หลังปลดแบน รายการด้านล่างเป็นผล ณ จบขั้น 3c

## ขอบเขต

เพิ่มชุดทดสอบในเครื่อง ไม่เปลี่ยนหน้าจอหรือกติกาธุรกิจ ไม่แก้ร่าง SQL เดิม ไม่เปิดสวิตช์จริง ไม่ติดตั้ง migration และไม่ติดต่อฐาน Supabase จริง

ชุด `--account-security-only` สร้าง PostgreSQL ใหม่บน loopback ด้วยชื่อฐาน/ผู้ใช้/พอร์ตชั่วคราวที่ตรวจยืนยันแล้ว จากนั้นต่อร่าง SQL06–26 ทั้ง 21 ไฟล์เข้ากับ base/04/05 และสิทธิ์ขั้น 3b ใช้คำสั่งฝ่ายขายจริงจาก repository ไม่ mock ผลลัพธ์การจองหรือแบบสอบถาม

บัญชีสมมติใช้ Auth/session facade และรับรองบทบาทผ่าน `review_account_role` จริง ไม่เขียนสิทธิ์ลง `crm_user_roles` โดยตรง ไม่ใช้ข้อมูลลูกค้า/รายชื่อบัญชีจริง ไม่อ่าน `.env` หรือคีย์ Supabase

## กรณีที่ตรวจ

| ส่วนงาน | สิ่งที่ตรวจร่วมกับสิทธิ์ใหม่ |
|---|---|
| จอง | Sales จองได้ เก็บเจ้าของ/ราคาหลังหักส่วนลด ไม่สร้าง legacy Lead ซ้ำ ส่งคำขอเดิมซ้ำไม่เพิ่มรายการ |
| ยกเลิก | เจ้าของจองยกเลิกได้ Owner/ฝ่ายขายคนอื่นทำไม่ได้ เก็บวันที่และราคาจองเดิม ปลดแปลงกลับว่าง |
| หลังจอง | ทำสัญญา เตรียมเอกสาร ยื่นกู้ ถูกปฏิเสธแล้วสร้างรอบใหม่ อนุมัติ และยืนยันโอนด้วย DATE โดยไม่แต่งเวลาโอน |
| Visit/Customer Voices | เช็คอินจริงจากคำสั่งแล้วรอแบบสอบถาม ออก QR และส่งคะแนนครบ 8 ด้านจึง completed ส่งซ้ำไม่สร้างคำตอบใหม่ ช่องส่วนตัวที่ไม่ตอบยังเป็น NULL |
| ความเป็นส่วนตัว | QR เปิดเผยเฉพาะรุ่นฟอร์มและวันหมดอายุ เจ้าของ Lead/Admin/Owner อ่านคำตอบได้ Sales คนอื่นเห็นการส่งแล้วแต่ไม่เห็นคำตอบ |
| SOP | เริ่มชุด SOP โดย Sales เจ้าของงาน Admin/Owner/Sales คนอื่นทำแทนไม่ได้ รอบนี้ไม่ทดสอบจบทุกขั้น SOP ใหม่ทั้งหมด |
| ถอน/เปลี่ยนสิทธิ์ | เมื่อเปลี่ยน Sales เป็น Owner หรือปิดบัญชีผ่านคำสั่งรับรอง การ replay คำสั่งเดิมไม่คืนสิทธิ์เขียน ปิดบัญชีแล้ว QR ของงานที่มีเจ้าของ inactive เปิด/ส่งไม่ได้ และ Admin ออกแทนไม่ได้ |
| อ่านข้อมูล | ตัวอ่านการจอง หลังจอง โครงการ รายงาน ค้นหา Lead Visit โครงการที่สนใจ SOP Voices และแจ้งเตือนใช้ READ ONLY ได้ เมื่อปิดบัญชีตัวอ่านทั้งสิบปฏิเสธ |
| ประวัติ | เทียบข้อมูลลูกค้า/โครงการที่สนใจ/จอง/แปลง/กู้/Visit/SOP/Voices/ติดตาม/SLA/audit/หลักฐานคำสั่ง ก่อน–หลังปิดบัญชีและคำสั่งที่ถูกปฏิเสธ ต้องเหมือนเดิม |
| แจ้งเตือน | Admin จัดเวรจำลอง จากนั้นใช้บทบาท worker จริงสร้าง due-soon notice เจ้าของอ่าน/รับทราบได้ คนอื่นอ่านหรือรับทราบแทนไม่ได้ วน worker ใหม่ไม่ส่งซ้ำ |
| Worker หลังถอนสิทธิ์ | งานยัง open แต่พักที่ needs_owner ถอนแจ้งเตือนเดิม ไม่ลบงานและไม่เลื่อนกำหนดบริการลูกค้าเดิม |
| ทำงานพร้อมกัน | สังเกต backend ที่รอ lock จริง ทั้งจองก่อนถอนสิทธิ์ และถอนสิทธิ์ก่อนจอง คำขอหลังถอนสิทธิ์ถูกปฏิเสธและไม่สร้างลูกค้า/การจองครึ่งทาง |

การแจ้งเตือนใช้ลูกค้าสมมติที่มีวันเริ่มย้อนหลัง 23 ชั่วโมง 45 นาที พร้อมหลักฐานสมมติและเวรต่อเนื่องเพื่อทดสอบกรณีใกล้กำหนด ไม่ใช่การนำข้อมูลเก่าเข้าระบบหรือเวรจริง ไม่เปลี่ยนเวลาเครื่อง ไม่รอ 24 ชั่วโมง และไม่ติดตั้ง cron

## การตรวจซ้ำ

คำสั่งนี้สร้างและปิดฐานจำลองของตนเองเท่านั้น ไม่รับ URL หรือชื่อฐานที่มีอยู่:

```text
node scripts/sales-runtime/run.mjs --account-security-only
```

ผลทดสอบสุดท้าย:

- Vitest บัญชี/ล็อกอิน/ความปลอดภัยตัวทดสอบ: **211/211 ผ่าน** จาก 13 ไฟล์
- Native PostgreSQL 17.11: ขั้นก่อนหน้า 257 + workflow integration 85 = **342 assertions ผ่าน**
- รายงาน: `node_modules/.cache/buildtrack-sales-runtime/runs/run-5ZBH1S/report.json` — `status=passed`, `stopped=true`, `productionChanged=false`, `sourceFilesUnchanged=true`
- ESLint ไฟล์ทดสอบที่เพิ่ม/แก้ผ่าน และ `git diff --check` ของเอกสาร rollout ผ่าน
- ระหว่างเพิ่มกรณีทดสอบ รอบหนึ่งส่ง filter ช่องค้นหาเป็น NULL แต่ contract เดิมต้องการสตริงว่าง จึงถูกปฏิเสธด้วย CRM_INVALID_INPUT แก้เฉพาะ payload ทดสอบ ไม่ผ่อน validator ของแอป แล้วรันชุดทั้งหมดซ้ำผ่าน ฐานจำลองรอบที่ไม่ผ่านปิดเรียบร้อยเช่นกัน
- ไม่มีการรัน production build/browser E2E หรือเขียน Supabase ในรอบนี้

## สิ่งที่ผลนี้ยังไม่รับรอง

- การแบน/ลบบัญชีใน Supabase Auth โดยตรงต่างจากการปิดผ่านคำสั่งรับรอง ขั้น 3b ตรวจ caller ที่ role reader แล้ว แต่ QR/การเลือกเจ้าของ/worker ที่อ่าน CRM directory ยังต้องออกแบบและตรวจเส้นทางนี้ให้ครบ ไม่ถือว่า Auth ban จะปรับ projection อัตโนมัติ
- การคอมไพล์ SQL06–26 ครบไม่เท่ากับทดสอบทุกเส้นทาง: lifecycle เปลี่ยนเจ้าของ/ปิด lost, เพิ่มโครงการที่สนใจ, SOP ครบขั้น, dispatcher/burst และการแข่งขันทุกคู่ยังต้องรวมเข้าชุดสิทธิ์ใหม่ต่อไป ชุดทดสอบแยกเดิมไม่ถูกลบหรือแทนที่
- ไม่ได้ทดสอบ Supabase Auth/PostgREST จริง, browser E2E, Realtime, Storage หรือ legacy policies ของก่อสร้าง/โครงการ/แปลงในรอบนี้ READ ONLY ที่จำลองไม่ใช่หลักฐานทดสอบเครือข่ายจริง
- ไม่รับรองความเร็วส่งแจ้งเตือน 5 นาทีหรือกำลังรองรับ production จากชุดตรวจสิทธิ์นี้ และไม่ได้รับรองสูตร KPI ทุกชนิด
- ร่างทุกไฟล์ยังมี DESIGN ONLY + ROLLBACK ผู้ใช้ยังไม่ต้องรัน SQL ต้องเตรียม migration/cutover แยกหลังทดสอบระบบแยกและรับรองบัญชีครบ

แนวทาง Supabase/RLS และสิทธิ์ขั้นต่ำทำให้ชุดนี้ทดสอบผ่านบทบาท client/worker จริงในฐานจำลอง และตรวจการปฏิเสธควบคู่กับการทำงานสำเร็จ ไม่ใช้สิทธิ์เจ้าของฐานแทนฝ่ายขายในคำสั่งที่กำลังทดสอบ
