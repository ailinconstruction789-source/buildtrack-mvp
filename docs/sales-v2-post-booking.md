# งานสัญญา สินเชื่อ และยืนยันโอนจากรอบจองส่วนกลาง

23 กันยายน 2569 — โค้ดและ SQL21 ร่างในเครื่องเท่านั้น ไม่อ่านข้อมูลลูกค้าจริง ไม่รัน SQL บน Supabase ไม่เปลี่ยน env/สวิตช์ ไม่ Deploy และไม่เปิดระบบแจ้งเตือน

## ขอบเขตที่เชื่อม

จากรายการจองในโครงการ หรือประวัติจองของลูกค้า เปิด `/sales-crm/post-booking?saleId=…` ตามรหัสรอบจองจริง ใช้สายข้อมูล `sales → lead_project_interests → sales_customers` เดิม ไม่สร้าง Lead โครงการหรือคัดลอกลูกค้าใหม่

| ขั้นตอน | การบันทึก |
|---|---|
| จอง → ทำสัญญา | วันเวลาเกิดเหตุการณ์ เหตุผล และข้อความอ้างอิงหลักฐาน; ตั้งวันทำสัญญาเพียงครั้งเดียว |
| ทำสัญญา → ดาวน์ / เตรียมเอกสาร | เปลี่ยนสถานะพร้อมเหตุผล; สถานะดาวน์ไม่ใช่บัญชีรับเงินหรือใบเสร็จ |
| เตรียมเอกสาร → ยื่นกู้ | เฉพาะกู้ธนาคาร ระบุธนาคาร สร้างรอบยื่นและเลขอ้างอิงใหม่ |
| ยื่นกู้ → อนุมัติ / ปฏิเสธ | ผูกกับรอบยื่นล่าสุด; อนุมัติต้องมีวงเงินจริง ผลปฏิเสธใช้วงเงิน null ไม่ใช่0 |
| ปฏิเสธ → ยื่นใหม่ | เพิ่มแถวใหม่ เลขรอบถัดไป เก็บผลปฏิเสธเดิม ไม่รีเซ็ตหรือเขียนทับ |
| กู้อนุมัติ → รอโอน | ตรวจผลอนุมัติล่าสุดจริง วันยื่น/วันผล/วงเงินครบ ไม่มีรอบที่ยังรอผลค้าง |
| เงินสด → รอโอน | ไปได้หลังสัญญา/ดาวน์/เตรียมเอกสาร ไม่สร้างสินเชื่อสมมติ |
| รอโอน → โอนแล้ว | ระบุวันโอนจริงแบบวันที่และเหตุผล ไม่บังคับไฟล์ เลขเอกสาร เวลาโอน หรือข้อความอ้างอิงหลักฐาน |

ผู้ใช้ยืนยันให้ระบุวันโอนเฉย ๆ จึงเพิ่มคำสั่ง `confirm_transfer` โดยคงเหตุผลตามกติกาทุกการเปลี่ยนสถานะเดิม ไม่มีการบังคับไฟล์/เลขเอกสาร/เวลาโอน ยังไม่มีคำสั่งส่งมอบ งานยกเลิกจอง/กลับมาติดตาม/จองใหม่ยังใช้คำสั่ง18ที่มีอยู่ ไม่เพิ่มคำสั่งยกเลิกซ้ำ การกู้ถูกปฏิเสธไม่ยกเลิกจองหรือคืนแปลงอัตโนมัติ

Sales/Admin/Owner อ่านทุกโครงการได้ตามสิทธิ์ที่ฐานรับรอง ผู้บันทึกได้เฉพาะ Sales เจ้าของความสนใจปัจจุบันหรือ Admin; Owner อ่านอย่างเดียว ไม่ให้สิทธิ์จากข้อความ metadata ในบัญชี ยืนยันโอนได้จากรอโอนเท่านั้น ไม่ข้ามสัญญาหรือผลกู้ ลูกค้าที่โอน/ส่งมอบ/ยกเลิกยังเปิดประวัติได้ แต่ไม่มีปุ่มเปลี่ยนขั้นต่อในรอบนี้

## วันโอนจริง ไม่ใช่เวลาโอนสมมติ

- แบบฟอร์มเริ่มวันที่ว่าง ให้ผู้บันทึกระบุเอง ใช้ `YYYY-MM-DD` แบบ Gregorian ผ่าน API และแสดงวันที่ไทย โดยไม่เติมเที่ยงคืนหรือเวลา ณ ตอนกดบันทึกเป็นเวลาโอน
- เก็บ `sales.crm_transfer_date` ชนิด DATE เป็นวันโอนของรอบจองเดิม; วันที่ใน event/receipt/audit เป็นหลักฐานประวัติธุรกรรม ไม่สร้างลูกค้า/การจองใหม่ เวลา `recorded_at` คือเวลาบันทึกจริงเท่านั้น ส่วน `occurred_at` ของเหตุการณ์โอนเป็นnull เพราะไม่ทราบเวลา
- วันที่ต้องถูกต้อง ไม่อยู่อนาคตตามวันกรุงเทพฯ และไม่ก่อนวันจอง/สัญญา/รอโอน/ผลกู้ที่ทราบ เปรียบเทียบระดับวัน จึงยืนยันโอนในวันเดียวกับการเตรียมเอกสารได้โดยไม่ต้องเดาเวลา
- เปลี่ยน `crm_stage` และ `contract_status` เป็นโอนแล้วในธุรกรรมเดียว ตรวจแปลงยังถูกครอบครองและไม่คืนสต็อก ไม่เปลี่ยน `plot.sale_status` ซึ่งมีความหมายเดิมด้านอื่น หลังโอนห้ามยกเลิกด้วยคำสั่งจองปกติ ห้ามยืนยันซ้ำด้วยรหัสใหม่หรือเขียนวันโอนทับ
- เงินสดไม่มีสินเชื่อสมมติ รายการกู้ตรวจผลอนุมัติล่าสุดและไม่มีรอบรอผลซ้ำอีกครั้งก่อนยืนยัน ไม่ให้ป้ายสถานะรอโอนอย่างเดียวใช้ข้ามหลักฐานผลกู้
- เก็บ `transferred_at` และข้อมูลย้อนหลังเดิมไว้ไม่แก้ ไม่แปลงหรือเติมวันที่ให้แถวเก่าอัตโนมัติ ต้อง review การย้ายวันโอนเก่าแยกก่อนเปิดจริง รายงาน legacy/SQL02–03 เดิมตรวจ timestamp ไม่ใช่ตัวตรวจรับวันโอน V2 หลัง cutover จึงต้องใช้แผนตรวจรับ V2 ที่รองรับ DATE และหยุดผู้เขียน legacy ให้ครบ
- รายการโครงการ19จะเข้าหมวดโอนจากสถานะเดียวกัน เปิดประวัติงานหลังจองเพื่อดูวันโอน; รายงาน20นับโอนเป็นส่วนหนึ่งของจองสุทธิ ไม่บวกจำนวนบ้านซ้ำ และไม่เปลี่ยนกติกา KPI รายบุคคล

## หลักฐาน ประวัติ และการป้องกันข้อมูลซ้ำ

- งานสัญญา/สินเชื่อผู้ใช้ระบุวันเวลาเองตามกรุงเทพฯ ไม่ใส่เวลาปัจจุบันแทนวันเกิดเหตุการณ์ และฐานไม่รับเวลาอนาคต/ก่อนหลักฐานก่อนหน้าที่ทราบ เวลาบันทึกเข้าระบบเก็บแยกต่างหาก ส่วนยืนยันโอนใช้วันที่อย่างเดียวตามหัวข้อข้างต้น
- ข้อความอ้างอิงหลักฐานเป็นคำบันทึกของเจ้าหน้าที่ ไม่ใช่ไฟล์แนบหรือการตรวจเอกสารจากธนาคาร หน้าจอแจ้งข้อจำกัดนี้
- ประวัติเปลี่ยนสถานะ/เหตุผล/ผู้บันทึกและรอบยื่นกู้แยกหน้าไม่เกิน50รายการต่อส่วน อ่านรอบล่าสุดแยกจากหน้าประวัติ จึงไม่บันทึกผลให้รอบเก่าเพราะเปลี่ยนหน้า
- ข้อมูลเก่าไม่มีหลักฐานยังคง null ไม่สร้างวันที่หรือวงเงินให้เอง วิธีชำระไม่ทราบอ่านได้อย่างเดียว; ผลกู้เก่าที่หลักฐานไม่ครบจะไม่ผ่านคำสั่งรอโอน/ยื่นใหม่โดยอาศัยชื่อสถานะอย่างเดียว
- คำสั่งหนึ่งครั้งบันทึกสถานะ/สินเชื่อ/เหตุการณ์/audit/ใบรับในธุรกรรมเดียว ถ้าล้มเหลวต้องไม่เหลือข้อมูลครึ่งทาง ใช้ lock ร่วมกับจอง/ยกเลิก18และตรวจ revision ผู้ดูแล/รอบจองอีกครั้ง
- เก็บคำขอชั่วคราวใน sessionStorage ตามผู้ใช้และแท็บก่อนส่ง หากผลไม่ชัดเจนต้องตรวจด้วยรหัสและข้อมูลเดิม ไม่สร้างคำขอใหม่เอง; ถ้าพื้นที่เก็บผิดพลาดให้หยุดบันทึก/นำทาง ไม่ล้างคำขออัตโนมัติ
- คำขอเดิมหลังสถานะเปลี่ยนคืนใบรับเดิมโดยไม่ย้อนสถานะ แต่ยังตรวจสิทธิ์ปัจจุบัน เจ้าของเก่าที่ถูกย้ายงานไม่มีสิทธิ์ replay ภายหลัง

SQL21 ไม่เปลี่ยน Lead date, เจ้าของความสนใจ, ราคาขาย/ส่วนลด/เงินจอง, stock หรือ legacy bank status ไม่ให้เครดิต KPI รายบุคคล รายงาน20และรายการโครงการ19อ่านสถานะจาก sale เดียวกัน ไม่ใช้การจองแรกแทนทุกรอบ

## ยังไม่เปิดใช้จริง

หน้า/API ต้องผ่านสวิตช์เดิมและ `SALES_CRM_POST_BOOKING_ENABLED=true` แบบตรงตัว ฝั่งฐานต้องมี capability `post_booking_v2` และ `post_booking_enabled` ซึ่งค่าเริ่มต้นเป็นfalse ฐานรุ่นv1จะไม่ผ่านการตรวจรับของ API ใหม่ ไม่มีการเปลี่ยนสวิตช์จริงในรอบนี้ ลิงก์งานหลังจองซ่อนเมื่อฟีเจอร์ปิด

SQL21 มีตัวหยุด DESIGN ONLY และท้าย ROLLBACK **ไม่ใช่ migration สำหรับให้ผู้ใช้นำไปรัน** ไม่มี service-role key ในการเรียก API ใช้ JWT ผู้เรียก ตรวจบทบาทจากฐาน และไม่มี fallback ไปเขียนตารางเดิม

ก่อนเปิดใช้ยังต้องตรวจ schema/RLS/trigger และ legacy writers จริง ซ้อมข้อมูลเก่าและ staging end-to-end ตรวจ production build และให้ผู้ใช้อนุมัติ migration/สวิตช์แยกต่างหาก ฟีเจอร์นี้ไม่ได้ทำให้ cutover ทั้งระบบพร้อมโดยอัตโนมัติ

## การตรวจสอบในเครื่องรอบยืนยันโอนแบบวันที่

Native `node scripts/sales-runtime/run.mjs --post-booking-only` รายงาน `node_modules/.cache/buildtrack-sales-runtime/runs/run-Jhfdgr/report.json` ผ่าน: compile19ร่าง base/04–21, **121 assertions และ10กลุ่ม concurrency/31assertions**; projection parity ของทั้งคำสั่งเดิมและยืนยันโอนแบบวันที่ผ่าน ฐานหยุดแล้ว (`stopped=true`) และไม่มี postmaster.pid

ครอบคลุมวันผิดรูป/ปีอธิกสุรทิน/วันอนาคต/ขอบวันกรุงเทพฯ, เหตุผล/เจ้าของ/Admin/Owner, กู้ต้องมีผลอนุมัติจริง, เงินสดไม่สร้างกู้, วันที่ไม่เติมเวลา legacy, audit/event/receipt, ผลอ่านอย่างเดียว, การย้อนทั้งหมดเมื่อ audit ล้มเหลว, ยืนยันซ้ำและยกเลิกชนกับโอนทั้งสองลำดับ รายงาน20ยังนับโอนเป็นส่วนหนึ่งของจองสุทธิไม่เพิ่มยอดบ้านซ้ำ

รอบแรก `run-9A4zIF` หยุดที่วงเล็บ expression JSON ใน assertion เทียบรายงานของ fixture แก้เฉพาะวงเล็บแล้วรันฐานใหม่ผ่าน ไม่เปลี่ยนตรรกะธุรกิจหรือผ่อนข้อบังคับ ทั้งสองฐานหยุดและไม่มี postmaster.pid ไม่รันชุดความจุ notification ซ้ำ และไม่ทดสอบ Supabase/PostgREST/บัญชีจริง

Vitest ทั้งแอป **5,107 tests / 127 files ผ่าน** ด้วยหนึ่ง worker (`205.03s`) รวมหน้าจอโอนแบบวันที่, ownership, ประวัติ, pending/retry หลังเน็ตขาดและ API/contract v2 ชุดเดิม HouseHandoverView มีคำเตือน React act แต่ไม่มีข้อทดสอบล้มเหลว TypeScript ทั้งโครงการ `--noEmit --incremental false` ผ่าน ไม่รัน production build หรือ browser E2E ในรอบนี้

ESLint เฉพาะ19ไฟล์ของงานนี้ผ่านโดยไม่มี warning และ `git diff --check` ผ่าน ไม่แก้ข้อมูล/env/สวิตช์จริงหรือโมดูลที่ไม่เกี่ยวข้อง

## การตรวจสอบในเครื่องรอบก่อนเพิ่มยืนยันโอน

ชุดทดสอบประกอบด้วย contract/API/client, การคงคำขอเมื่อเน็ตหลุด, หน้าจอ/สิทธิ์/การแบ่งหน้า และ PostgreSQL จำลองแยกผ่าน `node scripts/sales-runtime/run.mjs --post-booking-only` ใช้ฐานใหม่บน loopback เท่านั้น ไม่รับ URL/ข้อมูลเชื่อมต่อของแอป

Native รายงาน `node_modules/.cache/buildtrack-sales-runtime/runs/run-yWyPRX/report.json` ผ่าน: compile19ร่าง base/04–21, 75 assertions +6กลุ่ม concurrency/19assertions, SQL/TypeScript projection parity, read-only context และ `stopped=true` การ retry จำลองจากคำขอเดิม ไม่ใช่การตัดเครือข่ายจริงกับ Supabase/PostgREST ไม่รันชุดความจุ notification เดิมซ้ำ

Vitest ทั้งแอป **5,057 tests / 127 files ผ่าน** ด้วยหนึ่ง worker (`255.02s`) รวมจุดเชื่อมรอบจองจริงและการซ่อนลิงก์ระหว่างผลยกเลิกยังไม่ชัดเจน มีคำเตือน React act ในการทดสอบ HouseHandoverView เดิม แต่ไม่มีข้อสอบล้มเหลว TypeScript ทั้งโครงการ `--noEmit --incremental false` ผ่าน ยังไม่รัน production build หรือ browser E2E/บัญชีจริงในรอบนี้

ESLint เฉพาะไฟล์งานหลังจอง/จุดเชื่อม/เครื่องมือทดสอบผ่านโดยไม่มี warning และ `git diff --check` ผ่าน ไม่แก้โมดูลเดิมที่ไม่เกี่ยวข้องเพื่อเก็บ lint และไม่ลบข้อมูลหรือไฟล์ใด
