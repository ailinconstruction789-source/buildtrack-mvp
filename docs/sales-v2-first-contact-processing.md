# ประมวลผล SLA ติดต่อครั้งแรก — หลังบ้านและหน้า Admin ที่เตรียมไว้ ยังไม่เปิดใช้

สถานะ 17 กันยายน 2569: เตรียมคำสั่งหลังบ้านสำหรับ Admin เพื่อคำนวณ/บันทึกกำหนด ตรวจหลักฐานจบงาน และสร้างแจ้งเตือนในแอปแบบกันซ้ำ **ผ่านการรัน SQL/RPC บน PostgreSQL แยกในเครื่องด้วยข้อมูลสมมติแล้ว แต่ไม่อ่านหรือเปลี่ยน Supabase ไม่แก้ env ไม่เปิดสวิตช์จริง ไม่ส่งจริง และไม่มี SQL ติดตั้งให้ผู้ใช้นำไปรัน**

อัปเดต18กันยายน2569: แยก business application ในร่าง09 เป็น private shared core เพื่อให้ [system worker13](D:/buildtrack/buildtrack-mvp-main/docs/sales-v2-system-worker.md) ใช้ร่วมกันแล้ว โดยยังคง auth/สิทธิ์/ล็อก/ใบรับและรูปแบบผลของ Admin เดิม ไม่คัดลอกสูตร SLA ไม่เปลี่ยน API/หน้าจอ ไม่เปิด Cron หรือรัน Supabase ชุด native เดิมผ่านหลังแยกแกน

## 1. ขอบเขตของขั้นนี้

- เฉพาะงาน `first_contact` ของ Lead ส่วนกลางที่ไม่ได้เกิดจากกิจกรรมอื่น ไม่สร้างงานใหม่ ไม่รวม Follow-up/Hot/งานรายโครงการ และไม่คำนวณ KPI
- POST `/api/sales-crm/sla-process` รับเฉพาะ `requestId` กับ `taskId` ไม่มี GET ที่ประมวลผล ไม่มีปุ่มเรียกจากหน้าจำลองหรือ inbox ไม่มี scheduler/cron หรือการประมวลผลอัตโนมัติ
- รอบหน้า Admin เพิ่ม `/sales-crm/sla-processing` สำหรับเลือก/ทบทวน/ติ๊กยืนยันทีละงาน และ GET `/api/sales-crm/sla-receipts` เพื่ออ่านใบรับของ Admin บัญชีเดียวกันโดยไม่ส่งคำสั่ง ร่าง SQL10 อ่าน ledger เดิม ไม่เพิ่มตารางหรือเปลี่ยน SQL09 รายละเอียดใน [คู่มือ Admin](D:/buildtrack/buildtrack-mvp-main/docs/sales-v2-admin-processing.md)
- ตรวจบัญชีและบทบาท Admin จากแหล่งเชื่อถือได้ ใช้ public key กับ token ของผู้เรียก ไม่ใช้ service-role ไม่ให้ browser ส่งเจ้าของ เวลา เวร หลักฐานจบงาน หรือผล preview มารับรองเอง
- ร่าง 09 คำนวณใหม่ในธุรกรรมจากข้อมูลที่ล็อกไว้ ไม่ใช้ผล TypeScript preview เป็นคำสั่งบันทึก ทั้งคำสั่งต้องสำเร็จพร้อมกันหรือย้อนกลับทั้งหมด

## 2. สิ่งที่คำสั่งออกแบบให้ทำ

1. ตรวจสวิตช์และสิทธิ์ปัจจุบัน ล็อกคำขอ/ลูกค้า/หัวเวร/บทบาท/งาน/แจ้งเตือนตามลำดับที่เข้ากับคำสั่งเดิม แล้วอ่านเวลา Server หลังรอล็อก
2. ตรวจหลักฐานสร้าง Lead เดิม เจ้าของที่ไม่เคยเปลี่ยน วันเริ่มงาน กำหนดบริการ และข้อยกเว้น ไม่ใช้ชื่อ Sales หรือวันที่นำเข้าแทนหลักฐาน
3. ถ้ามีการติดต่อสำเร็จ ต้องพิสูจน์จากกิจกรรมของคำสั่ง `record_attempt` ในร่าง 04 พร้อม audit งานถัดไป และใบรับคำขอต้นฉบับที่ยืนยันผล/ช่องทาง/เวลา เลือกเวลาเกิดการติดต่อครั้งแรกที่พิสูจน์ได้ ไม่ใช้เวลาประมวลผลเป็นวันติดต่อ เติม `first_contacted_at` เฉพาะเมื่อยังว่างพร้อมประวัติก่อน–หลัง ไม่เปลี่ยนค่าที่ขัดกับหลักฐานให้เอง
4. ถ้ายังต้องติดต่อต่อ ให้นำเวรรุ่นปัจจุบันมาหักช่วงพัก/ลาที่ซ้อนกันโดยไม่หักซ้ำ แล้วคำนวณกำหนด Sales ด้วยกติกา 24 ชั่วโมง/120 นาทีทำงานที่ยืนยันแล้ว โดยไม่เปลี่ยน `lead_created_at` หรือ `service_due_at`
5. เก็บรุ่นเจ้าของ/lifecycle/เวร/นโยบายพร้อมกำหนดที่คำนวณ และเพิ่มประวัติก่อน–หลังใน audit ไม่ลบประวัติเดิมหรือคิดคะแนนย้อนหลัง
6. ถอนแจ้งเตือนที่ไม่ตรงหลักฐานปัจจุบัน และสร้างรายการที่เข้าเงื่อนไขเพียงครั้งเดียวต่อรหัสกันซ้ำ ตรวจช่วงทำงานจริง ณ เวลาประมวลผล เมื่อเกินกำหนดจะถอนรายการใกล้ครบกำหนดเดิมด้วย

การพบ `first_contacted_at` หรือกิจกรรมที่ระบุ `contact_success` อย่างเดียว **ไม่พอให้ปิดงาน** หลักฐานหลายขอบเขต ขัดกัน ถูกแก้ไข หรือไม่ครบยังพักรอตรวจ การติดต่อโดย Admin อาจพิสูจน์ว่าติดต่อแล้ว แต่ไม่ให้เครดิตว่า Sales เป็นผู้ทำแทนโดยอัตโนมัติ งานถัดไปที่ถูกแทนด้วยแผนใหม่ยังเป็นประวัติได้ ไม่บังคับว่าต้องเปิดอยู่

กรณีเปลี่ยนเจ้าของ ลูกค้าขอนัดภายหลัง ข้อยกเว้น ข้อมูลเก่า และเวรไม่ครบยังไม่สร้างสูตรใหม่ให้เอง งานที่พักจะไม่ค้างหลักฐานพร้อมส่งจากรอบก่อน งานปิดแล้วไม่ถูกเปิดกลับ และคำสั่งนี้ไม่ตีความ Lost เป็นการยกเลิกจอง

## 3. กันซ้ำและรับมือผลไม่แน่ชัด

| กลไก | หน้าที่ |
|---|---|
| ใบรับส่วนตัวต่อ Admin + requestId | คำขอเดิมคืนผลเดิม ไม่ประมวลผลซ้ำ; ใช้รหัสเดิมกับงานอื่นถูกปฏิเสธ |
| รหัสแจ้งเตือน `first_contact_delivery_v1` | ผูกงาน ผู้รับ lifecycle รุ่นเวร กำหนด ประเภท และนโยบาย ไม่ใช้เวลาที่กดเป็นรหัสใหม่ |
| `UNIQUE(recipient_user_id,dedupe_key)` | กันสองคำสั่งสร้างรายการเดียวกัน ไม่ย้ายผู้รับหรือสถานะอ่าน |
| คิวคำขอฝั่งแท็บ | เก็บเฉพาะ Admin/requestId/taskId ก่อนส่ง ตรวจว่าเก็บได้จริง และบล็อกการเปลี่ยนงานเพื่อข้ามคำขอค้าง |

รหัสแจ้งเตือนใหม่รวมรุ่นเวรด้วย เพราะเวรเปลี่ยนได้แม้กำหนดที่คำนวณเท่าเดิม รหัสจากตัววางแผน preview ไม่ใช่รหัสที่ใช้เขียนในร่างนี้ ไม่แก้หรือต่อชีวิตรายการที่ถอนแล้ว หากชนรหัสที่ถอนแล้วจะคืน `suppressed` ไม่รายงานว่าส่งสำเร็จ

ผลคำขอมี `processedAt` และ `replayed` จึงเป็นใบรับเหตุการณ์ในอดีต ไม่รับรองว่างานหรือแจ้งเตือนยังมีสถานะนั้นในปัจจุบัน ถ้าขาดการตอบกลับให้ลอง **requestId และ taskId เดิม** เท่านั้น ไม่สร้างรหัสใหม่ แม้การลองครั้งถัดไปถูกปฏิเสธ ก็ยังไม่พิสูจน์ว่าครั้งก่อนล้มเหลว

คิวไม่ส่งซ้ำเอง ไม่สร้าง UUID ให้เอง และไม่ล้างคำขอเมื่อผลไม่แน่ชัด ถ้าได้รับผลสำเร็จแต่ล้างคิวไม่ได้ จะแยก “ได้รับใบรับแล้ว” ออกจากปัญหาจัดเก็บ เมื่อเปลี่ยนบัญชีจะไม่ใช้คำขอของ Admin คนก่อนกับบัญชีใหม่ ข้อมูลคิวไม่มี token ชื่อลูกค้า เบอร์ หรือรายได้ แต่การปิดแท็บ/ล้างข้อมูลเบราว์เซอร์อาจทำคิวหาย ต้องให้ Admin ตรวจใบรับก่อนเริ่มรหัสใหม่

## 4. สวิตช์และข้อจำกัด

- ต้องเปิดสวิตช์ Server เดิมทั้ง 6 และ `SALES_CRM_SLA_PROCESSING_ENABLED` พร้อมสวิตช์ฐานเดิมทั้ง 6 และ `sla_processing_enabled` ร่างเพิ่มสวิตช์แบบเริ่มปิด ไม่มีการตั้งค่าจริงในรอบนี้
- การอ่านใบรับ SQL10 ต้องมีสวิตช์อ่านเดิม 6 ตัวและสิทธิ์ Admin แต่ไม่บังคับสวิตช์ประมวลผลตัวที่ 7 เพื่อให้ตรวจผลเก่าได้ขณะปิดการเขียน การไม่พบใบรับไม่ปลดล็อกคำขอค้าง
- ร่างเตรียม `sla_due_soon_minutes` ค่าเริ่มต้น 30 สำหรับการตั้งค่าภายหลัง แต่รุ่นนี้รองรับนโยบายที่ยืนยันแล้วเท่านั้น: 24 ชั่วโมง/120 นาทีทำงาน/เตือนก่อน 30 นาที ค่าอื่นพัก `POLICY_REVIEW` จนกว่าจะต่อหน้าตั้งค่าและ preview ให้ใช้รุ่นเดียวกัน
- จำกัดเวร 400 ช่วงต่อรุ่นและช่วงครอบคลุมไม่เกิน 366 วัน ตรวจหลักฐานติดต่อสำเร็จไม่เกิน 100 รายการ; เกินขอบเขตจะพัก ไม่ตัดข้อมูลแล้วอ้างว่าครบ
- ร่าง [09_first_contact_processing_draft.sql](D:/buildtrack/buildtrack-mvp-main/sql/sales/09_first_contact_processing_draft.sql) มีตัวหยุดก่อน DDL และ ROLLBACK **ห้ามถอดตัวหยุดแล้วรันเอง** ไม่แก้ SQL foundation/01–08 ไม่ backfill และไม่เปลี่ยนสิทธิ์จริง
- ใช้ตารางงานและแจ้งเตือนเดิม เพิ่มเฉพาะที่เก็บใบรับคำสั่งส่วนตัว ไม่สร้าง Lead/งาน/แจ้งเตือนอีกชุดคู่ขนาน

## 5. ต้องตรวจต่อก่อนใช้งานจริง

อัปเดตรอบฐานแยก 17 กันยายน: base และ 04–09 สร้างได้บน PostgreSQL 17.11, ชุดธุรกรรม/สิทธิ์ผ่าน 91 assertions, clock ผ่าน 80 กรณี และหลาย session ผ่าน 9 กลุ่ม/29 assertions โดย SQL ต้นฉบับไม่เปลี่ยนและฐานทดสอบหยุดแล้ว อ่านขอบเขต/สิ่งที่ยังไม่ครอบคลุมใน [ผลทดสอบฐานแยก](D:/buildtrack/buildtrack-mvp-main/docs/sales-v2-isolated-database-tests.md) ผลนี้ไม่แทนการตรวจ schema/trigger/สิทธิ์เดิมหรือ JWT/PostgREST บน staging

ผล unit/mock/static และ build ไม่พิสูจน์ว่า PostgreSQL/RLS/ธุรกรรมทำงานถูกต้อง การเขียน activity/ใบรับเดิม/การแก้ไขหลักฐานในอนาคตต้องรักษาประวัติและใช้ล็อกลูกค้าร่วมกัน ห้ามเปิดช่อง privileged write ที่ข้ามข้อกำหนดนี้ ต้องทดสอบในฐานแยกก่อนออก migration ติดตั้ง โดยเฉพาะ:

- เทียบตัวคำนวณ SQL กับ TypeScript สำหรับทั้ง 3 กติกา เศษวินาที ช่วงพัก/ลาซ้อน ข้ามวัน สิ้นเวร และข้อมูลไม่ครบ
- คำขอซ้ำ/ขัดแย้ง/สองคำขอพร้อมกัน/ขาดการตอบกลับหลัง commit ต้องมีใบรับและแจ้งเตือนเท่าที่ควร ไม่มีผลครึ่งทาง
- เปลี่ยนเวรครั้งแรกหรือเปลี่ยนรุ่นที่กำหนดเท่าเดิม เปลี่ยนเจ้าของ ปิด Lead ถอนสิทธิ์ และกดอ่านแล้วชนการประมวลผล ต้องไม่เกิดรายการข้ามคนหรือใช้รุ่นเก่า
- ติดต่อสำเร็จหลายรายการ/ย้อนหลัง/ถูก correction/ทำโดย Admin/หลักฐานโครงการปะปน ต้องไม่ปิดงานผิดหลักฐาน ไม่คิด KPI จากผลคำสั่ง
- เตรียมหน้าตรวจใบรับ/ปุ่มยืนยัน Admin และ [คำสั่งจำกัด 10 งานต่อรอบ](D:/buildtrack/buildtrack-mvp-main/docs/sales-v2-bounded-cycles.md) แล้ว แต่ยังไม่เปิดใช้งาน ต้องต่อ durable dispatcher/วัดความจุและตรวจทั้งเส้นทางใน staging ไม่เปิดตัวส่งจากการเปิดหน้าอ่านข้อมูล

สถานะรวมและผลตรวจในเครื่องอยู่ใน [แผน rollout](D:/buildtrack/buildtrack-mvp-main/docs/sales-v2-compatibility-and-rollout.md)
