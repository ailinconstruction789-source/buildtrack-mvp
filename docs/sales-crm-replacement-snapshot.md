# แผนรับข้อมูลฝ่ายขายชุดเต็มล่าสุด

ยืนยัน 28 กันยายน 2569: ผู้ใช้จะส่งชุดใหม่ที่รวมลูกค้าเดิม ลูกค้าเพิ่ม และสถานะล่าสุด ข้อมูลลูกค้า/จอง/ยกเลิก/โอนชุดเดิมไม่จำเป็นต้องคงแสดงในระบบใหม่ แต่ **ยังไม่ลบจนกว่าจะรับ ตรวจ และอนุมัติชุดใหม่พร้อมแผนคืนระบบแล้ว**

เอกสารนี้แทนเส้นทาง “ย้าย 895 Leads / 289 Sales จากฐานเดิมโดยตรง” ในแผนก่อนหน้า ตัวเลขเดิมเป็นเพียงผลตรวจในอดีต ไม่ใช่จำนวนที่บังคับให้ไฟล์ใหม่ต้องเท่ากัน ไม่ยกเลิกงานสิทธิ์และความปลอดภัยของ foundation ที่เตรียมไว้

## ขอบเขตที่ยืนยัน

- รับแบบ full snapshot ไม่ใช่ incremental update และไม่เอาไฟล์ใหม่ไปต่อท้ายจนลูกค้าเดิมซ้ำ
- ลูกค้าเดียวมีหลายโครงการที่สนใจได้ ผู้ดูแลและสถานะความสนใจแยกตามโครงการ; Lead ไม่จำเป็นต้องเลือกโครงการ
- การจองและยกเลิกแต่ละครั้งเป็นคนละรายการ ไม่ใช้ชื่อหรือเบอร์เป็นรหัสการจอง ไม่รวมคนจากเบอร์ร่วมกัน
- ข้อมูลที่ไม่มีหลักฐานคงเป็นไม่ทราบ ไม่สร้างวันที่ ประวัติ Visit/แบบสอบถาม ผลกู้ หรือ SLA ย้อนหลังให้ครบเอง
- เก็บโครงการ แปลง งานก่อสร้าง งานฝ่ายอื่น บัญชี และสิทธิ์เดิม ไม่ใช้ล้าง schema / TRUNCATE CASCADE / reset ฐานข้อมูล
- การปรับสถานะการขายบนแปลงต้องเป็นรายแปลงที่ตรวจผลกระทบและหลักฐานแล้ว ไม่ตั้งทุกแปลงเป็นว่าง
- การอนุญาตให้แทนที่ข้อมูลลูกค้าไม่ใช่การอนุญาตให้ลบรายการที่ฝ่ายอื่นอ้างอิงอยู่ ต้องรายงานและเลือกเก็บรหัส/เชื่อมใหม่/เก็บประวัติแทนก่อน

## ลำดับงาน

1. เตรียมระบบและทดสอบโดยยังเก็บฐานเดิมไว้ — ไม่ทำ legacy backfill ชุด 895 รายการระหว่างรอไฟล์ใหม่
2. รับไฟล์ต้นฉบับ ตรวจทุกชีต/คอลัมน์/สูตร/จำนวนแถว ระบุวันที่ข้อมูลล่าสุดและรุ่นไฟล์; ยังไม่กำหนดชื่อคอลัมน์ Excel ให้ผู้ใช้ต้องเปลี่ยนตอนนี้
3. จัด mapping รหัสลูกค้า รหัสความสนใจ และรหัสรายการจองที่คงเดิมเมื่อทดสอบซ้ำ หากไฟล์ไม่มีรหัส ให้จัดทำตารางจับคู่ที่ตรวจได้ ไม่ใช้ชื่อ/เบอร์/เลขแถวเป็นตัวตนถาวรโดยอัตโนมัติ
4. ตรวจข้อมูลตามตัวตรวจในเครื่อง แล้วเทียบรายละเอียดกับต้นฉบับ: จำนวนแต่ละโครงการ/เจ้าของ/สถานะ เงินที่ทราบและไม่ทราบ แปลงจองซ้อน รายการค้าง และประวัติที่มีจริง หากมีเพียงสถานะล่าสุดให้ระบุว่าประวัติไม่ครบ
5. ตรวจความเชื่อมโยงในฐานจริงแบบอ่านอย่างเดียว เตรียมรายการเปลี่ยนแปลงที่เจาะจงรหัสและช่องข้อมูล พร้อมสำรองและทดสอบการคืนระบบ; ตรวจหยุดช่องเขียนฝ่ายขายเดิมโดยไม่ปิดงานฝ่ายอื่น
6. ทดสอบการนำเข้าทั้งชุด รันซ้ำไม่เกิดข้อมูลซ้ำ ไฟล์เปลี่ยนต้องหยุดทบทวน ไม่เขียนทับเงียบ ๆ แล้วให้ผู้ใช้ตรวจยอดก่อนอนุมัติการแทนที่จริง
7. นำเข้าตามแผนที่อนุมัติ ตรวจยอด/สถานะแปลง/สิทธิ์/งานฝ่ายอื่น แล้วจึงเปิดใช้งาน; ถ้าไม่ผ่าน ไม่เปิดให้เขียนครึ่งชุด

อัปเดต 29 กันยายน 2569: ตรวจสำเนาแท็บ `ข้อมูลลูกค้า` ที่ดาวน์โหลด 28 กันยายนแล้ว ผู้ใช้ยืนยันเบอร์ไม่ทราบ วันที่ A885/B933 ชื่อเต็ม Sales ทั้ง 7 ชื่อโครงการทั้ง 7 คู่ และแปลงที่ต้องทบทวนแล้ว ยืนยัน N001 เป็นคนเดียวกัน ผู้ดูแลส่วนกลาง JEEJEE; N002–N065 แยกคนทุกแถว ผู้ดูแลแต่ละโครงการ/ประวัติยังคงเดิม

ร่าง snapshot ในเครื่องเก็บต้นฉบับ 965 แถว แยกลูกค้า 963 รายการ (รวม 5 รายการไม่มีผู้ดูแลที่พักไว้) ความสนใจรายโครงการ 960 รายการ และประวัติจอง 304 รายการครบ ผู้ใช้ยืนยันพัก 6 แถว 438/439/440/444/680/894 รอ Admin ตรวจ ไม่เปิดเป็น Lead รับงาน; แถว 680 ยังไม่มีลูกค้า candidate เพราะไม่มีชื่อ แถว 171 เก็บประวัติยกเลิกโดยยังไม่ผูกแปลง ดูวิธีตรวจและข้อจำกัดใน `sales-sheet-import-review.md`

อ่านทะเบียนโครงการ/แปลงจริงแล้ว แต่ยังไม่เทียบลูกค้า/รายการขาย/FK ของฝ่ายอื่นกับฐานจริงหรือตรวจ binding บัญชีสด **ร่างนี้ไม่ใช่ manifest พร้อมนำเข้า** ไม่มีรายการลบจริง ไม่มีการทดสอบนำเข้าซ้ำบนฐานข้อมูล และยังต้องตรวจสำเนาล่าสุดก่อน cutover

## ข้อจำกัดของโครงสร้างเดิมที่ต้องแก้ก่อนนำเข้า

Foundation candidate เดิมยังบังคับ `legacy_import` ให้มี `legacy_source_lead_id` อ้างอิง `public.leads` และมีข้อยกเว้นข้อมูลเก่าผูก snapshot ของ Sale เดิม จึง **ยังไม่ใช่ importer ของไฟล์ใหม่** ห้ามลบ Lead เดิมทิ้งเพื่อข้ามข้อจำกัด หรือปลอมรายการ imported เป็น live เพื่อเลี่ยง validation

หลังเห็นไฟล์ต้องเลือกและทบทวน provenance สำหรับชุดเต็ม: stable external key + รุ่นแหล่งข้อมูล + หลักฐานดิบ/วันที่ไม่ทราบ โดยคงกติกาชื่อและเบอร์ของ Lead ที่ Sales กรอกใหม่ตามเดิม ต้องมี migration แยกและทดสอบ ขณะนี้ไม่แก้ foundation หรือคลาย constraint ที่ทดสอบแล้ว

ความคืบหน้า 29 กันยายน: เตรียม private external staging และทดสอบ replay/rollback ในฐานจำลองแล้วตาม `sales-external-snapshot-staging.md` รองรับหลักฐาน/รายการรอ Admin โดยไม่อิง Lead เก่า แต่ยังไม่ใช่ bridge เขียน CRM และไม่มี deployment migration หรือการเปิดระบบจริง

ความคืบหน้ารอบถัดมา: เพิ่มร่าง identity bridge ไปยัง sales_customers/lead_project_interests พร้อม external FK แทน legacy Lead และลิงก์ประวัติจองใน private แล้ว ทดสอบบน exact sealed foundation ผ่าน ดู `sales-external-crm-bridge.md` ไม่ได้แก้ foundation candidate เดิม ไม่เขียน sales/เปลี่ยนแปลงจริง และห้ามเปิด flag จน booking/lifecycle/report รองรับ external history

## ตัวตรวจที่เตรียมในเครื่อง

`scripts/sales-runtime/replacement-snapshot.mjs` เป็น pure function `reviewReplacementSnapshot(snapshot, catalog)` ไม่มีอ่านไฟล์/เชื่อมฐาน/SQL/ลบ/เขียน/เปิด flag และไม่เชื่อมกับหน้าจอรับ Lead ตัวปัจจุบัน

ตรวจข้อมูลที่ **แปลงรูปแบบแล้ว** เท่านั้น ไม่ใช่ Excel parser หรือ payload พร้อม insert ไม่อนุมาน mapping ชื่อคอลัมน์ก่อนเห็นไฟล์

Contract `sales-replacement-source-v1`:

| ส่วน | ช่องข้อมูลที่ต้องส่งให้ตัวตรวจ |
|---|---|
| snapshot | version, mode=`full_snapshot`, sourceRevision, asOfDate, historyCoverage=`full/latest_only/unknown`, declaredCounts ของทั้งสามส่วน |
| customers | sourceKey, name, owner, phone, phoneStatus=`provided/unknown`, status, leadDate |
| interests | sourceKey, customerKey, project, owner, status |
| bookings | sourceKey, interestKey, plotId, stage, bookedDate, transferredDate, cancelledDate, cancelReason, salePrice, depositAmount |
| catalog | projects: ชื่อโครงการ, salesOwners: รหัสผู้ดูแลที่ตรวจแล้ว, plots: `{id, project}` |

วันที่เป็น ค.ศ. `YYYY-MM-DD` หรือ `null` สำหรับวันที่เหตุการณ์ที่ไม่ทราบ ส่วน `asOfDate` ต้องมีวันที่แน่นอน ต้องแปลง พ.ศ./Excel dates/เขตเวลาโดยอิงรูปแบบจริงก่อนตรวจ ไม่ส่งค่าว่างแทน null; ราคาขายกับเงินมัดจำแยกช่อง ไม่อนุมานว่าศูนย์หมายถึงไม่มีข้อมูล

สถานะหลัง mapping ต้องตรงชุดที่โครงสร้างรองรับ: intake new/contacted/following_up/nurture/lost/legacy_unclassified; interest new/contacted/considering/follow_up/nurture/lost; booking booked/contracted/downpayment/document_prep/loan_submitted/loan_rejected/loan_approved/transfer_pending/transferred/handover/cancelled. การจับคู่ป้ายเดิมเป็นสถานะเหล่านี้ยังต้องตรวจหลักฐาน ไม่เลือกอัตโนมัติจากช่องเงินหรือวันที่เดียว

รายงานส่งกลับเฉพาะรหัสข้อผิดพลาด/คำเตือนและลำดับแถวในแต่ละส่วน พร้อมจำนวนแถว ไม่ส่งชื่อ เบอร์ ราคา หรือรหัสบัญชี ไม่แก้ข้อมูลที่รับเข้า

- บล็อกชุดว่าง, mode ผิด, จำนวนที่ประกาศไม่ตรง, รหัสซ้ำ/ขาด, เจ้าของไม่อยู่ในทะเบียน, reference ขาด, สถานะไม่รู้จัก, วันผิด/หลังวัน snapshot, เงินผิด, เหตุการณ์ขัดสถานะ และจองซ้อนแปลงเดียวกัน
- cancelled ไม่ครองแปลง ส่วน loan_rejected ยังครองจนมีการยกเลิกชัดเจน; transferred/handover ไม่กลายเป็นแปลงว่าง
- เตือนเบอร์/วัน/เงินไม่ทราบ ประวัติไม่ครบ และเบอร์ร่วมกัน แต่ไม่รวมลูกค้า ไม่สร้างประวัติหรือศูนย์แทนข้อมูลขาด
- เบอร์แทนตรวจจับได้เพียงรูปแบบเลขซ้ำชัดเจน ไม่สามารถยืนยันทุกเบอร์ว่าเป็นเบอร์จริง ต้องตรวจจากต้นฉบับ
- `canProceedToMappingReview=true` แปลว่า **ผ่านรูปแบบเบื้องต้นเท่านั้น** ไม่พิสูจน์ความครบถ้วนของไฟล์หรือทะเบียนสิทธิ์ ค่า `importReady`, `deletionAuthorized`, `productionChanged` เป็น false เสมอ จำนวนที่ประกาศและ historyCoverage เป็นข้อมูลที่ผู้เตรียมส่งมา ไม่ใช่หลักฐานอิสระ
- ก่อนนำเข้าจริงยังต้องตรวจ FK ของทุกฝ่าย, การจับคู่ฐานเดิม, ประวัติรายการต่อเนื่อง, การคำนวณเงินและ KPI, บัญชีที่ยังใช้งาน, file hash/replay protection และรายการเปลี่ยนแปลงที่อนุมัติ

## ผลรอบตัวตรวจเริ่มต้น (ก่อนรับสำเนาชีต)

เพิ่มตัวตรวจและชุดทดสอบจากข้อมูลจำลอง พร้อมปรับเอกสารเส้นทางล่าสุด ผล Vitest ผ่าน 103/103 ข้อจาก replacement-snapshot, crm-foundation-candidate และ central-roster รวม 3 ไฟล์; ESLint ของตัวตรวจและ test ใหม่ผ่าน ไม่ใช่การทดสอบนำเข้า/ลบบนฐานจริง

ไม่อ่านลูกค้าจริง ไม่เปลี่ยน Supabase ไม่ลบข้อมูล ไม่ Deploy และไม่เปิดหน้า Lead จริง ไม่แก้ SQL candidate หรือกติกาสิทธิ์เดิม
