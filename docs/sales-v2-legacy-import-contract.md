# ข้อตกลงนำเข้าข้อมูลฝ่ายขายเก่า — ยืนยัน 15 กันยายน 2569

สถานะ: ปรับแบบข้อมูลและหน้า Lead ส่วนกลางในเครื่องแล้ว ยังไม่ได้ย้ายข้อมูล เปิด V2 เปลี่ยนบัญชีพนักงาน หรือรัน SQL บน Supabase
เอกสารนี้ต่อจากผลตรวจ 01–03 ที่ผู้ใช้รันเอง ไม่ต้องรันรายงานเดิมซ้ำหรือรัน SQL เพิ่มตอนนี้

## 1. คำยืนยันที่ใช้เป็นข้อกำหนด

- Lead เดิม 895 แถวเป็นข้อมูลจริงเก่า แต่เบอร์โทรเป็นค่าที่ใส่แทน ไม่ใช่หลักฐานว่าลูกค้าทั้งหมดเป็นคนเดียวกัน
- ชื่อ Sales เดิม `TAEW` และบัญชี Auth ที่แสดง `TEAW` เป็นคนเดียวกัน ให้ใช้ชื่อแสดงผล `TAEW`
- ข้อมูลเก่าส่วนที่ไม่มีหลักฐานให้เก็บเป็น “ไม่ทราบ” ไม่เติมศูนย์ วันปัจจุบัน เหตุผล หรือประวัติขึ้นเอง
- ข้อยกเว้นนี้ใช้กับการนำเข้าประวัติเก่าที่มีที่มาเท่านั้น การรับ Lead ใหม่ยังต้องมีชื่อและเบอร์ โดย Sales ผู้บันทึกเป็นผู้ดูแลตามกติกาเดิม

## 2. วิธีเก็บโดยไม่รวมผิดคนหรือทับต้นฉบับ

1. เตรียมรายการรหัส Lead ครบทั้งชุดและผูกกับรุ่นการนำเข้า ก่อนแปลงค่าใด ๆ ต้องเก็บข้อมูลดิบของ Lead/Sale ในพื้นที่ประวัติส่วนตัว พร้อมรหัสเดิมและเวลาเก็บ
2. ตั้งต้นหนึ่งลูกค้ากลางต่อหนึ่ง legacy Lead ID: เป้าหมาย 895 รายการสำหรับ snapshot นี้ ไม่รวมจากเบอร์แทนค่า หรือจากชื่อสะกดเหมือนกัน ตัวเลข 809 ชื่อสะกดต่างกันในรายงานไม่ใช่จำนวนคนที่พิสูจน์แล้ว
3. เก็บ `legacy_source_lead_id` และตารางเชื่อมรหัสเดิมเพื่อไม่ให้นำเข้าซ้ำ การรวมคนภายหลังต้องให้ Admin ยืนยันพร้อมเหตุผล โดยไม่ทิ้งรหัสเดิม รายการขาย หรือประวัติ
4. เบอร์ที่เป็นค่าแทนเก็บในหลักฐานดิบเท่านั้น ส่วนเบอร์ใช้งานเป็น `NULL`, `phone_data_status=unknown_legacy`, `record_origin=legacy_import` หน้าใหม่แสดง “ไม่ทราบ (ข้อมูลเก่า)” ไม่ใช้ค่าแทนค้นหา/รวมลูกค้าซ้ำหลังย้ายแล้ว
5. เก็บ Sale เดิม 289 รหัส ไม่สร้างการจองใหม่จากความสนใจ และตรวจให้แปลงเดิม 306 รหัสกับสิทธิ์ครองแปลงไม่เปลี่ยนเพราะการย้ายระบบ
6. แถวที่ยังไม่มีเจ้าของซึ่งตรวจบัญชีและสิทธิ์แล้วอยู่ในรายการรอตรวจ ไม่สุ่ม UUID หรือใช้ผู้รันแทนเจ้าของ และต้องเห็นจำนวนค้างในรายงานตรวจรับ

ผล 03 มีรายการเบอร์ตัวอย่าง 20 แถวและรายการขายตัวอย่าง 50 แถว ซึ่งถูกตัดตามขีดจำกัด จึงยังใช้เป็นรายการรหัสครบชุดสำหรับเขียนข้อมูลไม่ได้
หากมีงานเพิ่มหลังเวลารายงาน ต้องแยกข้อมูลใหม่และตรวจยอด ณ ตอนหยุดเขียนเพื่อย้ายจริง ไม่ใช้คำสั่งเหมารวมทุกแถวที่มีในวันนั้น

## 3. เงิน วันที่ และสถานะ

| ข้อมูล | แนวทางแปลงที่กำหนด |
|---|---|
| ราคาขายบ้าน | ตามข้อตกลง “มูลค่าจอง” คือราคาขายบ้าน ผลตรวจมีราคาที่ไม่ว่าง 280 รายการ ให้คงเป็นยอดที่บันทึกไว้ในข้อมูลเก่า ส่วน 9 รายการที่ไม่มีราคาเป็นไม่ทราบ ไม่ถือว่าราคาที่บันทึกคือเงินรับจริง |
| เงินจอง/มัดจำ | ข้อมูล sales เก็บศูนย์ทั้ง 289 รายการ แต่ไม่มีหลักฐานรับเงินที่ยืนยันจากรายงาน จึงเก็บยอดใช้งานเป็นไม่ทราบสำหรับรายการที่ไม่มีหลักฐาน โดยคงศูนย์ดิบไว้ ไม่ล้างศูนย์จริงของรายการอื่นหรือเดายอด 10,000/50,000 บาท |
| วันที่จอง | ไม่พบ lead.booking_date ของ Sale ทั้ง 289 รายการ เก็บไม่ทราบจนมีหลักฐาน ไม่ใช้วันสร้างแถวหรือวันโอนแทน |
| วันที่เป็น Lead / ติดต่อ / เหตุการณ์อื่น | เก็บค่าดิบเสมอ ใช้เป็นวันจริงเมื่อมีหลักฐานเท่านั้น หากพิสูจน์ไม่ได้ให้วันที่ใช้งานเป็น NULL ตัวอย่าง 20 แถวมี lead_date เดียวกัน แต่ยังสรุปไม่ได้ว่าทั้ง 895 แถวเหมือนกัน |
| สถานะกลาง | crm_status เดิมเป็น Follow-up ทั้ง 895 แถว จึงไม่คัดลอกเป็นหลักฐานการติดตามครบทุกคน ให้ใช้ legacy_unclassified จนมีการจัดสถานะจากหลักฐาน เก็บชื่อสถานะเดิมไว้ตรวจย้อนหลัง |
| จอง/โอน/ยกเลิกเดิม | รักษา sale ID และสถานะที่เก็บเดิมไว้ แยกการจับคู่แบบตรงค่า ไม่บันทึกเป็นธุรกรรมใหม่หรือเปลี่ยนสิทธิ์ครองแปลงระหว่างย้าย ถ้าขาดวันหรือเหตุผลให้ไม่ทราบพร้อมที่มาของการย้าย |
| เหตุผลยกเลิกเก่า | ไม่แต่งว่า “กู้ไม่ผ่าน” หรือเหตุผลลูกค้าอื่นขึ้นเอง ร่างอนุญาตเหตุผล/วันไม่ทราบเฉพาะ Sale รหัสเดียวกันที่ต้นฉบับยืนยันว่า Cancelled อยู่แล้วก่อนย้าย การยกเลิกภายหลังแม้เป็นรายการจองเก่าก็ยังบังคับวัน หมวด และเหตุผล |
| Visit / Customer Voices | มี lead.status=Visit 606 แถว แต่ actual_visit_date และ Customer Voices ที่ตรวจเป็น 0 จึงเก็บป้ายสถานะเก่า ไม่สร้าง Visit completed หรือแบบสอบถามย้อนหลัง Visit ใหม่สำเร็จเมื่อส่งแบบของครั้งนั้นครบ |
| สินเชื่อ | sales.bank_status เป็น Pending ทั้งหมด ไม่อนุมานว่ากู้ผ่านจากสถานะโอน และไม่สร้างประวัติยื่นกู้/ถูกปฏิเสธย้อนหลัง |

ยอดรวมราคาที่เก็บในรายงานไม่ใช่ยอดเงินเข้าบริษัทหรือยอดที่ผ่านการตรวจเอกสารแล้ว รายงานใหม่ต้องแยกยอดทราบ/จำนวนรายการไม่ทราบ ไม่แสดงยอดไม่ทราบเป็นศูนย์
การแปลงเงินจริงและสถานะยังต้องทำใน backfill ที่ตรวจแยกต่างหาก รอบนี้มีเพียงข้อกำหนดและร่าง ไม่ได้ UPDATE ข้อมูลเหล่านี้

## 4. ผู้ดูแล TAEW และสิทธิ์

Mapping ที่ผู้ใช้ยืนยัน: `TAEW → 9c1d670a-1d2a-4996-959c-33c243fd34d8` ซึ่งเป็นบัญชีเดิมที่ผลตรวจแสดงชื่อ `TEAW` (เกี่ยวข้องกับ Lead เดิม 10 รายการ)
ใช้ชื่อแสดงผล TAEW ในทะเบียนผู้ดูแล V2 ไม่สร้างบัญชีใหม่ ไม่เปลี่ยน UUID ไม่แก้ชื่อเข้าสู่ระบบหรือ metadata ของ Auth ในรอบนี้
Admin ยังต้องตรวจว่าบัญชีใช้งานอยู่และมีบทบาท Sales ก่อนติดตั้งทะเบียนสิทธิ์จริง เช่นเดียวกับอีก 6 ชื่อที่ตรงจากรายงาน; metadata ไม่ใช่หลักฐานให้สิทธิ์อัตโนมัติ
ชื่อผู้ทำรายการ/ผู้ปิดการขายเดิมคงเป็นประวัติแยกจากเจ้าของปัจจุบัน ไม่ย้ายเครดิตยอดขายย้อนหลังเมื่อเปลี่ยนผู้ดูแล

## 5. KPI และงานติดตาม

- รายการที่ไม่ทราบวันที่ Lead อยู่ในกลุ่ม “ไม่ทราบวันที่ (ข้อมูลเก่า)” ไม่โยนเข้ายอด Lead ของวันนำเข้า และไม่ตัดออกจากจำนวนรายการทั้งหมดโดยเงียบ ๆ
- ไม่สร้าง SLA ติดต่อครั้งแรกย้อนหลังให้ 895 รายการ การเริ่มติดตามใหม่ใช้กิจกรรม/การมอบหมายที่เกิดจริงตามกติกาเวร ไม่เปลี่ยนวัน Lead เดิม
- หนึ่งลูกค้าต่อ legacy ID เป็นจำนวนระเบียนที่รักษาไว้ชั่วคราว ไม่ใช่การรับรอง 895 คนไม่ซ้ำ ต้องติดป้ายกลุ่มข้อมูลเก่าที่ยังไม่ยืนยันตัวบุคคลใน KPI จน Admin ตรวจการรวมคน
- ไม่สร้าง Visit/วันจอง/ผลกู้ปลอมเพื่อให้ funnel ดูครบ และไม่ตัดรายการโอน/ยกเลิกเดิมทิ้งเพราะขาดประวัติก่อนหน้า

## 6. สิ่งที่เตรียมแล้วและงานถัดไป

เตรียมในเครื่อง: ร่าง customer provenance/เบอร์ไม่ทราบและพื้นที่เก็บต้นฉบับส่วนตัว, หน้า/API ส่วนกลางอ่านเบอร์ NULL ได้, การรับ Lead ใหม่ยังปฏิเสธเบอร์ว่างและไม่รับ flag สำหรับนำเข้าจากฟอร์มทั่วไป
ร่าง SQL ยังมีตัวหยุดการรันและ ROLLBACK ทั้งแอปและ DB write switch ยังคงปิดเป็นค่าเริ่มต้น ไม่มีการย้ายข้อมูลหรือเปลี่ยนหน้าจอเก่าให้รองรับการนำเข้าชุดนี้แล้วโดยอัตโนมัติ

ลำดับงานที่ยังต้องทำก่อนให้ผู้ใช้รัน SQL:

1. เตรียม foundation/backfill ที่ตรงรุ่นฐานจริง พร้อมรายการรหัสครบชุด, mapping ที่ Admin ยืนยัน, snapshot ก่อนแปลง, ตรวจนำเข้าซ้ำ/ความขัดแย้ง และรายงานเทียบยอด/รายการไม่ทราบ/รายการค้าง
2. ออกแบบ cutover สิทธิ์และทุกช่องทางเขียนเดิมพร้อมกัน ผล 03 พบ `public.users` เปิดสิทธิ์กว้างด้วย นอกจาก plots/projects; ต้องตรวจผลกระทบต่อฝ่ายก่อสร้างและทุกบทบาทก่อนเปลี่ยน ไม่ถือว่าพบการรั่วไหลแล้วจากรายงานการตั้งค่าเพียงอย่างเดียว
3. สำรองและทดลองกู้คืน/ย้ายบนฐานแยก ตรวจ RLS ทุกบทบาท การจองชนกัน และความครบถ้วน 895 Lead IDs / 289 Sale IDs / 306 plots ตาม baseline ที่ปรับเป็นปัจจุบัน
4. ส่ง SQL ติดตั้งที่ผ่านการทบทวนแยกจากร่างให้ผู้ใช้ตรวจและรันเองเมื่อพร้อม ไม่เปิด V2 หรือ importer เก่าเขียนซ้อนระหว่างย้าย

ยังไม่มี import writer หรือ SQL deployment ที่พร้อมรัน การทดสอบหน้า/API ใช้ข้อมูลจำลอง และการทดสอบร่างเป็น static checks ไม่ใช่การรัน PostgreSQL/RLS จริง
