# ป้องกันคำสั่งจัดการบัญชี — ขั้น 1 (เตรียมในเครื่องเท่านั้น)

วันที่: 25 กันยายน 2569

งานต่อเนื่อง: [ขั้น 2a แยกรายชื่อหน้าล็อกอิน](./account-security-login-directory.md) เตรียม frontend และร่างสิทธิ์รายคอลัมน์แล้วในเครื่อง รายละเอียดและผลรอบล่าสุดอยู่ในเอกสารนั้น ยังไม่ติดตั้งฐานจริง

## สถานะและขอบเขต

ผู้ใช้ให้ทำขั้นต่อไป โดยคง **เลือกรายชื่อ → กรอก PIN → เข้าสู่ระบบ** และยังห้ามเปลี่ยน Supabase จริง
รอบนี้เพิ่มร่างการจำกัดสิทธิ์จัดการบัญชี พร้อมทดสอบ PostgreSQL ในเครื่องด้วยข้อมูลสมมติเท่านั้น
ไม่ได้เปลี่ยนหน้า Login, PIN, บัญชีจริง, environment, feature flags หรือ deploy
มีการอ่านเฉพาะชื่อ/ชนิดคอลัมน์ `auth.users`, `auth.sessions`, `public.users` เพื่อยืนยันโครงสร้าง ไม่อ่านแถวข้อมูลผู้ใช้หรือลูกค้า

**ระบบจริงยังไม่ได้รับการแก้ช่องโหว่จากงานชุดนี้**
ไฟล์ `sql/security/account_admin_guard_draft.sql` เป็น DESIGN ONLY มีคำสั่งหยุดตั้งแต่ต้นและ ROLLBACK ตอนท้าย
ห้ามนำไปรันใน Supabase, ห้ามถอดตัวหยุดเพื่อเปิดใช้ และไม่ใช่ migration ที่พร้อมติดตั้ง

## สิ่งที่ร่างนี้ทำ

1. คงชื่อและพารามิเตอร์ RPC เดิมทั้ง 4 คำสั่ง: เพิ่มบัญชี, ลบบัญชี, เปลี่ยนชื่อ, เปลี่ยน PIN
2. ย้ายตัวทำงานเดิมเข้า schema ที่ไม่เปิดผ่าน Data API และถอนสิทธิ์เรียกโดยตรง; ตัวเดิมเปลี่ยนเป็น SECURITY INVOKER
3. หน้าเรียกสาธารณะเป็น SECURITY INVOKER ส่วนตัวจัดการที่ใช้สิทธิ์สูงอยู่ใน schema ภายในและตรวจทุกครั้งว่า:
   - เป็นบัญชีที่ผ่านการยืนยันและมีรายการ Admin ที่ตรวจรับรองแล้วตาม Auth UUID
   - บัญชีไม่ถูกระงับ/ลบ และไม่ใช่ Supabase anonymous-sign-in
   - session ตรงกับบัญชี ยังมีอยู่ และยังไม่เกิน `not_after` หากกำหนดไว้
   - ไม่ใช้ชื่อที่เลือก, `public.users.role`, `user_metadata` หรือป้ายบทบาทใน JWT เป็นหลักฐานสิทธิ์
4. ปิดการเพิ่ม/แก้/ลบ/ล้างตาราง `public.users` ตรงจาก client ทั้งระดับตารางและคอลัมน์ พร้อม restrictive RLS สำหรับ insert/update/delete เพื่อคร่อม policy เดิมที่เปิดกว้าง
5. ตรวจหลังติดตั้งใน transaction ว่าไม่มีสิทธิ์เขียน/เรียกตัวเดิมหลงเหลือจากสิทธิ์ที่สืบทอดมา; หากพบให้ยกเลิกทั้งชุด
6. **ยังคงสิทธิ์ SELECT เดิมชั่วคราว** เพื่อไม่ทำให้ dropdown หาย ก่อนแยกช่องอ่านรายชื่อในขั้น 2

การตรวจ session นี้ไม่แทนระบบตรวจ JWT ของ Supabase และไม่อ้างว่าตรวจนโยบาย inactivity/single-session ได้ครบก่อนรอบ refresh ของ Auth
การแก้สิทธิ์นี้ไม่ยกเลิกหรือเปลี่ยน PIN เดิม และไม่ถือว่าการใช้ PIN 4 หลักปลอดภัยเพียงพอแล้ว

## การยืนยัน Admin และป้องกันล็อกตัวเองออก

- `account_security_private.reviewed_admins` เป็นรายการผู้มีสิทธิ์ **จัดการบัญชี** ไม่ใช่ตารางแทนบทบาททั้งแอป และไม่ใช่การย้าย role map ของ Sales V2
- ผูก Auth UUID กับรหัสผู้ใช้เดิมที่ตรวจแล้ว, ค่าเริ่มต้น disabled, มีหลักฐานการตรวจ; ไม่อนุญาต client อ่านหรือแก้ตารางนี้
- ไม่มีการคัดลอกบัญชีที่ติดป้าย Admin เข้ารายการอัตโนมัติ เพราะข้อมูลบทบาทเดิมยังเชื่อเป็นหลักฐานไม่ได้
- ในร่างที่ยังไม่ใส่รายการรับรอง **ทุกคนจะจัดการบัญชีไม่ได้** จึงห้ามใช้จริงก่อนจัดชุด bootstrap ที่ผู้ใช้ตรวจรับรอง และทดสอบทางกู้คืนผ่านผู้ดูแล Supabase
- การสร้างบัญชีด้วยบทบาท `Admin` ผ่านตัวเก่า **ยังไม่ให้สิทธิ์จัดการบัญชีนี้อัตโนมัติ** ต้องมีขั้นรับรองต่างหากก่อนใช้งาน; ต้องออกแบบข้อความ/ขั้นตอนในหน้าจัดการบัญชีก่อน cutover
- FK แบบ RESTRICT ป้องกันการลบบัญชีที่อยู่ในรายการรับรองผ่านคำสั่งเก่า รวม Admin คนสุดท้าย; การปิดบัญชี/ถอดผู้ดูแลต้องทำขั้นตอนเฉพาะ ไม่ถอดข้อจำกัดเพื่อให้ทดสอบผ่าน
- หากย้าย schema แล้วมี function/trigger/view อื่นเรียกตัวเดิมด้วยชื่อหรือ OID ต้องตรวจและแก้จุดเรียกก่อน deploy ร่างนี้ไม่รับรอง compatibility ของ caller ทั้งฐานจริง

## การทดสอบในเครื่อง

ใช้ตัวทดสอบฐานจำลองเดิม เพิ่มโหมดเฉพาะบัญชีซึ่งไม่โหลด migration ฝ่ายขาย:

```powershell
node node_modules/vitest/vitest.mjs run scripts/sales-runtime/account-security.test.js scripts/sales-runtime/safety.test.js --maxWorkers=1
node scripts/sales-runtime/run.mjs --account-security-only
```

ตัวทดสอบสร้าง PostgreSQL cluster ใหม่, database/user/password/port สุ่ม, ฟังเฉพาะ loopback และตรวจ data directory ว่าเป็นของรอบนั้นก่อนส่ง SQL
ไม่อ่าน `.env`, ไม่รับ URL/ชื่อฐานที่มีอยู่, ไม่รับ Supabase key และไม่เชื่อมฐานจริง
ใช้ตัวทำงานเดิมจากไฟล์ SQL ใน repository เฉพาะนิยาม 4 ฟังก์ชัน ไม่รันคำสั่งย้ายข้อมูล/ลบ trigger ที่อยู่ในสคริปต์เก่า
ตัวหยุดในร่างถูกถอดเฉพาะในหน่วยความจำของตัวทดสอบ; ตรวจ hash ว่าไฟล์ต้นฉบับไม่เปลี่ยน และปิด process ฐานจำลองที่สร้างเมื่อจบหรือเกิดข้อผิดพลาด

ครอบคลุม:

- คนไม่ล็อกอิน, Sales, Owner, Foreman และป้าย Admin ปลอมเรียกทั้ง 4 คำสั่งไม่ได้
- ป้าย Admin เก่าที่ไม่ได้ตรวจรับรองยังถูกปฏิเสธ
- session หาย/ผิดบัญชี/หมดอายุ/ถูกลบ และ Admin ที่ถูกปิดสิทธิ์/ระงับ/ลบบัญชี ถูกปฏิเสธ
- อ่านหรือเขียนรายการ Admin รับรองไม่ได้, เรียกตัวเก่าโดยตรงไม่ได้, เขียนตารางผู้ใช้ตรงไม่ได้
- restrictive RLS ยังกัน insert/update/delete เมื่อจำลองการ grant สิทธิ์กลับโดยผิดพลาด
- SELECT สำหรับ dropdown ยังใช้ได้
- Admin สมมติที่รับรองแล้วเพิ่ม เปลี่ยน PIN เปลี่ยนชื่อ และลบบัญชีทั่วไปได้; การเปลี่ยนชื่ออัปเดต reference ก่อสร้างตามตัวเก่า
- คำสั่งที่ล้มเหลวหลังเริ่มเขียน Auth ต้อง rollback ไม่ทิ้งบัญชีครึ่งเดียว
- ร่างดิบรันไม่ผ่าน และการลงทับ schema เดิมถูกหยุด

ผลทดสอบจริงให้ดูหัวข้อผลล่าสุดด้านล่าง ไม่ใช้รายการข้างบนแทนผลผ่าน
ชุดนี้ไม่จำลอง GoTrue/PostgREST/JWT signature, Auth API login, production triggers, หรือ role/permission ทั้งแอป

## สิ่งที่ยังต้องทำก่อนเปิดจริง

1. ขั้น 2: แยกช่องอ่านชื่อสำหรับก่อนล็อกอินออกจากข้อมูลบัญชีภายใน แล้วเลิกอ่าน `users.*` ก่อน login; คง dropdown โดยส่งเฉพาะชื่อที่จำเป็น ไม่ส่งบทบาท/ออนไลน์
2. เปลี่ยนแหล่งตรวจบทบาทหลังล็อกอินและตอนคืน session ให้เชื่อถือได้ ครอบคลุม Sales และทุกฝ่ายก่อสร้าง; ไม่ใช้ user-editable metadata
3. ปิด `update_user_last_seen(p_username)` ที่อัปเดตชื่อใครก็ได้ ให้ผูกกับผู้เรียกจริง; ไม่รวมอยู่ในร่าง 4 คำสั่งนี้
4. ย้ายการเพิ่ม/ลบ Foreman ที่ปัจจุบันทำก่อน RPC ให้เป็นงานที่ตรวจสิทธิ์และสำเร็จ/ล้มเหลวร่วมกัน; การทดสอบเฉพาะฟังก์ชันไม่รับรองลำดับหน้าจอเดิม
5. ตรวจ public function/trigger/view อื่นที่เขียนบัญชีและ Auth, สิทธิ์กว้างของ projects/plots และข้อมูลฝ่ายขาย, ตัวอัปเดต metadata และ SQL เก่าที่อาจเปิดช่องเดิมกลับมา
6. ตรวจความเข้ากันได้ของการเขียนตาราง Auth เดิมกับ Supabase Auth API, นโยบายรหัสเริ่มต้น/การจำกัดเดารหัส/การกู้บัญชี; การห่อสิทธิ์ไม่ได้รับรองวิธีแก้ Auth ภายในเดิม
7. ทดสอบกับ Supabase แยกจริงด้วยบัญชีสมมติและทุกบทบาท รวม logout/relogin/refresh/revoke; ฐานใช้งานจริงที่มีข้อมูลทดสอบไม่ถือว่าแยก
8. เตรียม migration และ cutover/กู้คืนที่รักษาการปิดช่องโหว่ ไม่ใช้ rollback โดยคืน PUBLIC EXECUTE หรือเปิดตารางผู้ใช้ให้เขียน; ขออนุมัติแยกก่อนใช้ฐานจริง
