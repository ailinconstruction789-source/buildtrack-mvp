## ข้อตกลงที่ยืนยัน

- ใช้หน้าตา Lead Tracker เดิมเป็นหน้ากลางทุกโครงการ ไม่ทำทะเบียนลูกค้าอีกชุด
- มีชื่อและเบอร์ก็สร้าง Lead ได้ ไม่บังคับโครงการ; สนใจหลายโครงการได้
- Sales ผู้บันทึกเป็นผู้ดูแลเริ่มต้น; เจ้าของ/สถานะของแต่ละความสนใจแยกกันได้
- Sales ทุกคนเห็นทุกโครงการ; แก้ได้เฉพาะเจ้าของขอบเขตนั้นกับ Admin
- รับเข้า → ติดตาม → นัด → Visit/Customer Voices อยู่ส่วนกลางตลอด ไม่มีหน้า Lead แยกในโครงการหลัง cutover
- เมื่อจองจึงเชื่อม customer เดิม → interest ของโครงการ → sale ของแปลงนั้นในหน้าลูกค้าจอง ไม่ย้ายหรือลบ customer
- ลูกค้าที่มาจองเลย: ค้นและเลือกลูกค้าเดิมก่อน; ถ้าไม่มี ให้สร้าง Lead พร้อมการจองในคำสั่งเดียว ไม่กรอกลูกค้าซ้ำ
- ยกเลิกจอง: เก็บ sale เดิมในสถานะ cancelled พร้อมราคา แปลง วัน เหตุผล ผู้ทำ และประวัติเดิม
- Sales กด “กลับมาติดตามต่อ” เอง พร้อมเหตุผลและงานถัดไป ไม่เปิดกลับอัตโนมัติ ไม่เปลี่ยน cancelled เป็น booked
- จองใหม่ใช้ sale ID และ booking round ใหม่ เชื่อม previous_sale_id เมื่อเป็นการจองต่อจากรอบที่ยกเลิก
- จองหลายแปลง/หลายรอบได้ ไม่ใช้หนึ่งสถานะรวมทับทุก sale; การติดตามใหม่ไม่ยกเลิก sale อื่น
- ไม่เพิ่มระบบอนุมัติส่วนลด; Sales ใส่ส่วนลดตอนจองตามข้อตกลงล่าสุด
- ข้อมูลเก่าไม่มีหลักฐานเก็บ “ไม่ทราบ”; ไม่รวมคนอัตโนมัติจากชื่อหรือเบอร์ โดยเฉพาะ 895 รายการเบอร์แทน

## ทำแล้วในเครื่องรอบนี้

1. แยกหัวตารางและตาราง Lead Tracker เป็นส่วนหน้าตาร่วม ใช้ทั้งหน้าปัจจุบันและหน้าส่วนกลางที่เตรียมไว้ ไม่คัดลอกตัวบันทึก legacy มาใช้กับ V2
2. `/sales-crm` แสดงลูกค้าทุกคนในหน้าที่โหลดตั้งแต่เริ่ม ไม่ซ่อนคนที่มี workspace_state=project_active (ธงเดิมอาจมาจาก Visit ไม่ใช่หลักฐานจอง)
3. หนึ่งแถวต่อ customer ID พร้อมหลายความสนใจ ผู้ดูแล/สถานะรายโครงการ แปลงที่เล็ง และลิงก์งานติดตามในส่วนกลาง
4. เพิ่มตัวกรองโครงการ ช่องทาง Sales สถานะ และยังไม่ระบุโครงการ; โครงการ+Sales+สถานะต้องตรงในความสนใจเดียวกัน ไม่จับข้อมูลข้ามโครงการ
5. คงแบบรับ Lead/แปลงว่าง/idempotent intake เดิมของ V2 คงสิทธิ์และสวิตช์ปิดเดิม ไม่เพิ่ม write ทางลัด
6. ปรับกติกา pure function: Visit ไม่เปิดพื้นที่ Lead ในโครงการ; การกลับมาติดตามต้องอ้าง sale ที่ cancelled ใน interest เดียวกัน มีเหตุผล และคืนเฉพาะแผนแก้ interest กับ audit ไม่คืนคำสั่งแก้ sale/customer

ข้อจำกัดปัจจุบัน: ค้นหาและตัวกรองใช้ข้อมูลหน้าที่โหลด (50 รายการ) โดยบอกขอบเขตบนหน้าจอ ยังไม่ใช่ค้นหาทั้งฐาน; ไม่มีปุ่มจอง/กลับมาติดตามที่บันทึกจริงในหน้าส่วนกลางนี้ ไม่มีการแสดงยอดจอง/จำนวน Visit สมมติจากธงเดิม

## ยังต้องทำก่อนใช้แทนหน้าเดิม

### เชื่อมการจองและประวัติแบบถาวร

- เพิ่มคำสั่งฝั่งเซิร์ฟเวอร์/ร่าง SQL ที่ตรวจตัวตนและเจ้าของจากฐานจริง ไม่เชื่อ role/owner จาก browser
- ค้นลูกค้าเดิมทั้งทะเบียนแบบแบ่งหน้าและป้องกันผลเก่าข้ามคำค้น ก่อนเสนอสร้างลูกค้าใหม่
- จองด้วย customer เดิม หรือสร้าง customer+interest+sale ใหม่พร้อมกันใน transaction เดียว มี idempotency และล็อกแปลงก่อนตรวจว่างซ้ำ
- คำนวณ booking round ภายใต้ lock; เก็บข้อมูลราคา/ส่วนลด/เงินจองแยกกันตามแบบข้อมูลเดิม
- ยกเลิกและคืนสต็อกตาม sale/แปลงที่ถูกต้อง พร้อม audit; เก็บ cancelled sale ไว้ อ่านประวัติทุก round ไม่ใช้ find/maybeSingle จาก lead_id
- คำสั่งกลับมาติดตามต้องล็อก interest/sale ตรวจสิทธิ์และเหตุผล สร้างงานถัดไป+audit ด้วยเวลาเซิร์ฟเวอร์ และกัน retry ซ้ำ ห้ามแก้หลักฐาน cancellation เดิม
- ต่อหน้าจองและหน้าประวัติจริง แล้วทดสอบจองซ้ำ คำขอขาดการตอบกลับ แปลงชนกัน ยกเลิกหนึ่งในหลายแปลง จองใหม่ และการอ่านข้ามสิทธิ์

### ตรวจและเปลี่ยนทางเข้าเมื่อพร้อม

- ตรวจ SQL base/ส่วน lifecycle/trigger เดิมที่ยังยอมให้ Visit ตั้ง project_active และกฎ resume ทั่วไปก่อนรวม migration; รอบนี้แก้ pure rule เท่านั้น ไม่ได้แก้ schema หรือติดตั้ง enforcement ใหม่
- เปลี่ยน SalesKanban ที่ยังดึง lead เฉพาะ project และดึง sale แรก ให้หน้าจองอ่าน sale ตามโครงการ/แปลงพร้อมทุก round
- เปลี่ยนปุ่ม Lead Tracker และปุ่มจองจากแผนผังที่ยังเปิดแท็บ lead_tracker ไปหน้ากลาง/เลือก customer เดิม
- ถอดแท็บ Lead ภายในโครงการเฉพาะเมื่อจุดเชื่อมพร้อม ไม่ถอดตอนนี้จนระบบปัจจุบันไม่มีทางรับลูกค้า
- ตรวจทุก direct writer ที่เกี่ยวข้อง (LeadTracker, Kanban, Visit, Voices, Checklist, Import), RLS และการย้าย 895 รายการก่อนเปิด V2; ไม่ให้ legacy กับ V2 เขียนแข่งกัน
- ทดสอบรวมด้วยข้อมูลสมมติและตรวจ migration ให้ผู้ใช้รันเอง หลังได้รับอนุมัติติดตั้ง/เปิดใช้แยก

## ขอบเขตความปลอดภัยและผลตรวจ

รอบนี้ไม่อ่านรายชื่อลูกค้าจริง ไม่เชื่อม Supabase ไม่รัน SQL/RPC ไม่แก้ SQL/env/สวิตช์ ไม่ Deploy และไม่ย้าย/ลบ/แก้ข้อมูลจริง ระบบเดิมยังอยู่ระหว่างเตรียม cutover ไม่ถือว่ากระบวนการจองใหม่ทำงานครบแล้ว

ผลตรวจสุดท้าย: unit/component 124 กรณีผ่าน (6 ไฟล์: CentralLeadsView, CentralLeadForm, LeadTrackerCompatibility, QueueMonitorEntry, centralTracker, workflow), TypeScript และ lint เฉพาะไฟล์ V2 ที่แก้ผ่าน ใช้ mock เท่านั้น ไม่ได้ทดสอบฐานจริงหรือรับรอง production build; ปัญหา build เดิมเรื่อง next/font ยังอยู่นอกขอบเขตรอบนี้
