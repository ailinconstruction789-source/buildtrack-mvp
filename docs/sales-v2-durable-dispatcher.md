# ตัวเรียก First-contact SLA ที่กู้คำขอเดิมได้

วันที่ 18 กันยายน 2569 — ขั้นต่อจาก system worker13 เป็น **ร่างในเครื่องและฐานทดสอบสมมติเท่านั้น** ไม่มีการเชื่อมต่อ Supabase, ติดตั้ง Cron/extension/job, สร้างบัญชีจริง, ตั้งค่า env หรือ Deploy ผู้ใช้ยังไม่ต้องรัน SQL

## ผลที่เพิ่ม

[SQL14](D:/buildtrack/buildtrack-mvp-main/sql/sales/14_first_contact_dispatcher_draft.sql) เพิ่มตัวเรียกสองช่วง: จองคำขอและบันทึกให้ถาวรก่อน จากนั้นจึงสั่ง worker13 โดยใช้ UUID เดิม เมื่อการตอบกลับขาดหายสามารถอ่านสถานะที่เก็บในฐานได้ ไม่ต้องพึ่งข้อมูลในแท็บหรือหน่วยความจำของตัวเรียก

```text
prepare → บันทึก requestId + attemptId → COMMIT
                                              ↓
execute → ตรวจรหัส/สิทธิ์/สวิตช์ → worker13 → บันทึกผล → COMMIT
             ↑                         │
       ตรวจสถานะเดิมได้          ผิดพลาด: ย้อนกลับงานทั้งรอบ
```

หากหยุดก่อน COMMIT แรก จะยังไม่มีการทำงานลูกค้า หากหยุดหลัง COMMIT แรก คำขอและครั้งที่จองยังอยู่ หากหยุดหลัง COMMIT ที่สอง งานและสถานะสำเร็จจะอยู่พร้อมกัน ไม่มีการสร้าง UUID ใหม่เพื่อข้ามผลที่ยังไม่แน่ชัด

ยังใช้กติกา first_contact เดิมและ worker13 ครั้งละไม่เกิน10งาน ไม่เปลี่ยน Admin, SLA, KPI, Follow-up, Visit, Booking หรือข้อมูลเก่า ร่าง09/13และโค้ดหน้าจอ/APIไม่ได้แก้ในขั้นนี้

## รหัสรอบกับรหัสครั้งที่ลองต่างกันอย่างไร

- `requestId` คือรหัสของงานหนึ่งรอบ คงเดิมตลอดการลองซ้ำ และเป็นรหัสใบรับ worker13
- `attemptId` คือรหัสครั้งที่จองเพื่อเริ่มทำรอบนั้น เปลี่ยนเมื่อจองครั้งใหม่ รหัสครั้งเก่าจะใช้เรียกงานไม่ได้
- การจองแต่ละครั้งบันทึกเลขธุรกรรมเต็ม `xid8` ไว้ `execute` จะปฏิเสธหากยังอยู่ในธุรกรรมเดียวกับการจอง จึงนำ prepare+execute มาเรียกใน transaction เดียวเพื่อข้ามการบันทึกถาวรไม่ได้
- ประวัติ attempt เป็น immutable; ตัวตน/วันสร้าง request แก้ไม่ได้ และสถานะ `completed`/`review` ไม่ถูกแก้หรือลบทิ้งเพื่อเริ่มใหม่อย่างเงียบ ๆ

ประวัตินี้เก็บ **การจองแต่ละครั้งและสถานะล่าสุด** ไม่ใช่รายละเอียด error ทุกครั้งในอดีต รหัสผิดพลาดล่าสุดจะถูกล้างเมื่อจองครั้งใหม่ ส่วน `createdAt` เดิมคงอยู่เพื่อให้ตรวจอายุคำขอค้างได้

ใช้ control แถวเดียวชี้รอบปัจจุบัน และ advisory lock ของ dispatcher ก่อนเข้าสู่ worker13 ซึ่งยังใช้ global lock/cursor ร่วมกับ Admin11 ไม่ให้ตัวเรียกสองตัวเริ่มรอบใหม่แข่งกัน

## นโยบายจำกัดความเสี่ยงในร่าง

| เหตุการณ์ | พฤติกรรม |
|---|---|
| จองครั้งแรก | สร้าง request/attempt จาก server และให้เวลาเริ่มภายใน60วินาที |
| เรียกซ้ำขณะยังอยู่ในช่วงจอง | ไม่จองใหม่ ไม่ใช้ UUID ใหม่ ไม่ประมวลผลซ้อน |
| หยุดหลังจองแต่ก่อนทำงาน หรือถูกยกเลิกกลางทาง | ประวัติการจองยังอยู่ หลังหมดช่วงจองจึงใช้ request เดิมกับ attempt ใหม่ |
| ผิดพลาดชั่วคราวที่จำแนกได้ | ย้อนงานทั้งรอบ แล้วพัก60/120/240/480วินาทีก่อนลองครั้งถัดไป |
| ครั้งที่5ไม่สำเร็จ หรือหมดช่วงจองหลังขาดการเชื่อมต่อ | เมื่อประเมินครั้งนั้น/ปลุกรอบถัดไปจะเข้า `review` หยุดอัตโนมัติ ไม่มีครั้งที่6หรือเปลี่ยน UUID หนีขีดจำกัด; ถ้าครั้งที่5สำเร็จยังเป็น completedตามปกติ |
| ผิดพลาดอื่นที่จับได้ | ย้อนงานทั้งรอบ แล้ว `review` พร้อมรหัสปลอดภัย ไม่เก็บข้อความ error ที่อาจมีข้อมูลลูกค้า |
| ทำงานสำเร็จ | งาน/ใบรับ worker/สถานะสำเร็จ commit พร้อมกัน และเว้นอย่างน้อย60วินาทีก่อนสร้างรอบใหม่ |

ตัวเลขเหล่านี้เป็น **นโยบายร่างสำหรับทดสอบ ไม่ใช่ความถี่ production ที่เปิดใช้หรือรับรองแล้ว** หนึ่ง tick ทำไม่เกินหนึ่ง cycle ไม่มีการวนจนหมดฐาน ไม่มีการนอนรอหรือยิง retry ต่อทันทีในคำสั่งเดียว และช่วงจองจำกัดเวลาเริ่ม ไม่ใช่การตัดสินว่างานที่เริ่มแล้วเกิน60วินาทีต้องล้มเหลว

`lock_timeout=500ms` ยังเป็นเพดานการรอล็อกแต่ละครั้ง ไม่ใช่เวลารอบรวม ต้องกำหนด statement timeout ใน session ของผู้เรียกและวัดโหลดจริงก่อนเปิด หากมี895 candidate จริงและทำ10งานต่อนาที จะใช้ประมาณ90นาทีต่อ sweep จึง **ยังรับรองการเตือนก่อน30นาทีไม่ได้** ต้องปรับรูปแบบจำนวนรอบ/ความจุโดยมีผลทดสอบรองรับ ไม่ถือว่า Supabase Pro ทำให้ปัญหานี้หายเอง

## จุดเรียกและสิทธิ์

| จุดเรียก private | หน้าที่ |
|---|---|
| `crm_first_contact_dispatch_prepare()` | จองหนึ่ง attempt หรือคืน SQL NULL เมื่อ busy/รอเวลา/พัก review; ไม่แตะงานลูกค้า |
| `crm_first_contact_dispatch_execute(requestId, attemptId)` | ตรวจว่าเป็นรอบและครั้งล่าสุดที่ commit แล้ว ก่อนเรียก worker13; ไม่รับ task/clock/limit จากผู้เรียก |
| `crm_first_contact_dispatch_status(requestId)` | อ่านสถานะรอบที่ระบุ หรือรอบปัจจุบันเมื่อไม่ส่งรหัส; ไม่เขียนและไม่ส่งงาน |
| `crm_first_contact_worker_tick()` | procedure แบบ top-level CALL: prepare, COMMIT, execute, COMMIT ไม่ลงทะเบียนกับ Cron เอง |

บทบาทใหม่ `buildtrack_sales_sla_dispatcher` เป็น NOLOGIN/NOINHERIT ไม่มีสิทธิ์ระดับผู้ดูแล ได้ schema USAGE และ EXECUTE เฉพาะจุดเรียกนี้ ไม่มีสิทธิ์เข้าตาราง/เรียก worker13 หรือแกน09โดยตรง ไม่เป็นสมาชิก worker หรือ Admin หากชื่อบทบาทมีอยู่แล้วร่างหยุด ไม่ยึดสิทธิ์เดิมมาใช้

เพิ่ม `sla_dispatcher_enabled DEFAULT false` ต้องครบ10สวิตช์จึงจอง/เขียนได้ ปิดสวิตช์ระหว่างสองช่วงจะหยุดงานแต่ไม่ลบคำขอ การอ่านสถานะใช้6สวิตช์อ่านเดิม จึงกู้ประวัติได้ขณะปิดตัวเขียน บัญชี Sales/Owner/Admin ปกติและ worker13 ไม่มีสิทธิ์เรียก dispatcher โดยตรง

สถานะอ่านคืนเฉพาะข้อมูลกำกับคำขอ ไม่คืนชื่อลูกค้า เบอร์ รายได้ JWT เนื้อหาใบรับภายใน หรือ raw SQL error สถานะ `reserved` อาจหมายถึงกำลังทำงานหรือการเรียกขาดหาย ไม่ใช่หลักฐานว่าผิดพลาด; SQL NULL จากการอ่านก็ไม่ใช่หลักฐานว่างานไม่อาจ commit

## ข้อจำกัดของ procedure และการติดตั้ง

ตัว orchestrator เป็น **SECURITY INVOKER ไม่มี SET clause และไม่มี EXCEPTION block ครอบ COMMIT** จึงแยก transaction ได้ผ่าน top-level CALL เท่านั้น การเรียกภายใน BEGIN/ฟังก์ชันจะถูกปฏิเสธ ส่วนฟังก์ชันสิทธิ์สูงที่อยู่ข้างในกำหนด search_path และตรวจสิทธิ์ด้วย ACL ไม่ใช้ JWT สวม Admin ตามข้อจำกัด [PostgreSQL transaction management](https://www.postgresql.org/docs/17/plpgsql-transactions.html) และ [CREATE PROCEDURE](https://www.postgresql.org/docs/17/sql-createprocedure.html)

ยังไม่ได้พิสูจน์การเชื่อม NOLOGIN capability role กับผู้เรียก Cron จริง, รูปแบบ top-level CALL ของ launcher ที่ติดตั้ง, default privileges/เจ้าของฟังก์ชัน, สิทธิ์ service role และ legacy writers ใน Supabase เป้าหมาย ไม่มีตัวช่วยแอบตั้ง login/membership หรือเปิด extension ให้

SQL12 ยังคง `automationReady=false` เปลี่ยนเหตุผลเป็น `CRON_BINDING_NOT_VALIDATED` และตรวจข้อความอ้าง prepare/execute/tick เพิ่มเป็นสัญญาณชนกับ job เดิม ไม่ถือว่าผล preflight ยืนยันว่า14ติดตั้งแล้วหรือเปิดได้

## ขั้นถัดไปก่อนเปิดจริง

ผลตรวจในเครื่อง: native dispatcher120assertions + concurrency/recovery22assertionsผ่าน รวมactual top-level CALLและstatement timeoutหลังCOMMITแรก; ชุดเดิมทั้งหมดผ่าน Vitest3,921ข้อ/78ไฟล์, TypeScriptและscoped ESLintผ่าน ฐานจำลองหยุดแล้ว ผลนี้ไม่แทนการตรวจCron/สิทธิ์หรือข้อมูลจริง

1. ตรวจแบบติดตั้งและ privilege/launcher binding ในสภาพแวดล้อมที่ผู้ใช้อนุญาต พร้อมยืนยัน statement timeout และวิธีปิดเฉพาะงานเรา
2. วัดความจุ/backlog และเวลาเตือนด้วยข้อมูลสมมติที่ใกล้ขนาดจริงก่อนเลือกความถี่ ไม่ใช้ผลทดสอบตรรกะแทน load test
3. ออกแบบการแจ้งผู้ดูแลเมื่อเข้า review/ค้าง/ใกล้หมด budget และกระบวนการอนุมัติแก้ปัญหาโดยรักษาประวัติ ปัจจุบันมี read-only status แต่ยังไม่มีหน้า/ช่องทางแจ้งผู้ดูแลและไม่มีคำสั่งปลด review
4. จัด migration ติดตั้ง/ซ้อมและลงทะเบียน job แบบปิด หลังได้รับอนุมัติแยก จึงตรวจรับก่อนเปิดส่งจริง

ร่างนี้ยังมี RAISE ก่อน DDL และ ROLLBACK ท้ายไฟล์ ห้ามถอดตัวหยุดแล้วนำไปรันเอง หลักฐานการทดสอบและข้อจำกัดอยู่ใน [รายงานฐานแยก](D:/buildtrack/buildtrack-mvp-main/docs/sales-v2-isolated-database-tests.md)
