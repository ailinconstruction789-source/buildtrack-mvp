# ลูกค้าจองรายโครงการจาก Lead ส่วนกลาง

23 กันยายน 2569 — เตรียมโค้ดและร่าง SQL19 ในเครื่อง ไม่ได้เปิดใช้งานจริง ไม่อ่านข้อมูลลูกค้าจริง ไม่รัน SQL บน Supabase และไม่ Deploy

ต่อเนื่องรอบ SQL21: เพิ่มลิงก์ตามรหัสการจองจริงไปยัง [งานสัญญาและสินเชื่อ](D:/buildtrack/buildtrack-mvp-main/docs/sales-v2-post-booking.md) เมื่อสวิตช์งานหลังจองพร้อมเท่านั้น รายการ19ยังเป็นตัวอ่าน ไม่เพิ่มคำสั่งเขียนในหน้านี้ และยังไม่มีการเปิดสวิตช์จริง

## สิ่งที่เชื่อมในรอบนี้

`Lead ส่วนกลาง → customer เดิม → ความสนใจรายโครงการ → sale แต่ละแปลง/รอบ → หน้าลูกค้าจองของโครงการ`

- หน้า `/sales-crm/projects` อ่านจากการจองจริงที่เชื่อม `sales.project_interest_id` ไม่อาศัย `sales.lead_id` จึงเห็นการจองใหม่จาก SQL18 ที่ไม่สร้าง legacy Lead ซ้ำ
- หนึ่งแถวต่อ sale ID ไม่ใช้การจองรายการแรกของลูกค้า ไม่รวมหลายแปลงหรือหลายรอบเข้าด้วยกัน คนที่เพียงสนใจหรือ Visit แต่ยังไม่จองไม่ปรากฏเป็นลูกค้าจอง
- แท็บกำลังซื้อ / โอนแล้ว–ส่งมอบ / ยกเลิก / ทุกสถานะ; กู้ถูกปฏิเสธแต่ยังดำเนินการต่ออยู่ไม่ถูกนับเป็นยกเลิกเอง
- ค้นหาชื่อ เบอร์ และแปลงจากทั้งโครงการและสถานะที่เลือก ไม่ใช่เฉพาะ 50 รายการที่โหลด ใช้ข้อความตรงตัว ไม่ตีความ `%` หรือ `_` เป็น wildcard
- แบ่งหน้า 50 sale แสดง `hasMore` จากรายการที่ 51 จัดลำดับวันจองและ ID แน่นอน ไม่แสดงจำนวนแถวในหน้าเป็นยอดรวม/KPI
- ราคา วันจอง วันยกเลิก เบอร์ และแปลงเก่าที่ไม่มีหลักฐานยังเป็น “ไม่ทราบ” ไม่เติมจากวันสร้าง/ราคาแปลงหรือศูนย์ โครงการปิดรับใหม่ยังดูประวัติได้
- แสดงผู้ดูแลความสนใจปัจจุบัน ไม่อ้างว่าเป็นผู้รับยอด KPI ย้อนหลัง
- ลิงก์ประวัติใช้ customer ID เดิมไปยัง `/sales-crm/bookings` เพื่อดูทุกรอบ ไม่แก้ทับประวัติ cancelled
- Sales/Admin/Owner อ่านได้ทุกโครงการ หน้านี้ไม่มีคำสั่งเขียน ไม่มีปุ่ม Lead รายโครงการ ลบ นำเข้า Clear Data หรืออนุมัติส่วนลด

ตัวอ่านเป็น GET + RPC แบบ STABLE เท่านั้น ตรวจ JWT/บทบาทจากฐานและความพร้อม SQL18/19 ไม่เชื่อบทบาทจาก browser ไม่ใช้ service-role key ไม่บันทึก audit/receipt หรือเรียก worker จากการอ่าน

ตรวจการเชื่อมข้อมูลเก่าก่อนกรอง/แบ่งหน้า หากยังมี legacy sale ที่ไม่เชื่อม หรือความสัมพันธ์ลูกค้า/ผู้ดูแล/โครงการ/แปลงเสีย ให้หยุดพร้อมแจ้ง Admin ไม่ซ่อนรายการผิดปกติด้วยตัวกรอง ไม่รวมลูกค้าด้วยชื่อหรือเบอร์ กรณี legacy sale ระบุโครงการไม่ได้ให้ตรวจข้อมูลก่อนอ่านโครงการใด ๆ

## ทางเข้าที่เตรียมไว้ โดยสวิตช์ยังปิด

- `SALES_CRM_PROJECT_SALES_ENABLED`: เปิดได้เฉพาะส่วนอ่านและลิงก์จาก Lead ส่วนกลาง ต้องใช้ร่วมกับ V2/Lead Work/Lifecycle/Booking เดิมและความพร้อมฐานข้อมูล
- `SALES_CRM_PROJECT_WORKSPACE_ENABLED`: แยกอีกสวิตช์สำหรับเปลี่ยนทางเข้าโครงการเดิม **ยังไม่ควรเปิดจนตรวจรับการเปลี่ยนระบบครบ**
- Layout ฝั่ง server ส่งเพียงโหมด `legacy` / `central` / `blocked` ให้ตัวครอบทางเข้า ทั้งจากหน้าหลักและ `/sales` ไม่มีการส่ง token หรือค่าลับ การเปลี่ยนสวิตช์ต้องตรวจการ Deploy และโหลดหน้าใหม่ด้วย
- สวิตช์เปลี่ยนทางเข้าปิด: หน้าปัจจุบันและ props เดิมยังทำงานเหมือนเดิม ไม่ได้ลบไฟล์ SalesKanban
- สวิตช์เปลี่ยนทางเข้าเปิดและส่วนอ่านพร้อม: เปิด ProjectSalesWorkspace โดยไม่ mount SalesKanban ทั้งชุด เพราะแผนที่/แบบแก้ลูกค้า/นำเข้าเดิมก็มีการเขียน legacy ไม่ใช่แค่แท็บ Lead
- ทางเข้าตาราง Visit เดิมในโหมดใหม่แสดงทางไปงานส่วนกลาง ไม่เปิดตารางเก่าหรือสร้าง Lead รายโครงการ; ไม่ได้อ้างว่าตารางนัดหมายรวมแบบใหม่ทำเสร็จแล้ว
- ตั้งค่าไม่ครบหรืออ่านข้อมูลใหม่ไม่ได้: หยุดในหน้าแจ้งปัญหา ไม่เปิด legacy กลับมาเขียนแทน ไม่มีการแก้ env จริงในรอบนี้

การไม่ mount หน้าเดิมเป็นเพียงขอบเขต UI **ไม่ใช่การปิดสิทธิ์เขียน legacy ที่ฐานข้อมูล** browser เก่า/หน้าอื่นยังต้องถูกป้องกันด้วย RLS/trigger ที่ตรวจรับแล้วก่อนเปิดจริง

## ส่วนที่ยังไม่แทนของเดิม

ต่อเนื่องรอบเชื่อมรายงาน: [รายงานจองส่วนกลางและขอบเขตเมนูเดิม](D:/buildtrack/buildtrack-mvp-main/docs/sales-v2-booking-reports.md) พร้อม SQL20 แทนยอดสรุปจองผ่านโหมดทางเข้าได้แล้วในโค้ดที่ยังปิด ไม่ได้ทำรายงานทุกมิติหรือคำสั่งสินเชื่อ/โอนครบ ข้อจำกัดเดิมด้านการเปิดใช้ยังคงอยู่

1. แผนที่/ราคา/เอกสาร/รายงาน/แดชบอร์ดเดิมยังไม่ได้แปลงครบ เช่น `SalesDashboardExcelStyle`, `SalesReportsView`, `SalesSummaryTable` และตัวอ่านในหน้าอื่นยังมีเส้นทาง legacy ไม่ควรใช้เป็นยอดตรวจรับ V2
2. ยังต้องตรวจและยุติผู้เขียน legacy ทุกทาง รวมทั้ง `lib/sales_api.ts` และแท็บ/หน้าที่อยู่นอก SalesKanban; ไม่ใช่เพียงซ่อนปุ่ม
3. หน้านี้อ่านสถานะสัญญา/สินเชื่อ/โอน แต่ไม่ได้เพิ่มคำสั่งทำสัญญา ยื่นกู้ หรือยืนยันโอน ต้องมี replacement ที่ครบก่อนพักปุ่มเดิม
4. ยังต้องทบทวน schema/RLS/trigger จริงและ backfill ที่อนุมัติ รักษา 895 identity/เบอร์แทนและค่าไม่ทราบ ไม่อ่านหรือย้ายข้อมูลจริงในรอบนี้
5. ทดสอบ staging ครบเส้นทางและจัด migration ที่ผ่าน review ให้ผู้ใช้รันเอง จากนั้นขออนุมัติเปิดฟีเจอร์/Deploy แยกกัน

SQL19 มีตัวหยุดรันทันทีและ ROLLBACK ผู้ใช้ยังไม่ต้องนำไปรันบน Supabase ส่วนแจ้งเตือนที่พักไว้ไม่ถูกเปิดจากงานนี้

## การตรวจสอบ

ใช้ข้อมูลสมมติและ mock เท่านั้น ชุดทดสอบตรวจสิทธิ์ สวิตช์ การคงหลาย sale ต่อ customer ขอบเขตค้นหา/สถานะ ข้อมูลไม่ทราบ ผลตอบกลับเก่าข้ามโครงการ และการไม่ mount legacy เมื่อสลับโหมด ส่วนฐานข้อมูลแยกตรวจ RPC จริงใน transaction แบบ READ ONLY และเทียบผลกับตัวอ่าน TypeScript โดยไม่ถือเป็นการรับรองฐาน production

- Vitest ทั้งโครงการ: 4,792 tests ผ่าน / 112 files โดยจำกัดหนึ่ง worker
- PostgreSQL ฐานแยกโหมด `project-sales-only`: 71 assertions ผ่าน รวม READ ONLY transaction และการเทียบ business snapshot ก่อน–หลังอ่าน ผล SQL ผ่านตัวอ่าน TypeScript (`projectionParity: true`); รายงาน `node_modules/.cache/buildtrack-sales-runtime/runs/run-egkPvg/report.json` ระบุ `passed` และ `stopped: true`
- ร่าง base/04–19 รวม 17 ไฟล์ compile ในฐานสมมติและ hash ตรงก่อน–หลังทดสอบ รอบนี้ไม่ได้รันชุด concurrency/ความจุของระบบแจ้งเตือนซ้ำทั้งหมด และไม่ใช่การรับรอง production
- ตรวจชนิดข้อมูลทั้งโครงการผ่าน โดยจำกัดหน่วยความจำเฉพาะตัวตรวจเหมือนรอบก่อน
- ESLint เฉพาะไฟล์ส่วนใหม่/จุดเชื่อม และ `git diff --check` ผ่าน ไม่เปลี่ยน lint เดิมทั้งไฟล์ใหญ่ที่ไม่ได้อยู่ในขอบเขต
- รอบแรกของชุดทดสอบรวมพบ 3 ข้อที่อ้างรายชื่อ SQL และข้อความโหมด runner เก่าก่อนเพิ่ม18 จึงปรับความคาดหวังให้ตรงขั้น18/19 โดยคงการตรวจลำดับและความปลอดภัยไว้ ก่อนรันชุดรวมผ่านทั้งหมดข้างต้น
- ยังไม่ได้ทดสอบด้วยบัญชีจริงหรือบนระบบ Deploy

ข้อสังเกตจากการทดสอบ: ชุดข้อมูลสมมติครั้งแรกพยายามเปลี่ยน identity ของ sale เก่าหลังใช้ guard18 จึงถูกปฏิเสธตามกติกา แก้เฉพาะการสร้าง fixture ให้ใส่ sale ที่เชื่อมแล้วพร้อม source snapshot ในคำสั่งเดียว ไม่แก้ trigger18 ไม่ disable/defer FK และไม่เปิดทางแก้ cancelled history; ฐานที่ล้มเหลวก็ถูกปิดแล้วเช่นกัน
