ผู้ใช้ยืนยันเป้า **แจ้งเตือนภายใน 5 นาทีหลังงานเข้าสู่ช่วงเตือนล่วงหน้า 30 นาที** เป็นเป้าความเร็วระบบ ไม่เปลี่ยนกำหนดบริการลูกค้า 24 ชั่วโมง / Follow-up 48 ชั่วโมง / เวลาให้ Sales 120 นาทีทำงานตามเงื่อนไขเดิม

## สิ่งที่เปลี่ยนและสิ่งที่คงเดิม

[SQL16](D:/buildtrack/buildtrack-mvp-main/sql/sales/16_bounded_burst_dispatcher_draft.sql) เพิ่มนโยบาย `bounded_burst_v2` ต่อจาก SQL14 โดยไม่เพิ่มขนาด worker13 หรือคัดลอกสูตร SLA ใน SQL09 มีตัวหยุดก่อน DDL และ ROLLBACK ท้ายไฟล์ จึงยังไม่ใช่ migration ติดตั้งจริง

| สวิตช์ใหม่ | `sla_burst_enabled` เริ่ม false และต้องผ่านสวิตช์เดิมครบด้วย |

เลือกเพิ่มจำนวนรอบย่อยที่มีเพดาน โดยยังใช้ลำดับ/cursor กลางเดิม งานที่ขาดหลักฐานยังถูกพักพร้อมเหตุผล ไม่ทิ้งงาน ไม่เปลี่ยนวันเดิม ไม่ยกงานเก่าไปเป็นผลงานใหม่ และไม่เปิดทางให้คิวใกล้กำหนดแซงจนงานอื่นถูกปล่อยค้างไม่มีกำหนด ขณะนี้เป็นการเพิ่มความจุ **First-contact เท่านั้น** ไม่ได้เพิ่มตัวประมวลผล Follow-up/Visit/Booking

เพดาน 5/10 วินาทีจำกัดการจองเริ่มรอบ ไม่ใช่คำรับรองอัตราจบงานหรือจำนวนแจ้งเตือนจริง ไม่จำกัดงาน Admin/worker อิสระทั้งหมดในฐาน การเรียกซ้ำที่คืนใบรับเดิมไม่กิน admission ใหม่

## ประวัติและการหยุดอย่างปลอดภัย

- คำขอเก่าเก็บ `completion_spacing_v1` และกติกาพัก 60 วินาทีเดิม แม้เปิดสวิตช์ใหม่ ไม่เปลี่ยนนโยบายย้อนหลัง คำขอใหม่ในโหมด burst จึงค่อยเป็น `bounded_burst_v2` และแก้ policy ของคำขอไม่ได้
- แต่ละรอบยังจอง request/attempt/admission แล้ว COMMIT ก่อน execute; ผล worker และสถานะจบ COMMIT พร้อมกัน ใช้ request UUID เดิมในการกู้ ไม่สร้างรหัสใหม่เพื่อหลบงานค้าง
- ถ้าปิด burst ระหว่างจองกับ execute จะไม่ทำผลของคำขอ v2 ต่อ ไม่ตีความเป็นคำขอเก่าเมื่อสวิตช์ปิด อ่านประวัติได้ตาม read gates เดิม การกู้ต้องผ่านนโยบายที่ถูกต้อง
- จำกัด 5 attempts ต่อคำขอ, reservation 60 วินาที, backoff/review และหลักฐานเดิม คิวที่เข้า review ยังหยุดรอการตรวจ ไม่มีการปลด review อัตโนมัติหรือปุ่มแก้ review ใหม่ในขั้นนี้
- ประวัติ admission ห้ามแก้/ลบและอ้าง attempt จริง ใช้เวลาฝั่งฐาน; ถ้าพบเวลาเดินย้อนก่อนหลักฐานล่าสุดให้ปฏิเสธ ไม่ลบประวัติเพื่อรีเซ็ตเพดาน
- เรียก procedure แบบ top-level เท่านั้น ไม่ใส่ CALL ใน transaction ครอบหรือ SECURITY DEFINER ที่มี COMMIT ฟังก์ชันภายในตรึง search_path/UTC ส่วน procedure แบบ invoker ระบุชื่อ namespace ของสิ่งที่เรียกชัดเจน

SQL16 เปลี่ยนชื่อ implementation ของ prepare/execute14 ให้เป็น helper ส่วนตัว แล้วครอบด้วยการตรวจนโยบายและสิทธิ์ ไม่คัดลอกตัว execute14 ต้องตรวจการเปลี่ยนชื่อ/สิทธิ์/แผนคำสั่งค้างใน connection เดิมและการเรียกจาก connection ใหม่ใน staging ก่อนออก migration ที่ติดตั้งได้

ฟิลด์ `nextAttemptAt` ของคำขอ v2 ที่ **completed** ยังเป็นค่าที่ implementation14 บันทึก (`completedAt + 60s`) แต่ไม่ใช่เวลาปลุกรอบ burst ถัดไป ให้ตีความร่วมกับ policy/status และ admission window ห้ามใช้ฟิลด์นี้เพียงตัวเดียวทำ UI หรือตัวตั้งเวลาใหม่ สำหรับคำขอที่ยังไม่จบ ฟิลด์นี้ยังคงความหมายของ reservation/backoff

## แบบจำลองไม่ใช่คำรับรองความจุ

[burst-capacity.mjs](D:/buildtrack/buildtrack-mvp-main/scripts/sales-runtime/burst-capacity.mjs) เป็น pure helper ไม่ตั้ง timer/เชื่อมฐาน สมมติชุดงานคงที่, ไม่มีผู้แย่ง admission/งานเข้าใหม่/การลองซ้ำ/review, ปลุก fixed-phase และงบต่อรอบรวม prepare/execute/commit/ค่าเรียกทั้งหมด

การปลุกทุก 10 วินาทีอาจชน admission ที่จองช่วงท้ายของรอบก่อน จึงไม่รับรองผลเลขนั้น แบบจำลองบังคับช่วง tick ไม่น้อยกว่า `10 วินาที + งบเวลาของรอบย่อยทั้งหมดต่อ tick` ก่อนให้ผลว่าเข้าเป้า เมื่อสมมติรอบละ 1 วินาที/ไม่เกิน 5 รอบ จึงใช้ 15 วินาที ไม่ถือว่าผลวัด worker เพียงอย่างเดียวพิสูจน์งบ 1 วินาทีได้

| สมมติฐานที่ 895 candidates แน่นอน / รอบละ 1 วินาที | เวลากวาดตามแบบจำลอง | เข้าเป้า 5 นาทีในแบบจำลอง |
|---|---|---|
| เริ่มหัวชุด / admission window ว่าง | 4 นาที 35 วินาที | ใช่ |
| ไม่ทราบ cursor / window ว่าง | 4 นาที 46 วินาที | ใช่ |
| ไม่ทราบทั้ง cursor และ admission window | 5 นาที 1 วินาที | ไม่ใช่ |

มีการเผื่อรอ tick แรกและเวลา cycle สุดท้ายด้วย ตัวเลขแสดงว่าระยะเผื่อยังน้อย ไม่ใช่เหตุผลให้เปิดจริงทันที จำนวนเก่า 895 Leads ไม่เท่ากับ candidate backlog จริง; ถ้ารายงานชน LIMIT901 ให้ถือเป็นขอบล่าง ไม่รับรองความจุ `activationReady=false` และ `guaranteesDelivery=false` เสมอ

## การตรวจในฐานสมมติ

ผลล่าสุด `run-MoFYVc` ผ่านและหยุดฐานแล้ว: กวาด895งานครบใน18wakes/90cycles สร้าง448แจ้งเตือนถูกตามกรณี ก่อนกำหนด224รายการมีความหน่วงDB-visibleสูงสุด **4นาที31.239วินาที** ต่ำกว่าเป้า5นาที ค่าp50=2นาที16.129วินาที และp95=4นาที16.367วินาที ไม่ใช่ผลทดสอบหน้าจอหรือSupabaseจริง รอบแรกพบตัววัดเลือกจุดเริ่มผิด จึงแก้เฉพาะตัวทดสอบและทดสอบใหม่ทั้งชุดตามประวัติในรายงานฐานแยก

คำสั่ง `npm run test:sales-db -- --burst-capacity` รันชุดเดิมจนถึง SQL15 ก่อน จึงสร้าง SQL16 เพื่อแยกตรวจว่าพฤติกรรมเดิมยังผ่าน จากนั้นตรวจ policy/เพดาน/สิทธิ์/COMMIT/สวิตช์/การหยุดและกู้คำขอ แล้วค่อยจับเวลาชุด 895 งานจริงทุก 15 วินาที มีจำนวนรอบสูงสุด ไม่ติดตั้งงานเบื้องหลังถาวร

fixture มี Sales สมมติ 8 คน เวรต่อเนื่องคนละหนึ่งช่วง แบ่งงานเป็นขาดหลักฐาน/ยังไม่ถึงเวลา/ใกล้กำหนด/เกินกำหนด เก็บประวัติเดิมต่อ ไม่แก้ timestamp ของ admission ไม่ปิด trigger เพื่อเร่งช่วง 10 วินาที มีการรีเซ็ต control/cursor เฉพาะการแบ่งกรณีของฐานสมมติ และปรับ deadline ที่แก้ได้เฉพาะกรณีทดสอบกู้ reservation ไม่ใช่กระบวนการ recovery สำหรับ production

การจับเวลาวัดจากจุดเริ่มช่วงเตือนที่ fixture กำหนดไว้ล่วงหน้า (`seeded_at`) จน query แยกอ่านพบแจ้งเตือนหลัง commit โดยยืนยันว่า `available_at` และ `staff_due_at - 30 นาที` ตรงจุดเริ่มนี้จริง ไม่ใช้ `task.notify_at` ซึ่งเป็นจุดเริ่มรับผิดชอบ/เริ่มงาน ไม่ใช้เวลาประมวลผลเป็นจุดเริ่ม เป็น **DB-visible latency** ไม่ใช่เวลาที่เบราว์เซอร์ Sales แสดงผล ไม่ทดสอบ Supabase Cron launcher, JWT/PostgREST/Next E2E, ปฏิทินซับซ้อน, ข้อมูลจริงหรือโหลดอื่นพร้อมกัน ผลละเอียดและสถานะหยุดฐานบันทึกใน [รายงานฐานแยก](D:/buildtrack/buildtrack-mvp-main/docs/sales-v2-isolated-database-tests.md)

## สิ่งที่ยังต้องทำก่อนรับรอง 5 นาทีและเปิดจริง

อัปเดตขั้น2: เตรียม [ส่วนอ่านสถานะคิวสำหรับ Admin และแนวทาง Review](D:/buildtrack/buildtrack-mvp-main/docs/sales-v2-queue-monitor.md) ในเครื่องแล้ว ยังไม่รวมตัวแจ้งผู้ดูแลอัตโนมัติ/การวัดเวลารอและอายุ sweep จริง/คำสั่งกู้ Review จึงยังไม่ถือว่าข้อ2เสร็จทั้งหมด และต้องเพิ่ม SQL17 เข้าขอบเขตข้อ3

อัปเดตขั้นถัดมา23กันยายน: ข้อ1เตรียมโค้ดในเครื่องแล้วตาม [ผลหน้าแจ้งเตือนอัตโนมัติ](D:/buildtrack/buildtrack-mvp-main/docs/sales-v2-notification-refresh.md) ยังไม่เปิดระบบจริง เหลือข้อ2–5; การรับรองเวลา5นาทีครบเส้นทางยังอยู่ในข้อ4

1. **หน้าจอ — เตรียมแล้วในเครื่อง:** `NotificationsView` อ่านอัตโนมัติประมาณ15วินาทีหลังรอบก่อนจบ พักเมื่อซ่อนแท็บ/ออฟไลน์ และอ่านใหม่เมื่อกลับมา ป้องกันข้อมูลข้ามบัญชี/คำขอซ้อน ยังต้องวัดงบฐาน + API + refresh + render รวมกันในข้อ4 ไม่รับรองเวลาที่ผู้ใช้ปิดแอป/ออฟไลน์ และไม่มี push notification
2. **Monitoring/review:** วัดเวลารอจริง/อายุ sweep/candidate ที่นับแน่นอน/งานขาดหลักฐาน/คำขอ review และแจ้ง Admin เมื่อเสี่ยงเกิน 5 นาที ต้องมีกระบวนการแก้ review ที่รักษาประวัติ ไม่ใช้การลบ ledger/reset control เป็นทางลัด
3. **Audit:** SQL15 ตรวจรายการทางเข้าเดิมเท่านั้น ยังไม่ครอบคลุม procedure/helpers/admission table ใหม่ใน16 และส่วนอ่านใหม่ใน17 ส่วน SQL12 ยังไม่รู้จักชื่อ burst และ gate ใหม่ครบ ต้องขยาย inventory/audit ก่อนตรวจรับ ไม่ถือรายงานเดิมเป็นใบรับรอง SQL16–17
4. **Staging ที่อนุญาตแยก:** ตรวจเวอร์ชัน/DDL/grants/body/เจ้าของ/cached connections, ผู้เรียกจริง, top-level CALL, timeout, การปลุก/คิวงานซ้อน/stop/recovery และ throughput ภายใต้โหลดจริง กำหนด hard timeout ของ caller โดยไม่สับสนกับ soft 8 วินาที
5. **ติดตั้งและเปิด:** หลังผ่านข้อข้างต้นค่อยออก migration/ซ้อม rollback และ job แบบปิด ขออนุมัติแยกก่อนแตะ Supabase หรือเปิดส่งจริง ไม่เปิดตัวตั้งเวลาสองชุดคู่กัน ไม่เปลี่ยนแพ็กเกจ Vercel/Supabase ในขั้นนี้

### ขอบเขตหน้าจอที่ใช้ดำเนินการขั้น1 (ดูผลล่าสุดในลิงก์ข้างต้น)

จุดเชื่อมคือ [NotificationsView](D:/buildtrack/buildtrack-mvp-main/components/sales/NotificationsView.tsx) ที่ `/sales-crm/notifications` และ client/API อ่านรายการเดิม เสนอเริ่มด้วยการรีเฟรชแบบอ่านอย่างเดียวขณะเปิดหน้าและแท็บใช้งานอยู่ พร้อมโหลดใหม่เมื่อกลับเข้าแท็บ ไม่สร้างแจ้งเตือนหรือทำเครื่องหมายว่าอ่านแล้วจาก timer ไม่ใช้ client เรียก worker โดยตรง

ต้องรักษาตัวกันคำขอซ้อนและผลตอบกลับเก่า (`busyRef`/`generation`), หยุดเมื่อเปลี่ยนบัญชีหรือสิทธิ์, ไม่ให้ผลเก่าข้าม session, ไม่รบกวนคำสั่ง “อ่านแล้ว” และไม่รีเซ็ตหน้าที่ผู้ใช้กำลังเปิดเอง เมื่อเน็ตขาดให้แสดงสถานะข้อมูลไม่ล่าสุด ไม่อ้างว่าไม่มีงาน การรีเฟรชหน้านี้อย่างเดียวยังไม่ทำให้มีแจ้งเตือนบนทุกหน้าแอปหรือขณะปิดแอป

ทดสอบก่อนเปิด: แจ้งเตือนใหม่ปรากฏโดยไม่กดโหลด, ซ่อน/กลับแท็บ, request ช้า/ล้มเหลว/ซ้อนกับ mark-read, เปลี่ยนบัญชี/สิทธิ์ระหว่างรอ, pagination และ cleanup เมื่อออกจากหน้า พร้อมวัดเวลาตั้งแต่ eligibility ผ่าน DB → API ที่ผ่านสิทธิ์ผู้รับจริง → หน้าจอ ต้องรวมเวลารอรีเฟรชในเป้า5นาทีด้วย ไม่ใช้ผลอ่านตารางด้วยสิทธิ์ตัวทดสอบแทนผลเห็นในบัญชี Sales
