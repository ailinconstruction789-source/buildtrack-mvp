## 3. ช่องว่างที่ต้องแก้ก่อนต่อหน้าจอ

1. ปัจจุบัน Lead หนึ่งแถวผูกกับโครงการเดียว ทำให้ลูกค้าคนเดียวที่สนใจหลายโครงการถูกนับซ้ำและมีสถานะร่วมกันไม่ได้อย่างถูกต้อง
2. สถานะและ Sales เจ้าของยังอยู่บน Lead ไม่ได้แยกตาม “โครงการที่สนใจ”
3. การเปลี่ยนสถานะบางจุดแก้ตารางโดยตรงและยังไม่บังคับเหตุผลทุกครั้ง
4. Visit ยังถือว่าสำเร็จได้โดยไม่ผูกกับ Customer Voices อย่างบังคับ
5. การยื่นกู้มีเพียงวันที่/สถานะล่าสุด จึงเก็บประวัติการยื่นใหม่หลังถูกปฏิเสธไม่ได้
6. สิทธิ์ข้อมูลฝ่ายขายในฐานข้อมูลยังเปิดกว้างแก่ผู้ใช้ที่ล็อกอิน และยังไม่มีรายชื่อ Sales ประจำโครงการ
7. แปลงที่เล็งไว้เก็บบน Lead เดิมและยังไม่มีการตรวจว่าเป็นแปลงว่างในโครงการเดียวกันที่ระดับฐานข้อมูล
8. `status_history` เดิมยังไม่มีรหัสเหตุผล รายละเอียดเหตุผล และผู้ใช้ที่เปลี่ยนสถานะแบบอ้างอิงกับบัญชีจริง
9. ระบบปัจจุบันใช้ `projects.name`/`plots.project_name` เป็นตัวเชื่อมโครงการ ไม่มี `projects.id` ในฐานข้อมูลจริง จึงออกแบบ Phase แรกให้เข้ากับโครงสร้างนี้ก่อน

## 4. แบบข้อมูลเป้าหมาย

```text
ลูกค้า 1 คน (sales_customers)
  ├─ สนใจโครงการ A 1 รายการ (lead_project_interests)
  │    ├─ Sales เจ้าของ / สถานะ / แปลงที่เล็ง
  │    ├─ กิจกรรมและ Follow-up หลายครั้ง
  │    ├─ Visit หลายครั้ง → Customer Voices ของแต่ละ Visit
  │    ├─ ยื่นกู้หลายครั้ง
  │    └─ การจอง/ขาย 1 รายการ
  └─ สนใจโครงการ B 1 รายการ
       └─ มี Sales เจ้าของและสถานะของโครงการ B แยกต่างหาก
```

ตารางใหม่/ส่วนขยายที่เสนอ:

| ส่วน | หน้าที่ |
|---|---|
| `sales_customers` | ข้อมูลลูกค้าหลัก ชื่อ เบอร์ และข้อมูลส่วนบุคคลที่ใช้ร่วมกันทุกโครงการ |
| `lead_project_interests` | หนึ่งรายการต่อหนึ่งลูกค้า–หนึ่งโครงการ เก็บสถานะ เจ้าของ แปลงที่เล็ง และ SLA |
| `sales_project_members` | กำหนดว่า Sales คนใดเข้าถึงโครงการใด โดย Sales เห็น Lead ทั้งโครงการ |
| `lead_activities` | โทร แชท นัดหมาย Follow-up และกิจกรรมอื่น พร้อมวันติดตามครั้งต่อไป |
| `lead_visits` | เช็กอินเข้าชมและ QR token; Visit สำเร็จเมื่อมี Customer Voices เท่านั้น |
| `loan_attempts` | เก็บการยื่นกู้ครั้งที่ 1, 2, 3… รวมผลปฏิเสธและการยื่นใหม่ |
| `sales_reason_catalog` | เหตุผลมาตรฐานที่ Admin จัดการได้ เช่น Lost และยกเลิกหลังจอง |
| `crm_settings` | ค่า SLA เริ่มต้น 24 ชั่วโมง และ Follow-up ไม่เกิน 48 ชั่วโมง |
| `status_history` | เพิ่มการอ้างอิงรายการสนใจโครงการ เหตุผล และผู้เปลี่ยนสถานะ |
| `customer_voices` | เพิ่มการอ้างอิง Visit และเวลาที่ลูกค้าส่งแบบฟอร์ม |
| `sales` | เพิ่มการอ้างอิงรายการสนใจโครงการและเก็บราคา/ส่วนลด โดยไม่มีขั้นตอนอนุมัติส่วนลด |

## 5. สถานะมาตรฐาน

เส้นทางหลัก:

`new → contacted → appointment → visit_pending_voice → visit_complete → considering/follow_up → booked → contract_downpayment → document_prep → loan_submitted ↔ loan_rejected → loan_approved → transfer_pending → transferred → handover`

ทางออก:

- `lost` ใช้ก่อนจองเท่านั้น
- `cancelled` ใช้หลังจอง โดยแยกเหตุผลเป็น ยกเลิกจอง, ทิ้งดาวน์ หรือกู้ไม่ผ่านสุดท้าย
- ทุกครั้งที่เปลี่ยนสถานะต้องมีรหัสเหตุผลหรือข้อความเหตุผล

## 6. กฎสำคัญที่ SQL ฉบับร่างรองรับ

- สร้างลูกค้าใหม่ต้องมีชื่อและเบอร์โทร
- ลูกค้าคนเดียวสนใจหลายโครงการได้ แต่มีรายการสนใจซ้ำในโครงการเดียวกันไม่ได้
- สถานะและ Sales เจ้าของแยกตามรายการสนใจโครงการ
- แปลงที่เล็งต้องอยู่ในโครงการเดียวกันและยังไม่มีลูกค้าจอง แต่การเล็งไม่ล็อกแปลง
- การจองจริงเท่านั้นที่ล็อกแปลง และหนึ่งแปลงมีรายการขายที่ยังไม่ยกเลิกได้เพียงรายการเดียว
- Visit เปลี่ยนเป็นสำเร็จได้เมื่อ Customer Voices ถูกส่งแล้วเท่านั้น
- รองรับการยื่นกู้ใหม่ด้วยเลขครั้งที่ไม่ซ้ำกัน
- Sales อ่านข้อมูลทั้งโครงการที่ Admin จัดสิทธิ์ให้ ส่วน Admin/Owner อ่านได้ทุกโครงการ
- KPI บริษัทนับจาก `sales_customers.lead_created_at`; Funnel โครงการนับจาก `lead_project_interests.lead_at`
- Sales บันทึกราคาตั้งต้น ส่วนลด และราคาขายสุทธิได้ โดยไม่มีตารางหรือสถานะอนุมัติส่วนลด

## 7. แผนย้ายข้อมูลเดิม

SQL ที่จัดทำใน Phase นี้เป็นโครงสร้างแบบเพิ่มใหม่ ไม่ลบตารางหรือคอลัมน์เดิม เพื่อให้หน้าจอปัจจุบันยังทำงานได้ระหว่างเปลี่ยนระบบ

ก่อนนำไปใช้จริงต้องทำตามลำดับนี้:

1. ตรวจ Lead เดิมที่ไม่มีชื่อ/เบอร์ และเบอร์ซ้ำที่อาจเป็นคนละคน
2. ยืนยันรายชื่อ Sales ที่รับผิดชอบแต่ละโครงการ เพื่อเติม `sales_project_members` ก่อนเปิด RLS ใหม่
3. สร้างลูกค้าหลักจาก Lead เดิมโดยรวมรายการที่เป็นคนเดียวกันด้วยเบอร์โทร
4. สร้าง `lead_project_interests` จาก Lead เดิม และบันทึก `legacy_lead_id` เพื่อย้อนตรวจได้
5. เชื่อม `sales`, `status_history` และ `customer_voices` เดิมกับรายการสนใจโครงการ
6. เปรียบเทียบยอด Lead/จอง/โอนก่อนและหลังย้ายข้อมูล
7. เปลี่ยนหน้าจอให้ใช้โครงสร้างใหม่ แล้วจึงพิจารณาเลิกใช้คอลัมน์เดิมใน Phase หลัง

## 8. ข้อมูลที่ต้องยืนยันก่อนรันจริง

- Sales แต่ละคนรับผิดชอบโครงการใดบ้าง
- กรณีเบอร์เดียวกันแต่ใช้ชื่อคนละชื่อ ให้รวมเป็นลูกค้าคนเดียวเสมอหรือให้ Admin ตรวจทีละรายการ
- เหตุผลมาตรฐานของแต่ละสถานะที่ต้องการให้แสดงใน dropdown
- การแก้ข้อมูลรายได้/ข้อมูลส่วนบุคคล: Sales ทุกคนในโครงการแก้ได้ หรือให้แก้ได้เฉพาะ Sales เจ้าของ Lead
